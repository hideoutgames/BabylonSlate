# Feature Test project

Inventory and rules for the built-in **Feature Test** starter (`apps/editor/src/lib/feature-test/`): what each scene and zone authors, the workload knobs, media slots, on-device check, perf route and known gaps. It showcases every engine feature in one project and is the agents' default deterministic performance workload. The [FeatureTest rule](../rules/feature-test.md) requires any feature change to update the scaffold, this file and the scaffold test in the same PR.

## How it is built

- Create Project → Feature Test (listed only in Debug Mode). `ProjectService.createEmptyProject(name, { kind: "feature-test" })` runs the Basic 3D scaffold (Input assets, Kenney Mannequin) and then lazily loads [`apps/editor/src/lib/feature-test/`](../../apps/editor/src/lib/feature-test/).
- `index.ts` runs areas in a fixed order so every referenced asset exists before its referrer: imports, audio, materials, scripting types, scripting, the `FT_Timeline` asset, rendering, physics, world, animation, particles, AI, 2D, Scene Layers. Area modules then place actors in their zones. Scene documents save last (Scene Layers, sub-scenes, scenes, then the main scene), then the navmesh bake and project settings.
- Content is deterministic: fixed ids, positions and counts. Only asset guids differ between projects, so tooling finds assets by path or name.
- Feature Test's own assets live under `assets/FeatureTest/<Area>/`, an Always Package Folder, so Preview Build and export ship the whole showcase. The Basic 3D scaffold keeps its files where it writes them: the startup scene `assets/main.scene.hasset`, Input assets under `assets/Input/`, and the Mannequin (`assets/Mannequin/` plus `assets/Mannequin.class.hasset`), which the areas reuse.
- Zones sit on a 32 m grid in [`layout.ts`](../../apps/editor/src/lib/feature-test/layout.ts) (`FEATURE_TEST_ZONES`); each has an Outliner folder and a 3D Text label. The main camera `ft-camera-main` (`FT_RenderCameraTour`) starts at the head of the closed `FEATURE_TEST_CAMERA_TOUR` Spline (`Camera Tour Path`, `FT_RenderCameraPath`) and, in Play, Preview and export, rides it at 6 m/s (about 2.5 min a lap) on a lagging Spring Arm: in front of the first row, low through both gaps between rows, high behind the back row and down the left side. Play-frame measurements of the main scene therefore see a moving view. Landscape and water live in the separate `FT_World` scene.

## Scripting, data and settings

- **Game Instance** `FT_GameInstance` (Project Settings): logs on init; on the first scene prints the scene name, spawns `FT_ScriptSpawned` when the Scripting zone exists (Deferred Spawn Actor, a Cast and Set Variable writing its `SpawnedBy`, then Finish Deferred Spawn Actor; its Begin Play prints that value, which `ft_spawn` leaves at its default), and runs `ft_stats`. **Subsystems**: `FT_GameScoreSubsystem` (GameSubsystem), `FT_GameSceneWatcher` (SceneSubsystem).
- **Editor**: `FT_EditorProbe` (EditorUtilityObject, registered) logs editor events; `FT_EditorMath` (EditorFunctionLibrary) is authored only.
- **Types and data**: `FT_ScriptSpeedMode` (Enum), `FT_ScriptSpinConfig` (Structure), `FT_ScriptDescribable` (ScriptInterface), `FT_DataItemStats` / `FT_DataItems` (Data Definition and Data Tree; `DamageRoll` is a built-in Float Range field), `FT_DataFalloffCurve` / `FT_DataSwayCurve` / `FT_DataTintCurve` (Float, Vector and Color Curve assets), `FT_DataProgress` (SaveGame, `wipeOnPlay` on). The probes check themselves with the Assert family, so a broken read reports a session error: `FT_DataProbe` asserts that it found `Weapons/Sword` (Assert) and that `Weapons` has two children (Assert Equal), and holds built-in range and curve Structure variables (`SpawnCount`, an Int Range; `DamageFalloff`, a three-key Float Curve) that it checks with Evaluate Float Curve and Clamp Integer To Range (Assert Equal), and asserts that the Sword's Damage lies in its `DamageRoll` (Is Float In Range), and that Get Float Curve Object and Get Value At Time read `FT_DataFalloffCurve` at 1 s (Assert Equal); `FT_ScriptInterfaceProbe` asserts that it found the Fast Spinner (Assert Is Valid) and that the Game Instance ran On Init before its Begin Play (Assert); `FT_DataSaveProbe` stores an Int Range and a Float Curve variable in the `SavedRange` and `SavedCurve` Structure fields of `FT_DataProgress`, asserts that its save succeeded, then reads both fields back and checks them with Clamp Integer To Range and Evaluate Float Curve (Assert Equal); `FT_ScriptObjectProbe` (Scripting zone) keeps an `FT_ScriptDataObject` from Create Object in a variable, creates an `FT_ScriptTicker` (Object with the engine Tickable Object interface, which counts `ObjectTicks` on the Game Instance) and drops it in Drop Ticker with Collect Garbage, both custom events that never wait so no latent frame holds the ticker, then asserts it ticked (Assert), stopped ticking once collected (Assert Equal) and that the kept object is still valid (Assert Is Valid); `FT_GameInstance` asserts that it spawned `FT_ScriptSpawned` (Assert Is Valid) and that the `ft_stats` console command succeeded (Assert).
- **Input**: Basic 3D actions plus `FT_ScriptPulse` (P, pad button 3, Swipe Up, Double Tap or Shake; every press also rumbles pad 0 through Set Gamepad Rumble and vibrates the device through Vibrate Device) and `FT_ScriptNudge` (arrow keys or Two-Finger Drag); the HUD joystick adds touch bindings to Move.
- **Timeline Clips**: the main scene holds `Intro` (4 s, one Custom Event Track `On Intro Line` with a key at 0.5 s) and `FT_HUD` holds `Reveal`, both without property tracks; their Scene Scripts bind and play them on Begin Play (above). `FT_World` holds `Door Loop`, the animated one (property tracks on an actor transform and two Light properties, Auto Play, Loop).
- **Timeline Asset**: `FeatureTest/Timeline/FT_Timeline` (created by `timeline.ts` before any scene binds to it) holds `Intro`, `Reveal` and `Door Loop`: clips from a Scene, a Scene Layer and a second Scene. The main Scene Script reaches Intro and its re-fired event through it, and `FT_TimelineListener` does the same for Door Loop from a Class. It also holds two clip assets, played through Create: `FT_DoorSwing` (3D, Loop: a Door actor proxy with a Rotation track, a Handle Glow `LightComponent` proxy with an Intensity track, an `On Swing Open` event), which each `FT_SwingDoor` in FT_World creates with Door bound to Self and Handle Glow to its light, and `FT_HudPulse` (2D, Ping Pong: a Badge `2DTextComponent` proxy whose Opacity dips), which every FT_HUD instance's Scene Layer Script creates on its title text. The gate requires the `FT_SwingDoor heard On Swing Open (FT_DoorSwing)` and `FT_HUD script plays its own FT_HudPulse` lines.
- **Heard lines**: the scaffold test also requires the `heard` lines these event handlers print (main: `On Intro Line (Intro)`; `FT_World`: `On Door Open (Door Loop)`), so a handler whose asserts never ran fails it.
- **Project settings**: Garbage Collection Interval 30 ticks (Scripting module); Feature Test tags, collision layers Default, Dynamic, Trigger, Water, Ghost, with Collision Presets Default, Dynamic, Trigger, Ghost and Ghost Pass (Dynamic layer; Overlap on Ghost, Block on the rest); every physics-zone collider names its layer's preset; PBR with Scene Linear and ACES, bloom, vignette, white balance, the High tier's MSAA 4x Anti-Aliasing, FSR at render scale 0.8, ambient occlusion, reflections and volumetrics at 0.5 scale (the starter takes the new-project High quality; ambient occlusion and reflections run from Medium, scene-wide volumetric fog from High; the Effects zone's Fog Volume renders on every tier); Real-Time Reflections apply in CEL too, so `ft_cel` at Medium and above keeps the metal and mirror surfaces reflecting; shadows on; render path Auto; WebGL2; dynamic resolution off; Onest as the default font.

## On-device check and benchmark

The **Feature Test** starter and its check appear only with Engine Settings → Debugger → **Debug Mode** on; e2e routes enable it through `seedEngineSettings`. When a scene fails to load in Debug Mode, **Copy Error** on the Scene Loading dialog copies the failure details; in Play, **Copy Details** during a load also says what the first frame is waiting on.

For devices without a test harness (iPad, phones, other browsers), a Feature Test project's **Debug** menu has **Run Feature Test Check…** (phones: **More Tools** → Debug). It walks the scenes with the editor's own controls and writes a plain-text report; **Copy Report** copies it (the text stays selectable when the clipboard is unavailable).

| Mode | Scenes | Per scene |
| --- | --- | --- |
| Quick | Current Feature Test scene (main otherwise) | Open in the editor and sample viewport frames; Play, sample frames, run `ft_stats`; Stop |
| Full | `main`, `FT_World`, `FT_Lights`, `FT_Occlusion`, `FT_2D`, `FT_Stress` | As Quick; the main scene also runs `ft_spawn 10`, `ft_stream`, `ft_cel`, `ft_pbr`, and `FT_Occlusion` runs `ft_occlusion` |
| Benchmark | All five | Play with the frame cap lifted to 240, then 5 s per profile: `low`, `medium`, `high`, `ultra`. After its commands each profile waits up to 90 s until the view draws without held frames (a profile can rebuild every lit shader and its render targets); when the view does not, the profile reports it and that scene's sweep stops, so changes do not pile up on a view that stopped drawing. quality and cap are restored afterwards |
| Breakdown | `FT_World`, `FT_Occlusion` (**All Scenes**: all six) | A GPU breakdown without timer queries, at the normal 60 fps cap (iOS Safari paces frames to the display, so a lifted cap only queues frames behind a busy GPU), by one of two methods (`FeatureTestBreakdownMethod`, the dialog's **Add One** / **Remove One**, kept in `FeatureTestBreakdownInfo.method`; the base's label is its `tier`). A tablet GPU near its cap runs at two speeds with hysteresis, so a change measured there says only whether a step crossed the cap; hence **add-one is the default**: every sample stays below the cap, so a change is the feature's own cost. Each method has a base (`FEATURE_TEST_BREAKDOWN_BASES`), applied before the warm-up and, after `quality reset`, again after every step: add-one's is `quality low`, `quality resolution scale 0.5` (also turns dynamic resolution off), shadow filter low, water detail low, water reflections sky, water refraction off, anti-aliasing off, AO, SSR and volumetrics off by name, `postprocessing off` and `rendertargets off` (its `cleanup`, `postprocessing on` and `rendertargets on`, runs after `quality reset` at the end); remove-one's is `quality medium` then `quality resolution reset` (tiers below Ultra turn dynamic resolution on, which the project keeps off). Otherwise it waits until no shader has been first drawn or compiled for 3 s (at most 90 s) and samples 5 s with `gpubusy on` (GPU-busy time per frame from fences, restarted per sample; `gpubusy off` at the end). First it warms up at the base in 10 s windows until two consecutive windows differ by under 3% (GPU-busy median, else mean frame time), at most 90 s. A unit test replays every step's commands through `RenderingQualitySession` and requires each to change only its own fields, or to be one of the expected skips. Only when the dialog's **Compare Preserve Drawing Buffer** checkbox (off by default, `FeatureTestBreakdownInfo.ab`) is on does the preserveDrawingBuffer A/B (below) run the same scenes and steps again after one editor reload; otherwise the Breakdown is one pass at the stored setting, with no reload |

- **Report**: app version, device (platform, touch points, pixel ratio, screen, cores, memory), browser and GPU adapter (iPadOS Safari reports a Mac; `MacIntel` with touch points is labelled `iPad (reports MacIntel)`). Per scene: editor and Play load times and where a load stuck (an editor load failure adds its error with cause chain; the GPU line falls back to the viewport's adapter when Play never ran); fps, p95, max frame, stalls over 100 ms; draw calls per frame over the sample window (read every half second; their median, with the range when frames differ: a pass that draws on alternate frames, such as a static view's planar reflection, moves one frame's count by its whole draw count), mesh and texture counts, CPU/GPU frame cost (median and range over the sample, as draws), render resolution; console command output and duration; shaders first drawn after the scene presented (`firstDraws`, read once its commands ran, so Full's `ft_spawn 10` counts; WebGL2 only): how many, how many the load compiled, the frames that held them, those over 100 ms, the worst one and the most in one frame; long frames after the scene presented (from the same session, WebGL2 only): how many took over 100 ms and the four longest, each with its time inside the Engine's frame, first draws and compiles; Preview Session Report entries; texture counts before and after Play (`LEAK` when textures created during Play are still loaded after release; Babylon's once-per-Engine placeholder textures do not count); Play error/warning lines.
- **preserveDrawingBuffer A/B** ([`feature-test-breakdown-ab.ts`](../../apps/editor/src/lib/feature-test-breakdown-ab.ts)): the attribute is fixed when the project Engine is created, so after the first pass (the stored setting) the dialog keeps that pass and a resume marker in localStorage (`haptic:feature-test-check:breakdown-resume`), stores the other setting and reloads the editor after a 3 s status with **Cancel**. Home's `FeatureTestCheckResume` reopens the project from the project list (marker stage `reload` → `reopen`); the check dialog, mounted with the project, starts the second pass on the same scenes (`second-pass`), then stores the user's setting again and writes one report (the live Engine keeps the switched attribute until the editor reloads or the project is reopened; the report says so). A marker that is unreadable or older than 30 minutes, or found past `reload` when the editor loads (the attempt stopped part-way), is never retried: the user's setting is stored again and the report of what completed waits in the dialog (`saveFinishedCheck`; a crash during the second pass leaves both passes as the unfinished record, which gets the notes). The A/B runs one pass, with a note, when the first is cancelled, measured no baseline, ran on WebGPU (`presentation.preserve` is `n/a`), its project is not the top project-list entry, storage fails, or the page did not reload within 20 s (e.g. the unsaved-changes prompt was dismissed).
- **Breakdown output**: a header line with the method, the base and each pass's stored setting (`no A/B` for a single pass), `preserveDrawingBuffer on vs off, median baseline gpu busy: <scene> <on> vs <off> ms (off ±ms, ±%)` per scene and camera (the median of each pass's baseline GPU-busy medians, grouped by each scene's live attribute), the A/B's notes, `WARM DEVICE: previous run ended N min ago` under the result line when the Breakdown started within 10 minutes of the end of the last check of any mode (`haptic:feature-test-check:ended`, decided once before the first pass), and `NON-ADDITIVE` / `SATURATED` / `OVER CAP` on the result line. Scenes are grouped under `Pass N of 2 · preserveDrawingBuffer on|off (live)`. Per scene: a one-line legend, a `preserveDrawingBuffer: on|off (live)` line (the Engine's live attribute, `presentation.preserve` in the settings fingerprint), a `Base:` line, a `Warm-up drift:` line (the first warm-up window against the last, steady one, `breakdownWarmupDrift`, so a GPU that changed speed while warming shows), `NON-ADDITIVE:` (remove-one only) when a camera's step savings (`breakdownAdditivity`; steps marked `overlaps`, a lower setting or part of another step or the resolution scale, are left out) sum past its first baseline in its basis, `SATURATED:` when over half the baselines' frames (weighted by frame count, `breakdownSaturation`) lasted 4+ display intervals, `OVER CAP:` (add-one only) for each baseline past `ADD_ONE_CAP_MS` (30 ms GPU-busy median, else mean frame time; `breakdownOverCap`), a timing line (the GPU-busy poll interval, which bounds each frame's timing error), then a per-step table: fps over the window, mean and p95 frame time, the share of frames lasting 1/2/3/4+ display intervals (`vsync`; vsync-paced frames last 16.7, 33.3 or 50 ms, so a bimodal split means pacing, not cost), `gpu busy` (median and p95 GPU-busy time per frame, `RenderDiagnostics.gpuBusy`), the change against the baselines of the same camera around the step (a baseline's against that camera's first: drift such as thermal throttling; the camera switch is not drift), CPU frame cost (median), what bounds the frames (`gpu` when they take over 1.5 times the CPU cost, `vsync` at the cap, otherwise `cpu`), draws (median and range over the sample) and notes. The change compares GPU-busy medians when the step and its baselines measured them, since display pacing does not quantise them; otherwise mean frame time (the median snaps to a whole display interval), marked `*`. GPU-busy time is a frame's fence completion minus the later of its submission and the previous frame's completion; fences are polled from a zero-delay timer (clamped to about 4 ms), so each frame is up to one poll late, an error that does not accumulate across frames. Warm-up windows are rows marked `warm-up`, never references. Notes list the render settings the step changed against its camera's first baseline (`RenderDiagnostics.settings`: `qualitySettingsFingerprint` in `@haptic/core` (shadows, `shadows.filter`, device-clamped water refraction, refraction scale, reflections, planar scale, shading detail and FFT grid (`water.fft`, size x cascades), post-processing tier values, resolution scale, `geometry.occlusion`) plus the live MSAA samples, `post.enabled`, `captures` and `presentation.preserve`), `no setting changed` when a measured step changed none of its fields, `skipped (already …)` for a skipped step (no frames), `own ±ms beyond <step>` for an add-one step that `includes` another (its change less that step's), `OVER 30 ms` for an add-one step whose GPU-busy median passed the cap, `fft <size>x<cascades>` for a water detail step, `UNEXPECTED:` for a setting outside its own, `NOT RESTORED:` for a baseline or warm-up window that differs from that baseline, `UNSETTLED:` when shaders were first drawn or compiling during the sample, and, while the view culls, `occlusion culled <culled>/<tested> · <n> tris · <ms> ms` (the medians of `stat draws`' occlusion row over the sample: meshes culled of those tested, occluder triangles, culling time). For add-one the change is the feature's cost on the base; for remove-one, on a GPU-bound device below saturation, its share of the Medium frame.
- **Benchmark output**: a per-profile table per scene (quality tiers include their resolution scale, so the resolution column changes between tiers) and the highest Forward tier that holds 60 fps (>= 55 fps, p95 <= 25 ms) and 30 fps (>= 28 fps, p95 <= 45 ms), per scene and across all.
- **Crash**: a running check keeps its report so far and a resource sample every 2 s (Effects every Engine holds and how many are still compiling, the Play view's drawn and held frames and graphics context losses, textures and their estimated GPU bytes from `estimateTextureMemory`, the JS heap where the browser reports it, the native shell's footprint) in this browser's localStorage ([`feature-test-check-record.ts`](../../apps/editor/src/lib/feature-test-check-record.ts)); Benchmark samples are kept as each profile finishes. When the app stops during a check (a crash, an out-of-memory reload), reopening the dialog shows that report marked `DID NOT FINISH`, with the step it reached and the last 60 samples; during an A/B's second pass the record holds both passes. The same key keeps a finished report the dialog has not shown (an A/B whose second pass was abandoned). Finishing, cancelling, **Start** and **Run Again** clear it.
- **Pass/fail**: a scene fails when it does not open or load (120 s each), a command fails or times out (60 s), the session report has an error, or release is not confirmed. While a check runs a small status bar with **Cancel** replaces the dialog and the Preview Session Report dialog is held back (its entries go into the report).
- **Code**: runner [`feature-test-check.ts`](../../apps/editor/src/services/feature-test-check.ts); text report [`feature-test-check-report.ts`](../../apps/editor/src/lib/feature-test-check-report.ts); dialog [`feature-test-check-dialog.tsx`](../../apps/editor/src/components/feature-test-check-dialog.tsx); A/B resume [`feature-test-breakdown-ab.ts`](../../apps/editor/src/lib/feature-test-breakdown-ab.ts) and Home's [`feature-test-check-resume.tsx`](../../apps/editor/src/components/feature-test-check-resume.tsx). `FEATURE_TEST_CHECK_SCENES` must name existing scenes (the scaffold gate checks this); a new or renamed Feature Test scene is added there in the same PR.

## Performance testing

The opt-in route `e2e/feature-test-perf-route.spec.ts` runs only through `playwright.perf.config.ts`:

```sh
HAPTIC_PERF_FEATURE_TEST=1 pnpm run test:e2e e2e/feature-test-perf-route.spec.ts \
  --config playwright.perf.config.ts --project perf-software
```

It creates FeatureTest through the real Create dialog, waits for background texture encodes, then for each scene in `HAPTIC_PERF_SCENES` records editor viewport frames, overlay Play frames, tick rate, draw calls, main-thread busy time and long tasks, and times create, scene ready, Play boot and reopen; each scene's Play entry also carries the load's spawnable warm-up report (`spawnableWarm`). A scene that shows **Scene Loading Failed** is retried once and counted as `loadRetries`; a second failure fails the run. The JSON report is attached to the test, written to `test-results/perf-route/`, and also to `HAPTIC_PERF_OUT` when set.

| --- | --- | --- |
| `HAPTIC_PERF_SCENES` | `main,stress` | Any of `main`, `stress`, `world`, `lights`, `occlusion`, `2d` (with `HAPTIC_PERF_COMMANDS=ft_occlusion` to cull) |
| `HAPTIC_PERF_SAMPLE_MS` / `HAPTIC_PERF_SAMPLES` | 15000 / 2 | Measurement windows per host |
| `HAPTIC_PERF_WARMUP_MS` / `HAPTIC_PERF_SETTLE_MS` | 10000 / 5000 | Play warm-up and editor settle |
| `HAPTIC_PERF_QUALITY` / `HAPTIC_PERF_FRAMECAP` | project defaults | Play console `quality` (then `quality resolution reset`, so resolution stays fixed) and `framecap` |
| `HAPTIC_PERF_VIEWPORT_CAP` | Engine Settings (30) | Editor viewport frame cap |
| `HAPTIC_PERF_REOPEN` | 1 | `0` skips the reload-and-reopen timing |
| `HAPTIC_PERF_LABEL` / `HAPTIC_PERF_OUT` | none | Free-text label; extra report path that survives the next run |

Rules: compare runs on the same machine, browser project and build only; never assert frame rates. Dynamic resolution is off in FeatureTest projects so the workload stays fixed. Quick smoke: `HAPTIC_PERF_SAMPLES=1 HAPTIC_PERF_SAMPLE_MS=2000 HAPTIC_PERF_WARMUP_MS=2000`. Agents wrap long runs in `pnpm --silent agent:wait local --script test:e2e -- <same arguments>`.

### Fly-through route

`e2e/feature-test-flythrough-route.spec.ts` (opt-in `HAPTIC_PERF_FLYTHROUGH=1`, same config) looks for camera-motion stutter. It creates FeatureTest, optionally switches the project backend and quality in Project Settings, then per scene drives the editor camera along a fixed eye path at fly speed the way the joystick and WASD do (a pose change and camera invalidation per animation frame under a continuous render lease): a static warm-up, then the same path `HAPTIC_FLY_PASSES` times. The test-build hook `__hapticViewportTest.flyThrough` ([`flythrough-probe.ts`](../../apps/editor/src/testing/flythrough-probe.ts)) instruments the Engine for the run only and records every rendered frame: main-thread frame time, eye position, and counters for new Effects, WebGL links and compiles or WebGPU pipelines, shader modules, bind groups, buffers, textures and uploads, material and define invalidations by flag, failed readiness checks, strict readiness probes, graph builds, held frames, shadow generator construction, disposal and moves, enabled-light changes and visible-set churn, plus long tasks and JS heap. The spec ranks spike frames, correlates event kinds with frame cost, groups the event log (with stacks) and, with `HAPTIC_FLY_PROFILE=1`, adds the hottest functions of each spike frame from a CDP CPU profile. Counts are hardware-independent; compare counts across backends and builds, and times only on one machine.

## Verification

[`apps/editor/src/services/project-service.feature-test.test.ts`](../../apps/editor/src/services/project-service.feature-test.test.ts) (node) creates the project in memory and reopens it. It requires every `ENGINE_COMPONENT_CLASS_IDS` entry (`packages/core/src/engine-components.ts`), every creatable (`CREATABLE_ASSET_TYPES`) and imported asset type, and every `ENGINE_BASE_CLASSES` entry to be present; every dependency to resolve; every document to decode; Play validation to report no errors; every compiled script to load the way Play loads it; every Material and Material Instance to compile; every Particle and Animation Graph to validate; every Scene to open clean (the open-time prefab instance sync leaves it unmodified, so the next Scene opens without an Unsaved Documents prompt); and physics pairing to be clean. Class instances are authored in the form that sync produces, for example both Mesh material override keys. In the browser, [`e2e/feature-test-smoke.spec.ts`](../../e2e/feature-test-smoke.spec.ts) (part of the required e2e shards, about 4 minutes) creates the starter, opens the main scene in the editor viewport, plays it on software GL until the load has finished, Scene Layers included (`frameAdmission.worldLoading` false and no Scene Loading dialog; Play draws frames minutes earlier), and for three seconds more, and fails on any Preview Session Report error, so a renderer combination that fails to load or warm (an outline beside a Mirror once did) or raises a WebGL error that fails the presentation (the built-in Mirror surface's geometry-pass draw once did) fails in CI; a Scene Layer load starving behind the world's slow frames (the HUD's once took ten minutes more) fails it too; the other browser routes are perf-only.

It then plays each `FEATURE_TEST_CHECK_SCENES` scene for 180 ticks (three seconds), headlessly, as editor Play does without a renderer ([`run-project-scene.ts`](../../apps/editor/src/testing/run-project-scene.ts)). That is the same compile, asset preparation, load control and boot, with native physics and the Save Game in memory. Preloads and streamed scenes get their sources the way Play prepares them. Any session error fails the scene: a failed assert, an uncaught error, a failed scene or Scene Layer load, or a boot that did not start. So the probes assert what they check, and a feature whose result can be checked within those ticks should assert it too.

## Known gaps

A feature that cannot be showcased is recorded here with its reason; never skip it silently or weaken the gate.

- Console `quit`: it ends the Play session, so the starter's console workload never runs it.
- Skinned Skeletons and retargeted Animations: the repository has no skinned model (the Mannequin is a hierarchy rig, the door a node animation).
- MSDF font atlases: none exists; text uses the facetype and Onest source Fonts.
- Sprites cut from atlas sub-rects: the Sprite editor preview reads V top-down and the runtime bottom-up, so `FT_2D` Sprites use whole-frame Textures and crates stay Tilemap tiles.
- Color grading waits for a human-supplied CC0 LUT in its slot (Kenney publishes no LUTs).
- Project plugins (PluginSettings): the scaffold host has no plugin API, so no project plugin is authored.
- Environment Source Texture: no `.env` or prefiltered cube exists in `engine-content`; the hub lights from its Skybox instead.
- HDR environment import: no human-made `.hdr` panorama exists in `engine-content`, so the starter authors no Texture converted from one (nor its kept panorama or Face Size); `hdr-environment.test.ts`, `import-worker-client.test.ts`, `e2e/environment-texture.spec.ts` and `e2e/import-progress.spec.ts` cover conversion, Face Size, the import worker and cancellation with numeric RGBE data.
- Editor-only by design: Spline drawing (the camera tour still travels its Spline in Play), the EditorFunctionLibrary, and graph debugging, watches, the stepping bar, Step, Pause On Errors and node breakpoints (Class and Behaviour Tree nodes, State Machine states and transitions, with conditions and hit counts) in Simulation and editor Play, the Profiler's console commands (`profile start`, `profile stop`, `capture frame`) and its Scripts view (editor state, never in an asset), which add no authored data: simulate or play the starter and open any Class, Behaviour Tree or Animation Graph with live instances.
- Physics query channels: the authored queries are the `FT_UIPitCounter` Sphere Overlap Actors on Dynamic and the `FT_ScriptTouchProbe` Project Touch To Scene on the default channel. Line Trace, Sphere Shape Sweep, Project Cursor To Scene and the Static, Character, Solid and Triggers channels are not authored in any zone yet.
- `FT_World` cold open on a real GPU is slow: its Water bodies compile large fragment shaders that ANGLE/D3D11 builds one variant after another, taking many seconds each with an empty shader cache; the loading budgets renew while the driver is still compiling. A view that draws Water through its scene copy compiles only the variants it draws (copy-sampling colour variant and its depth pre-pass, during graph preparation under the `Forward transparent` pass id), but colour and depth still compile sequentially because the depth pre-pass is probed only once the colour variant is ready.
- Main-scene Play on software GL (the `perf-software` project, SwiftShader) does not finish loading in reasonable time; this is the recorded exception to the "first frame on software GL" requirement. Every scene cold-opens within the `SCENE_FIRST_FRAME_TIMEOUT_MS` first-draw budget, and `FT_World`, `FT_Lights`, `FT_2D` and `FT_Stress` Play load. In main-scene Play the world layer is ready and keeps drawing under the `FT_HUD` layer's loading UI; each frame costs seconds of main-thread time, almost all of it the registered-view canvas copy waiting for SwiftShader, and each HUD slot acquisition re-checks its dependency closure in storage so every storage completion queues behind such a frame. Engine follow-ups: throttle a ready layer while another owner loads; share catalog revision checks between concurrent slot acquisitions. `FT_Stress` Play loads but then runs at one frame every few seconds on software GL.
- Engine follow-ups found while authoring: Scene Layer switcher entries and virtualized-list item classes are not in Play's required closure (the HUD places sample instances as a workaround); BT Play Animation and Play Sound guids are not header dependencies.
