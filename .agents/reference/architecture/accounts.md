# Project browser and accounts

Launcher routing, optional and required sign-in, the temporary demo account, and Clerk setup for web, desktop and mobile builds.

## Launcher

- `App` retains settings and the project/document owner. `AppRoutes` loads mutually exclusive Home and Editor route modules. Play, validation, search, utility execution, and renderer hosts mount only with the Editor route.
- Haptic is dark only; there is no theme setting or toggle.
- The launcher is a sidebar (wordmark, Projects and Templates, account row) beside the library. Project cards show the chosen icon framed in the project colour, or the uploaded picture when `appearance.cover` is not `icon`; the caption shows a compact age (`31m ago`) and the Local and Source Control status.
- An empty library shows **Start Your First Project** with flat Basic 3D, Basic 2D and Blank tiles (`homepage-welcome.tsx`). Those tiles and the Templates cards open New Project at the naming step with that template chosen. The editor's first chrome tab shows the open project's icon or picture in its colour (`ProjectIdentityMark`).
- Where source control exists (`isSourceControlHost`), the header's **Clone** opens Clone Project (lazy), which clones a repository's branch into a new app-storage project and then opens it as a listed project ([source-control.md](source-control.md#integrated-mode)).
- App boot plays the full-screen intro in `apps/editor/index.html` ([architecture.md](../architecture.md)). Opening a project shows one flat splash card from `LauncherTransitionProvider` (`launcher-transition.css`): the text wordmark (the intro's Block Berthold face and fringes), an amber-to-red progress line, status and build label. Its colours are editor tokens (`--background`, `--card`, `--foreground`, `--brand-*`, …), so it follows the Application theme; the page has no CSS reset, so the card sets `box-sizing` itself.
- The project browser owns its dialogs, account UI, styles, and animation lifecycle. Opening a project unmounts that entire surface, including its inline stylesheet. Returning to the browser creates fresh menu state; project state stays with `DocumentProvider`. JavaScript modules may remain in the browser's import cache.
- Project selection mode (toolbar **Select**, or **Select Project** in a card's actions) makes the card-wide button a pressed toggle and hides the card actions and context menu. Its **Delete** dialog (`homepage-delete-projects-dialog.tsx`) snapshots the selection, lists `removeDeletesProject` tiers for deletion and chosen folders as **Can't Be Deleted**, needs the typed phrase (trimmed, case-insensitive for touch keyboards), and passes only the listed projects to `removeListedProject`, one at a time, stopping at the first failure.
- Opening, reconnecting, recovery, updates, and removal show operation status and keep launcher actions disabled until the operation settles. Web project options explain browser-local storage and Export Project backups.

## Accounts

- Web and Electron keep account sign-in optional, including phone-sized browser windows. Native iOS and Android require an active Clerk session before the project browser mounts; missing configuration, loading failures and pending sessions keep it hidden, and the app offers no way around sign-in. Development builds synced with `--demo` skip the requirement for simulator and emulator testing ([development.md](../development.md#native-shells-capacitor)): `VITE_MOBILE_DEMO=true` is compiled into the bundle, and distribution builds refuse it. This account requirement is separate from subscription plans.
- **Mobile offline access.** Once signed in, the iOS and Android apps open local projects offline indefinitely. The launch check (`NativeClerkClient.restore()`) shows progress and decides the gate: `signed-in` opens the launcher; `offline` with the cached user (stored beside the token in the account `SecretStore` under `slate-clerk-user:<publishable key>`; the `NativeClerkSession` fields only, never token material) opens it marked offline (the profile row's status reads **Offline**); `offline` without a cached user shows **Let’s Get You Connected**; `signed-out` shows the sign-in form. Each window focus, visible `visibilitychange` or `online` event while signed in runs `restore({ background: true })` without hiding the launcher: `signed-in` refreshes the user and clears the offline mark, `offline` keeps the user and marks it, and only `signed-out` leaves the session (which unmounts the launcher and its dialogs; open projects are in the editor route, outside the gate, and are untouched). Holds still defer these checks: returning from a system picker fires those events, so anything inside the gate that opens one holds the check from the click until the result is handled, the pick is cancelled or the dialog closes (`holdSessionCheck` from `useNativeHomepageAccount()`; a no-op outside the mobile gate), so a definitive sign-out cannot drop a picked file or a form being filled in. The project picture in New Project and Edit Project, the Account dialog's profile picture and delete code, and Clone Project while it clones do this. iOS also sends window focus while the app stays in front (for example as the keyboard closes), so the Homepage holds the check for as long as New Project / Edit Project, Clone Project, Engine Settings, the Account menu or dialog, or a Remove or Delete Projects confirmation is open, with `checkWhenReleased`: a check that came due meanwhile runs as soon as the last of them closes. A picker's hold leaves it to the next focus.
- **Session check outcomes** (`NativeClerkRestore`). Definitive `signed-out`, which clears the token and the cached user: a 401 (any request) or 403 (the session check only; elsewhere 403 carries refusals such as `session_reverification_required`) whose body is Clerk's JSON `errors`, a 404 on `/client/sessions/…` likewise, `response: null` (no client for the token), or a client with no active session. Everything else is `offline` and keeps both: a transport failure or timeout, a 5xx or 429, a 401 or 403 without Clerk's JSON (a captive portal or proxy), a 200 that is not JSON or not a `client` object (`network_error` for any request). Signing out (`signOut`) tries to revoke the session and always clears the token and cached user, so it works offline; only a secure storage failure rejects.
- The mobile gate (`homepage-mobile-account-gate.tsx`) shows the boot intro's text wordmark (the Block Berthold ink over red and amber copies, as on the project splash) above a sheet holding the sign-in, code, loading and failure states: a bottom sheet on phones, a centred card on tablets, a card beside the wordmark on landscape phones. Loading uses the splash's amber-to-red line. The sign-in form, shared with the desktop sign-in dialog (400px wide), opens with **Sign In With** (**Sign Up With** when creating an account), a row of the social providers Clerk enables that the app can finish (GitHub, Discord, Google; see [Social sign-in](#social-sign-in)) and an "or" divider above the email field; iOS also shows **Apple**, disabled until native Sign in with Apple exists. The desktop dialog's title is screen-reader only, so the form heading leads. The form ends with a "Secured by Clerk" footer band: lock icon and text on the page background, never Clerk's logo. The frame reserves all four viewport safe-area insets in every state: it pads the top and sides, and the sheet's surface runs under the home indicator while its padding keeps content above it. CSS owns these insets so the iOS status bar never overlays account chrome.
- When configured on web, the launcher lazy-loads `@clerk/react` to restore the avatar. The launcher's own profile dropdown reads the user from `useUser` and calls `useClerk` for the Clerk sign-in modal (`openSignIn`), account management (`openUserProfile`), and `signOut`. The profile menu opens the **Account** dialog (Account, Subscription and Application sections) from its identity row and also lists Engine Settings and Changelog, for guest, Clerk and native accounts alike. Polling, focus-touch requests, and telemetry are disabled. Electron restores native session identity for its compact profile menu and loads the shared native email-code form when Sign In is selected, using the public Clerk Frontend API through VFS native HTTP. Mobile uses that form as its account gate. Account providers, forms, and UI unmount on entry to the editor. No Clerk dependency enters engine packages.
- The **Subscription** section lists the plans from haptic.no/pricing (Haptic free on desktop, Haptic Pro for phone and tablet, Enterprise by contact). There are no plan-based restrictions in the editor yet.

## Billing

- RevenueCat runs every subscription so entitlements stay unified: Web Billing (`@revenuecat/purchases-js`, loaded only when configured) on web and Electron, and `@revenuecat/purchases-capacitor` for the App Store and Google Play. Both sit behind the `PurchasesPort` in `@haptic/vfs` (`createPurchases`). Clerk handles sign-in only.
- [`subscription-billing.ts`](../../../apps/editor/src/services/subscription-billing.ts) picks `VITE_REVENUECAT_WEB_API_KEY`, `VITE_REVENUECAT_IOS_API_KEY` or `VITE_REVENUECAT_ANDROID_API_KEY` for the host and uses the Clerk user id as the RevenueCat app user id, so one Haptic Pro subscription covers every device. Signing in is required to subscribe. Haptic Pro is sold as two plans, RevenueCat's well-known packages `$rc_monthly` and `$rc_annual` (`MONTHLY_PACKAGE`, `ANNUAL_PACKAGE`, `SUBSCRIPTION_PACKAGES` in [`purchases-port.ts`](../../../packages/vfs/src/purchases-port.ts)). `PurchasesPort.plans(account)` lists those present in the current offering, Monthly first, each with the store's localized price string verbatim and its ISO 8601 billing period (Capacitor: `product.priceString`, `product.subscriptionPeriod`; Web Billing: `product.price.formattedPrice`, `product.normalPeriodDuration`); Haptic never formats or computes a price. On the Subscription page, the Haptic Pro card shows both as a `ToggleGroup` (**Monthly** selected by default), a single plan as text, and, when the offering has neither, an error naming both packages. Subscribers see neither the choice nor Subscribe; they change plans through Manage Billing or the store. `purchase` takes the chosen package identifier, with no default in the adapters, and a missing package fails with a message naming it. Status and plans load when the account changes and again whenever the Subscription page shows after a failed load (`onShow`), so an offline first mount recovers. It checks the `VITE_REVENUECAT_PRO_ENTITLEMENT` entitlement (default `pro`), opens the customer's management URL for Manage Billing only when it is `https:` (with `noopener,noreferrer`), and offers Restore Purchases in the mobile apps.
- `PurchasesPort` calls take the account (`{ apiKey, appUserId }`) and run in one queue per port: each first configures the SDK or switches it to that account (`ensureConfigured`), so purchase and restore work after an initial mount that failed offline, a failed configure is retried by the next call, and a configure for one account cannot finish after a switch to another. `logOut` unbinds the account and never rejects: Capacitor calls RevenueCat `logOut` unless the user is anonymous (which RevenueCat refuses), and forgets the bound user even when the call fails offline, so the next account logs in explicitly; Web Billing closes its SDK instance and configures afresh for the next account.
- Sign-out logs RevenueCat out: `useSubscriptionBilling` when its account goes away, the web Clerk account owner when Clerk reports signed out, and the native account gate when it leaves a session (`endSubscriptionBilling`). The entitlement shown resets with the account.
- Electron hands only haptic.no, the documentation site under `https://hideoutgames.github.io/BabylonSlate/docs/` (**Settings > Documentation**), Web Billing (RevenueCat and Stripe), App Store / Google Play subscription and the GitHub and gitlab.com device sign-in pages ([source-control.md](source-control.md#device-sign-in)) as HTTPS links, and mailto, to the system browser or mail client (`externalOpenUrl`), so Preview scripts cannot open arbitrary sites. Subframes load only the bundled Preview player or, outside it, Web Billing checkout from RevenueCat and Stripe over HTTPS (`isBillingFrameUrl`, `insidePreviewFrame` in `apps/desktop/src/packaged-security.ts`). Desktop checkout and RevenueCat API access from the `app://` origin still need validation with real keys.
- Without keys, purchase and management actions stay disabled and the Subscription page says subscriptions are not set up for the build. Without a signed-in account (guests and `--demo` mobile builds), billing never configures RevenueCat and asks the user to sign in.

## Account management

The Account dialog's Account section differs by host because only the web has Clerk's own account screen.

- **Web:** **Manage Account** calls `clerk.openUserProfile()`; Clerk's screen owns name, picture, connected accounts and deletion. Its delete form wraps `user.delete()` in `useReverification` (`@clerk/ui` `DeleteUserForm`), and Clerk documents account deletion as a sensitive action reverified at the strongest available level within 10 minutes, so the web already re-verifies; the repository does not rebuild that screen. There is no separate Delete Account entry: `@clerk/react` 6.x only offers the `@experimental` `__experimental_startPath`, and the installed types document no value for the delete page.
- **Electron, iOS, Android:** the section edits the Clerk user through `NativeClerkClient` (`updateName`, `setProfileImage`, `removeProfileImage`, `deleteAccount`) behind `NativeProfileActions`. Both session owners (`HomepageNativeAccount` for mobile, `HomepageAccount` for desktop) build them with `nativeProfileActions`, take the refreshed session back, and drop to the account gate (mobile) or guest (desktop) when the account is deleted.
  - **Name:** Clerk's first and last name. The launcher shows `name || username || email`, the order the web profile menu uses.
  - **Picture:** a hidden file input limited to PNG, JPEG, GIF and WEBP up to 10 MB (Clerk's limit), which also runs in iOS WKWebView and Android WebView. `imageUrl` is kept only when the user's `has_image` is true, as on web. Returning from the picker fires window focus, whose session check would unmount the input before its change event if it signed the user out, so the mobile gate skips that check from the Upload Picture click until the upload settles, the pick is cancelled or the section closes (`holdSessionCheck`).
  - **Delete Account:** offered only when the user's `delete_self_enabled` is true, behind a destructive `AlertDialog` that says local projects on the device are not deleted and that a subscription is not cancelled. Success clears the stored client token in the same serialized step. App Store guideline 5.1.1(v) requires in-app account deletion for apps that let people create accounts; that is why native deletion exists.
  - **Reverify before deleting:** the dialog's first action (**Send Code**) starts Clerk session reverification, and **Delete Account** is enabled only once the person enters the emailed code. `nativeProfileActions.deleteAccount` calls `completeReverification` and only then `deleteAccount`, so an unattended unlocked device cannot delete the account. This is Clerk's own mechanism (the one `useReverification` drives around `user.delete()` in the web profile), not a second sign-in: the native client has no OAuth, so a "fresh OAuth sign-in" is not available, and an account created with GitHub, Discord or Apple reverifies with the email-code first factor because Clerk offers it for any user with a verified address. It always runs, even inside Clerk's own reverification window, so the check does not depend on the dashboard. If Clerk offers no `email_code` factor the flow stops with `reverification_unavailable` and nothing is deleted; a second factor (`needs_second_factor`) stops with `additional_verification_required`, as sign-in does. If Clerk still answers `session_reverification_required` after a verified code, the existing "sign out and sign in again" message shows. Holding `holdSessionCheck` from **Send Code** until the dialog closes defers the mobile session check while the person reads the code in a mail app.
  - **Subscription note:** `storeSubscriptionsUrl` gives `https://apps.apple.com/account/subscriptions` on iOS and `https://play.google.com/store/account/subscriptions` on Android, shown as **Manage Subscriptions** in the dialog; Electron subscriptions run through Web Billing, so its note points to **Manage Billing**. The web Account center repeats the note beside **Manage Account**. Both store hosts are already in the Electron `externalOpenUrl` allowlist (`STORE_MANAGEMENT_HOSTS`); links are plain `target="_blank"` anchors, as the pricing link is.
- **Frontend API** (mirrors `@clerk/clerk-js` `User.update`, `User.setProfileImage`, `Image.create/delete` and `User.delete`). `PATCH` and `DELETE` go out as `POST` with `_method`, as clerk-js sends them, so native HTTP stays GET/POST. `/me` calls add `_clerk_session_id`; each change is followed by `GET /v1/client` to read the user back.

| Action | Request |
| --- | --- |
| Name | `POST /v1/me?_method=PATCH`, form body `first_name`, `last_name` |
| Upload picture | `POST /v1/me/profile_image`, multipart part `file` |
| Remove picture | `POST /v1/me/profile_image?_method=DELETE` |
| Start reverification | `POST /v1/client/sessions/{id}/verify`, form body `level=first_factor`; `supported_first_factors` must hold `email_code` |
| Email the code | `POST /v1/client/sessions/{id}/verify/prepare_first_factor`, `strategy=email_code`, `email_address_id` |
| Check the code | `POST /v1/client/sessions/{id}/verify/attempt_first_factor`, `strategy=email_code`, `code`; the response `status` must be `complete` |
| Delete account | `POST /v1/me?_method=DELETE` |

- **Upload transport:** `NativeHttpRequest.upload` carries one base64 image part and no `Content-Type`. Capacitor passes it to the iOS and Android form-data encoders (`dataType: "formData"`, a `base64File` entry, `Content-Type: multipart/form-data` without a boundary, which both natives then set). Electron builds the multipart body in the main process (`encodeMultipartImage`); `validateIpcArguments` accepts it only for a POST without `body`, a plain field and file name, an image type and bounded base64. The picked file's own name never leaves the device.
- **Errors:** unknown server errors read as `account_update_failed` or `account_delete_failed`, never as a sign-in failure. Name and picture rejections have their own messages. `session_reverification_required` after a verified code tells the user to sign in again.
- **Not covered:** connecting more providers to an account, email or password changes, and signed-in device management stay web-only.

## Clerk configuration

Create a Clerk application, copy `apps/editor/.env.example` to `apps/editor/.env.local`, and set `VITE_CLERK_PUBLISHABLE_KEY` to its publishable key. Restart Vite after changes. Never expose a Clerk secret key through Vite. See Clerk's [React quickstart](https://clerk.com/docs/react/getting-started/quickstart) and [provider options](https://clerk.com/docs/react/reference/components/clerk-provider).

Distribution builds read the key from the repository variable `VITE_CLERK_PUBLISHABLE_KEY` (see [Distribution maintainer setup](../distribution.md#maintainer-setup)). Without it, packaged desktop builds are guest-only and Android/iPadOS builds stop at **Sign-In Is Not Set Up**.

Dashboard settings account management depends on (nothing is provisioned by the repository):

- **First and last name** under User & authentication, for name editing on every host.
- **Allow users to delete their accounts**, for deletion on every host. Without it `delete_self_enabled` is false and the native Delete Account entry is hidden.
- **SSO connections** (GitHub, Discord, Google) for social sign-in on every host. Development instances use Clerk's shared credentials; production needs each provider's own OAuth app. The native apps sign in with them but do not connect more providers to an account.
- **Native applications → Allowlist for mobile SSO redirect**: `haptic://sso-callback`. Clerk sends the rotating token nonce only to allowlisted redirects, so the native and desktop social sign-in fails without it.
- **Sessions → Maximum lifetime**, plus **Inactivity timeout** when enabled (and the native-session values where Clerk lists them separately). The native client token survives restarts and app updates, but Clerk ends a session at its maximum lifetime (7 days by default) and the next launch that reaches Clerk asks for sign-in again (offline launches keep the cached user); set it to how long a device should stay signed in.

Web sign-in, sign-up, and account settings use Clerk-managed modal UI; redirect fallbacks honor Vite's deployment base. Configure the Clerk application for the deployed web origin. No account or key is provisioned by the repository. Local projects do not become cloud-synced by signing in.

For Electron and native iOS/Android, enable **Native API** in the Clerk dashboard's Native applications page. Enable email addresses for sign-in and sign-up, **Sign-in with email code**, and email verification codes at sign-up. Use email-only registration without other required profile fields, passwords, or MFA; the native flow handles email codes and refuses authenticated access when additional verification or session tasks remain. Desktop guests can still create and open projects. See Clerk's [email-code configuration](https://clerk.com/docs/guides/development/custom-flows/authentication/email-sms-otp) and [native-client terminology](https://clerk.com/docs/guides/development/sdk-development/terminology).

[`apps/editor/src/services/native-clerk.ts`](../../../apps/editor/src/services/native-clerk.ts) serializes public Frontend API requests with native-client headers, reads the rotating client token from response headers, and stores it through `SecretStore`. iOS uses Keychain, and Android uses the `BabylonSlateSecrets` plugin's AndroidKeyStore-encrypted store. Electron's `app://babylonslate` renderer uses native HTTP and a dedicated account store: OS-encrypted persistence when available, otherwise process memory; restarting a process-memory session requires sign-in again. Signing out of a process-memory session always clears its token; removing an older encrypted token from the file is best effort. No client token is persisted in local storage or project data. The native form supports email-code sign-in/sign-up, resend, restoration, and sign-out. Profile editing, deletion and its reverification are in [Account management](#account-management). The token key includes the publishable key, so a build for another Clerk application starts signed out.

### Social sign-in

The native and desktop apps follow Clerk's native SSO flow (as `@clerk/expo`'s `useSSO`), in [`native-clerk.ts`](../../../apps/editor/src/services/native-clerk.ts); the web build keeps Clerk's own window.

1. `socialStrategies()` reads `GET /v1/environment` and keeps the enabled, authenticatable `oauth_*` strategies. The form shows only those it has a button for, and only where `createAuthBrowser()` exists.
2. `beginOAuth` creates a sign-in with `strategy` and `redirect_url=haptic://sso-callback` and returns `first_factor_verification.external_verification_redirect_url`.
3. `createAuthBrowser()` in `@haptic/vfs` opens it: iOS through the `BabylonSlateAuthSession` plugin's `ASWebAuthenticationSession`; Android through the system browser and MainActivity's `haptic://sso-callback` intent filter, resolving as closed when the app resumes without the redirect; Electron through `shell.openExternal`, limited to provider hosts (`authProviderUrl`), with the deep link from `open-url` (macOS) or a second instance's arguments, one pending sign-in and a three-minute timeout ([`desktop-auth-browser.ts`](../../../apps/desktop/src/desktop-auth-browser.ts)). The scheme is registered by the packaged app (`protocols` in `electron-builder.yml`, `setAsDefaultProtocolClient` on Windows), so macOS and Linux deep links reach only packaged builds.
4. `completeOAuth` accepts only the callback scheme and host, fails on `__clerk_status=failed` unless the code is `external_account_not_found` or `external_account_exists`, reloads the sign-in with `rotating_token_nonce`, and turns a `transferable` first factor into a sign-up with `transfer=true`. A closed browser leaves the form as it was.

Sign in with Apple waits for the native iOS flow (`oauth_token_apple` with the system sheet), which needs the Sign in with Apple capability, a refreshed provisioning profile and the app registered on Clerk's Native applications page.

New and restored sessions must appear active in Clerk's response. While the account UI is mounted, window focus or foreground visibility revalidates a signed-in session in the background (above). These listeners and forms unmount on entering the editor (desktop sign-in forms also unmount when their modal closes). Authentication failure never gates desktop project access. The configured Clerk application and actual desktop/mobile host transport still require end-to-end validation before distribution, including the profile calls, the reverification endpoints against an OAuth-created account, and the multipart picture upload on iOS, Android and Electron; unit tests exercise controlled external HTTP/storage boundaries.

### Shared client and sign-in in progress

- `createNativeClerkClient` returns one `NativeClerkClient` per publishable key, so the desktop account row, its sign-in dialog and the mobile gate share one request queue and token. Every request, its token rotation and `restore`'s token decision run in that queue.
- `signInInProgress` is set by `beginEmail` and `beginOAuth` and refreshed by `resendCode`. It clears when `verifyCode` succeeds or loses the client (`session_unavailable`), when `completeOAuth` returns or throws, when `beginEmail` or `beginOAuth` fails, on `cancelSignIn()` (the browser closed or timed out, **Use Another Email**, the form unmounting, as when the desktop dialog closes), on `signOut`, and `SIGN_IN_HOLD_MS` (15 minutes) after it was last set. A wrong or expired code keeps it. It lives in memory only, so quitting mid-flow clears it.
- While it is set, background checks return `deferred` without a request (the desktop row checks on focus, which fires on return from the mail app or the `haptic://sso-callback` deep link). No check clears the token while it is set or while Clerk's client reports a pending `sign_in` or `sign_up`; the token is the sign-in's.
