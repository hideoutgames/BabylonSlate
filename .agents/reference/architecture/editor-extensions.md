# Editor Extensions

Engine and Project Extensions (trusted JS/TS packages with an editor API, and for gameplay packages a game library and content root) and the graph-based, editor-only EditorUtilityObject, EditorFunctionLibrary and SkyboxCreator types.

## Decisions

- Two separate mechanisms. **Extensions** are JavaScript/TypeScript packages with their own manifest, archive (`.hextension`) and activation host. **Editor utility types** are ordinary graph assets run by the editor ScriptHost. Content plugins (`.hplugin`, [plugins.md](plugins.md)) are a third, content-only format.
- Extensions execute as **trusted code**, in the editor and (gameplay packages) in games; neither host is a security sandbox. Imported Project Extensions stay disabled until enabled, and replacing imported executable code requires confirmation.
- **Editor Only** (default on) keeps a package's code and folder out of Play and packed games. A gameplay package (Editor Only off) adds a game library and an `extension:<guid>` content root ([Gameplay extensions](#gameplay-extensions)); it is not a plugin, so Show Plugin Content and export-preset plugin overrides never apply. Assets an extension's API creates under the project `assets/` are ordinary project assets.
- Editor-only assets and graphs are stripped from Play and export by one set of helpers; runtime graphs never see editor utility classes, their functions or editor-only nodes, even with Context Sensitive off.
- The removed EditorUtilityInterface type (`.eui.hasset`) is not a document kind and not creatable; its header type stays editor-only so leftovers never enter Play or export. The game HUD / UserInterface is removed and must not return through this path.

## Extensions

| Scope | Storage |
| --- | --- |
| Engine Extensions | Protected bundles in `engine-extensions/` plus an app-owned user library. Engine Settings → Engine Extensions manages new-project defaults, downloads and confirmed deletion of user entries; bundled entries cannot be deleted or replaced. |
| Project Extensions | Editable `extensions/<folder>/`: `extension.json`, the editor entry (`index.ts`), the game entry (`game.ts`, gameplay packages), added files under `code/`, content under `assets/`. Project Settings → Project Extensions: enable, maturity and Gameplay badges, diagnostics, commands, New / Import / Export, settings and code file editing. |

- New projects copy the Engine library into editable Project Extensions; later library changes never rewrite copies. A project copy shadows an Engine extension with the same stable `extensionGuid`. `project.json` stores enable overrides by guid.
- Manifest: `kind: "extension"`, `formatVersion`, `extensionGuid`, display name, version, description, author, category, Lucide `iconKey`, `experimental` / `beta` (confirm on enable), `enabledByDefault`, `engineVersion`, `extensionDependencies`, `entryPoint`, `editorOnly` (absent = true), `gameEntryPoint` (default `game.ts`, never the editor entry, required in the package when `editorOnly` is false), `libraryName` (JS identifier, default camelCase of the display name), `appearInContentBrowser` (default false), `contributes` (declarative editor contributions; `{}` when none).
- Missing or disabled dependencies and cycles block activation; version differences are diagnostics only. Malformed manifests and duplicate ids stay visible as disabled recovery entries that cannot activate or export.
- Archive limits: 64 MiB compressed, 256 MiB expanded, 4096 files, 1 MiB per code file (`.ts`/`.js` outside `assets/`), 256 KiB manifest; paths are validated before writing. Exports carry the whole folder: every code file and `assets/`.

### Code entry

- The editor entry exports `activate(api)` (ESM or CommonJS), may be async and may return a cleanup function. Each file is transpiled to CommonJS with `ts.transpileModule` without type checking.
- `linkExtensionModules` follows value imports, re-exports and literal `require` from the entry: specifiers must be relative and stay inside the package; `.ts`, `.js`, `/index.ts`, `/index.js` and a `.js` name for a `.ts` file resolve. Dynamic `import()` and non-literal paths are rejected; type-only imports are erased and may name anything. The bundle is plain data (`{ entry, modules: [{ path, code, imports }] }`); `evaluateExtensionBundle` runs one `new Function` per module with its own `haptic-extension:///` source URL and CommonJS semantics. Extensions use the `api` object, never repository modules.
- Code files: every `.ts`/`.js` outside `assets/` (`readExtensionCodeFiles`). Saves (`EditorExtensionService.save` with `{ write, remove }`) put new files only in `code/` or the entries, never remove an entry, cap each file at 1 MiB and roll back on failure. Refresh reads files from storage, so edits from an external IDE apply on the next refresh, Play or export.
- API surface: `registerCommand` (fields use the shared field schema below), `assets.list/read/create/update` (JSON `.hasset` under `assets/`; updates to open documents are refused), `code.read/write` (`.ts`/`.js` under `code/`; writing never compiles or loads into the game), `materials.convertGlsl` (no save), `log`. The type lives in `editor-extension-host.ts`.
- The project owns activation and commands. Disable, reload or project close removes commands, runs cleanup and invalidates old API references; the host drains outstanding API calls before releasing storage. A refresh with unchanged packages keeps running extensions and retries only failed ones and their dependents. Failures surface as extension diagnostics.

### Contributions and fields

- Contributions are declared in `extension.json` `contributes`, so compile, validation, export and the settings modal read them without running code; code only registers handlers (commands) at activation. Editor-wide Engine Settings never take contributions: extensions are per project.
- One field schema (`normalizeExtensionField`) serves settings and command dialogs: `text`, `multiline`, `code` (`javascript` | `glsl`), `number` (`min`, `max`, `integer`, `unit`), `toggle`, `choice` (`options`); each with `id`, `label`, optional `hint` (label tooltip, never visible text) and a typed `default` filled per type. Ids are unique per form, and per category across sections. `resolveExtensionFieldValues` gives every field a value of its type (numbers clamped and rounded, unknown choices and keys dropped), falling back to the default.
- `contributes.settings { title, sections[{ id, title, fields }] }` (optional) adds Project Settings category `extension:<guid>` under the extension's own `title` in the Plugins & Extensions group while the extension is enabled; its fields join settings search (`property-ext-<guid>-<fieldId>`). Values live in `project.json` `extensionSettings[guid][fieldId]` (primitives only, `normalizeProjectSettings`) and are always read through the resolver.
- Editor code: `api.settings.get()` and `api.settings.onChange(listener)`; `EditorExtensionsRuntime` pushes the project's values with `setSettingValues`, which updates running extensions without restarting them. Game code: `import { settings } from "haptic:extension"` (`EXTENSION_HOST_MODULE`); the linker keeps that specifier as a host import and `loadExtensionGameLibraries` supplies each library's frozen `settings`, resolved at link time from the overrides and values Play or export passes to `gameLibraries`. Editor code that requires it fails with a pointer to `api.settings`. Values ship in games, so they are never secrets; no Secret field type exists.
- `contributes.nodes[{ id, title, category?, description?, call, pure, latent, hosts[], inputs[], outputs[] }]` (gameplay packages only; an Editor Only package with nodes gets a refresh diagnostic). Pins are `{ id, name, type, default? }` with ids that are JS identifiers unique per node (never `execIn`/`execOut`), types `bool | int | float | string | vec2 | vec3 | vec4 | rotator | quat | transform | color`, defaults only on primitive inputs. Pure nodes need an output and cannot be latent.
- Node catalog ids are `extension.<extensionGuid>.<nodeId>` (`extensionNodeTypeId`), stable across Library Name and display name edits. Codegen calls the hoisted `__extensionCall(libraryName, call)` (throws a named error when the library or export is missing at run time) with inputs as positional arguments; one output takes the return value, several destructure the returned object by output id; latent awaits. `category` defaults to the display name; `hosts` sets `NodeDefinition.hosts`, which Add Node checks against the Class lineage (`classLineageIncludesAny`); editor graph hosts and Animation Graphs never list extension nodes.
- The service's `syncNodes` hook (`ProjectService` → `syncExtensionNodes(defaultNodeRegistry(), …)`) replaces the extension definitions in the editor's single registry whenever the enabled gameplay set or its node declarations change, and empties them on close. A graph keeping a node whose definition is gone validates with `node.missing_extension` (error) instead of compiling to a silent no-op. `extensionNodesFingerprint()` (hashed when non-empty) joins `graphCompileSignature`, the Play compile cache key and `scriptPaletteInjectorKey`.
- Commands: `registerCommand` normalizes `fields`; `run(extensionId, commandId, values, context)` passes exactly the declared fields' resolved values (a blank `required` string blocks the run) and a frozen structured clone of the menu context (`{}` outside menus) as `execute(values, context)`, and resolves to the string `execute` returns, which the command dialog shows. The dialog renders fields with `ExtensionFieldList`, so no command needs special-casing.
- `contributes.menus[{ menu, command, title? }]` places commands in editor menus. Menu ids are the fixed list `EXTENSION_MENU_IDS` (`settings`, `debug`, `contentBrowser.asset|folder|empty`, `outliner.actor|folder`, `viewport`, `graph.node`); an unknown id or a command listed twice in one menu is a manifest error. `extensionMenuEntries` ([`extension-menus.ts`](../../../apps/editor/src/lib/extension-menus.ts)) lists, per menu in extension order, only entries of valid packages whose command is registered, so a stopped extension's entries vanish without manifest checks. Each surface calls `useExtensionMenuItems(menu, context)` ([`use-extension-menu-items.tsx`](../../../apps/editor/src/components/use-extension-menu-items.tsx)), which appends a separator and `NestedMenuItem`s (extension icon, `extension-menu-<menu>-<commandId>` test ids) and reads `context()` only when an entry is chosen, so menus capture their target in refs at open time. `ExtensionCommandHost` (in `editor-route.tsx`) runs them: a command with fields opens `ExtensionCommandDialog` with the context; one without runs at once and shows its text or error in an alert. Context shapes are user-documented in [extensions.md](../../../docs/projects/extensions.md#menus); keep them plain JSON (paths, ids, names), never live objects. Content Browser asset and folder entries require a selection of only that kind.

### Gameplay extensions

- `gameLibraries(overrides)` links the game entry of each enabled, valid, non-Editor-Only package in dependency order from current files; Play preparation (project overrides) and `exportProjectGameArtifact` (export document overrides) call it, and a link error or a Library Name claimed twice (also a refresh diagnostic) fails Play or export by name.
- Libraries travel as data: Play `load.extensionLibraries` (worker and in-process), `game.json` `extensionLibraries` for exports and Preview Build. `ScriptHost` evaluates them once, before its first module (`loadExtensionGameLibraries`); each library sees earlier ones as `extensions`, the result is frozen, and a library that throws is reported through `reportError` and left out. Compiled modules receive `extensions` as their Function-shim parameter; Execute JavaScript reserves the name.
- Content: the service calls `syncContentRoots` with the enabled gameplay packages whenever that set changes, and with a package excluded before its folder is replaced (import) or deleted. `ProjectService` mounts them with `mountExtensionContentRoots` (also on every registry remount) as `extension:<guid>` roots over `<folder>/assets` (engine packages read-only on engine storage). Export reads the live registry's non-plugin roots, so mounted extension content packs like project content. The Content Browser lists a mounted root only when `appearInContentBrowser` is on, whatever Show Plugin Content says.

### GLSL to Material

The bundled Experimental extension ([`engine-extensions/glsl-to-material/`](../../../engine-extensions/glsl-to-material/)), disabled by default, calls `materials.convertGlsl` and saves `assets/<name>.material.hasset` only on success; an existing filename or failed conversion leaves the destination unchanged. The result is ordinary Material nodes with no extension or Custom GLSL dependency ([shader-graph.md](shader-graph.md)).

## Editor utility types

| Type | Kind | Notes |
| --- | --- | --- |
| EditorUtilityObject | Class parent (`Object`), `*.class.hasset` | Events: Editor On Begin Play, On Editor Startup, On Scene Open, On Scene Saved, On Editor Shutdown. Never game Begin Play / Tick |
| EditorFunctionLibrary | Class parent (`FunctionLibrary`), `*.class.hasset` | Static Call Function rows only on editor graph hosts |
| SkyboxCreator | `*.skyboxcreator.hasset` helper | Slices a Texture into six skybox faces; the generated Textures are runtime assets and ship when a `SkyboxComponent` references them |

- `isEditorOnlyAssetType` / `isEditorOnlyAsset` / `isEditorUtilityObjectClass` / `isEditorFunctionLibraryClass` / `isEditorGraphClass` / `isEditorGraphHost` walk the parent chain; Play compile (`collectPlayScriptDocuments`) and export reuse them. Editor-only types: PluginSettings, SkyboxCreator, EditorUtilityInterface. Export Project keeps editor tools.
- `NodeDefinition.editorOnly` marks catalog nodes (editor lifecycle events), not a user flag. Hydrate stamps `data.__editorOnly`; GraphEditor draws the Editor Only hazard-tape footer.
- Registration: `ProjectSettings.editorUtilityObjects` (unique class ids, General page `ClassPicker`) merged with enabled plugins' `PluginSettings.editorUtilityObjects` (`mergePluginEditorUtilityObjects`).

## Editor ScriptHost

- Not the Play worker. On project open it compiles the registered utility graphs and fires `onEditorStartup`, then `onSceneOpen` if a scene tab is restored. Later scene opens fire `onSceneOpen`, saves fire `onSceneSaved`, and project close fires `onEditorShutdown` exactly once.
- Changing the utility list or toggling a plugin that registers utilities disposes the host (`onEditorShutdown`) and boots the new list. Unrelated `project.json` edits and Content Browser refreshes do not reboot it.
