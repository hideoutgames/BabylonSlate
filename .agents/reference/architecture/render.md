# Render

Contributor reference for Haptic's main-thread Babylon renderer: Engine ownership, the frame path, resources, lighting, Play presentation, feature owners and the Babylon 9.29 workarounds that must survive upgrades.

## Ownership and boundaries

| Area | Owner |
| --- | --- |
| Every Babylon object (Engine, Scenes, materials, textures, FrameGraphs, particles, audio voices) | [`packages/render/src/`](../../../packages/render/src/) (`@haptic/render`) |
| Engine/session construction | [`create-engine.ts`](../../../packages/render/src/create-engine.ts) (`createEngine`, `createAppEngine`; handle and option types in `create-engine-types.ts`, editor viewport camera, gizmos, handles and gestures in `editor-viewport-tools.ts`, Play pointer, touch, wheel and key input in `play-game-input.ts`, per-slot outlines, deformers, fog volumes, reflection probes and area lights in `play-visual-bindings.ts`, e2e mesh readouts in `play-handle-inspection.ts`), [`apps/editor/src/lib/project-engine.ts`](../../../apps/editor/src/lib/project-engine.ts) (`createProjectEngineSession`), [`backend-engine-session.ts`](../../../packages/render/src/backend-engine-session.ts), [`webgpu-engine.ts`](../../../packages/render/src/webgpu-engine.ts) |
| Editor project Engine wiring: controller sync, Retry, shared Engine registration | `useProjectRendering` ([`apps/editor/src/context/use-project-rendering.ts`](../../../apps/editor/src/context/use-project-rendering.ts)), called by `PlayProvider`, over [`project-engine.ts`](../../../apps/editor/src/lib/project-engine.ts) and [`project-rendering-recovery.ts`](../../../apps/editor/src/lib/project-rendering-recovery.ts) |
| GPU backend, color pipeline, scalability, shadow presets (Babylon-free) | [`packages/core/src/`](../../../packages/core/src/) (`rendering-pipeline.ts`, `render-effects.ts`, `scalability.ts`, `shadows.ts`, `render-setting-ownership.ts`) |
| Water/cable/wave math shared with the worker | [`packages/core/src/`](../../../packages/core/src/) (`water.ts`, `water-blend.ts`, `cable-simulation.ts`), [`packages/runtime/src/water-world.ts`](../../../packages/runtime/src/water-world.ts) |

- The game worker ([`packages/runtime/`](../../../packages/runtime/)) never imports Babylon. It sends render commands (`assignMesh`, `assignMaterial`, `assignParticle`, `debugDraw`, …) and snapshot buffers through [`packages/bridge/`](../../../packages/bridge/); render applies them.
- UI packages (`ui`, `editor-kit`, `graph-ui`) never import Babylon (ESLint `boundary/ui-packages`); they talk through the engine command bus.
- Babylon-free IR packages (`shader-graph`, `particle-graph`, `assets`) own schemas; render lowers or applies them. Never store Babylon serialization as an asset payload.
- Construct `Texture` only in [`resource-cache.ts`](../../../packages/render/src/resource-cache.ts) (ESLint `boundary/render-texture-cache`).
- The game HUD / UserInterface system is removed; Print HUD is DOM (`print-hud` in core). SceneLayers are the only in-game UI path ([scene-layers.md](scene-layers.md)).

## One Engine per project

- One project Engine on a hidden constructor canvas. **Never create a second WebGL/WebGPU context** (context caps). Scene viewport and Play bind visible canvases with `registerView(canvas, undefined, true)` and present as below; Material/Model/Animation/Skeleton/Particle/Prefab previews and thumbnails render to an RTT and blit (`createRttCanvasBlitter`, `flipReadPixelsRgba` in [`flip-read-pixels.ts`](../../../packages/render/src/flip-read-pixels.ts)). Editor code obtains it with `ensureSharedEngine`.
- Only exception: Preview Build's iframe (its own cold Engine). Do not add preview Engines.
- Previews must not `registerView` or `scene.render()` to the default framebuffer; Scene/Play own it. Do not move the Scene viewport to an RTT: Play blits from the Scene Engine framebuffer.
- View presentation ([`direct-view-presentation.ts`](../../../packages/render/src/direct-view-presentation.ts), driven by [`registered-view-admission.ts`](../../../packages/render/src/registered-view-admission.ts)): while exactly one enabled registered view has a layout box (`viewCanvasHasLayoutBox`; a hidden dock tab's view stays enabled but is neither admitted nor counted), the Engine canvas itself is placed over that view's canvas (same box at device-pixel offsets, `pointer-events: none`, `aria-hidden`) and shown, with no per-frame copy (on WebKit a copy is a CPU blit with a CPU/GPU sync). Input, picking (`mapCanvasPointer`, GPU pick, CPU ray) and gizmos keep using the view canvas, whose bitmap keeps the presented size. Two or more such views, a view canvas in another document (a popout window), WebGL1, a multisampled default framebuffer or WebGPU main pass, or `setDirectViewPresentationEnabled(false)` copy the Engine canvas into each view's 2D canvas instead. Only the editor's project Engine presents directly, on either backend: its session is created with `presentViewsDirectly` (`createProjectEngineSession`; checked per frame through `Presentation.allowDirect`). The exported player and Preview Build run their own Engine session, which copies, because the player and its pixel checks read the view canvas.
- Z-order: the placed Engine canvas is the view canvas's next sibling, positioned absolutely with no `z-index`. An absolutely positioned overlay that comes before the view canvas in the DOM and has no `z-index` now paints under the Engine canvas; give viewport overlays a `z-index` or place them after the view canvas.
- Direct held frames (WebGL2): each coherent frame blits the default framebuffer into the view's held renderbuffer; an incoherent frame, a view step that resized the buffer, or an `engine.setSize` outside a view step, blits it back before the browser presents. A step whose loop declined to draw (`Presentation.dirty`, render on demand) blits nothing: the default framebuffer is preserved. A view that stops being covered (another sole view, the copy fallback, release) gets its held image in its own canvas once, so it keeps its last frame. Releasing a view untracks its canvas, and parking a disposed Engine's canvas removes it instead of returning it to the document. While a view is covered, nothing may draw to the default framebuffer outside that view's step. Test builds write the presented image into a covered view canvas before `drawImage`, `getImageData`, `toDataURL`, `toBlob` or `createImageBitmap` read it (`installDirectViewReadSync`).
- WebGPU direct frames ([`webgpu-held-image-store.ts`](../../../packages/render/src/webgpu-held-image-store.ts)): the store touches Babylon only from the first direct step (`engage`), so a copying Engine session keeps stock members. While a view is presented directly, Babylon's main pass renders into one of two owned textures (swap-chain format, canvas size) instead of the canvas texture: `_startMainRenderPass` runs with a `_context` whose `getCurrentTexture()` returns the texture that does not hold the last coherent frame, and `_configureContext` adds `COPY_DST`. A coherent frame flushes, acquires the canvas texture and copies into it; any other frame never acquires the canvas, which keeps showing its last image (no held-image copy back). Main passes outside a direct step (the attachment pass `setSize` runs) also land in the draw target, never on screen; a coherent step must draw the whole backbuffer, as on WebGL2. After a resize or reconfiguration clears the canvas, the held texture is copied back once, unscaled into the top-left corner, until the next coherent frame: a shrink shows a crop of the held frame that fills the view; a grow shows it at its old size with transparent bands to the right and below, where the view canvas shows through. A view that stops being covered gets that overlap region 1:1 (`restoresUnscaled`), which its canvas box stretches. A coherent frame the store cannot present (it turned off while the frame drew, so the frame is in the canvas) is copied like a non-direct step instead of re-showing the held image. Replaced textures are destroyed at the end of their frame (Babylon submits before end-frame observers); disposing the store submits pending work and destroys its textures at once, since no later frame may come; context loss drops them without destroying and re-arms the first-copy check. Fallback: the store creates nothing (copy path) when an internal is missing or MSAA is on (`webGpuPresentationInternals`), and turns itself off, restores `_startMainRenderPass` / `_configureContext` and leaves presentation to copies when the redirected main pass throws (that frame re-renders into the canvas) or binds anything but the owned texture, when Babylon's configure needs more than `context.configure`, or when a validation scope reports that the `COPY_DST` configuration or the first copy failed. That last case also reconfigures the canvas Babylon's way, which clears it: at the store's next `clear` (the presenter has parked the Engine canvas by then), or at once when nothing is presented. A lost device never turns it off. `webgpu-held-image-store.test.ts` pins the Babylon source shapes involved.
- Held images are a fixed presentation cost outside the managed ledger, like the Engine's own framebuffer: one RGBA8 renderbuffer per held view on WebGL2, two canvas-size swap-chain-format textures on WebGPU (4 bytes per pixel each, about 22 MB apiece at 2732×2048). They exist while a view is presented directly and go when presentation copies or the view is released.
- View canvases take their 2D context with `VIEW_CANVAS_2D_ATTRIBUTES` (`willReadFrequently: false`, [`registered-view-admission.ts`](../../../packages/render/src/registered-view-admission.ts)), and any 2D canvas the page reads back (`getImageData`, e.g. glyph rasterization in [`text2d-bitmap.ts`](../../../packages/render/src/text2d-bitmap.ts)) declares `willReadFrequently: true`. After readbacks on default 2D canvases, Chromium creates later default contexts unaccelerated, and each view copy then becomes a synchronous GPU readback.
- Closing a Scene tab disposes its Scene and cache retains, never the Engine. Closing the project disposes the Engine.
- Shared views size the framebuffer with `engine.setSize` from the view's CSS box, never `engine.resize()` (it follows the hidden constructor canvas). Resize only on integer CSS size change; ignore zero sizes. A view whose canvas has no layout box (a hidden dock tab) is not admitted: it neither sizes the Engine (that would collapse it to 1×1) nor draws, because a 1×1 frame turns the water scene copy off, re-plans the graph and compiles the variants it then draws.
- Backend is project-wide (`settings.render.gpuBackend`: `auto | webgl2 | webgpu`, normalized default `webgl2`). A Scene never changes backend in place; `createBackendEngineSession` falls back WebGPU→WebGL2 on a fresh canvas. Custom GLSL in the emitted material closure forces WebGL2 (`webGpuMaterialCompatibilityReason`). Backend changes wait for Play/Preview Build to stop; uncertain cleanup blocks any new allocation (never publish a partially released context).
- A lost WebGPU device is never restored in place: Babylon 9.29 rebuilds every resource before its new device exists. [`webgpu-engine.ts`](../../../packages/render/src/webgpu-engine.ts) sets `doNotHandleContextLost` (textures keep no source bytes for a restore), marks the Engine lost, notifies `onContextLostObservable` (Babylon does neither under that flag; the direct presenter relies on it to vacate the Engine canvas and drop its held textures) and settles `BackendEngineSession.deviceLost`. Retry's new Engine gets its own presenter and store. The editor's project Engine controller ([`project-engine.ts`](../../../apps/editor/src/lib/project-engine.ts)) then publishes `deviceLost`, detaches every client and offers Retry. [`project-rendering-recovery.ts`](../../../apps/editor/src/lib/project-rendering-recovery.ts) stops Play or Simulate at once, discarding Simulate's Keep Changes (its capture needs the lost Engine). Preview Build has its own Engine: Retry asks the user to stop it instead. Retry waits, bounded, for the stopped game's release, reports a quarantined or still-releasing game instead of allocating, then creates a new Engine. Release must never depend on a frame of a lost Engine: frame-gated lease releases also settle on context loss. `isUsableEngine` rejects a WebGPU Engine with `_contextWasLost`. WebGL2 keeps Babylon's in-place restore: a lost WebGL2 Engine stays usable, and its views reload on `onContextRestoredObservable`.
- The exported player and Preview Build get the same `doNotHandleContextLost` Engine but no Retry: a lost device stops their drawing for good, and [`player-backend.ts`](../../../apps/player/src/player-backend.ts) reports `render.device.lost` (logged; Preview Build forwards it to the editor).
- A WebGPU request that fails to initialize falls back to WebGL2 with the request unchanged; the controller publishes `webGpuFallbackReason` (not for a material compatibility switch) and the editor shows it once per Engine.
- WebGPU devices request two limits and keep every other at its default (`adapterRequiredLimits` in [`webgpu-engine.ts`](../../../packages/render/src/webgpu-engine.ts), the construction path of every product Engine: the editor's project Engine, Retry after a lost device, the exported player and Preview Build). Neither request exceeds the adapter's value, so the device request cannot be refused for it.
  - `maxInterStageShaderVariables` at the adapter's maximum. Babylon's WGSL fragment inputs always declare `@builtin(front_facing)` and Dawn counts it, so the default 16 leaves 15 user varyings; each cascade and spot shadow adds PBR varyings.
  - `maxUniformBuffersPerShaderStage` at `min(adapter, REQUESTED_UNIFORM_BUFFERS_PER_SHADER_STAGE)` (20), only when the adapter offers more than the default 12. Every light is in one block (`HapticLights`), so the limit does not bound the light count; it leaves room for Babylon's per-draw and per-Material blocks. D3D12 adapters report 12; Metal reports more (44 on Apple GPUs). Babylon's note that the limit "cannot be raised through requiredLimits" holds for D3D12 only.
  - `maxSampledTexturesPerShaderStage` and `maxSamplersPerShaderStage` stay at their defaults (16). Lights cost no sampler and every shadow is a tile of the one atlas. Raising only the texture limit would also let pipelines exceed the sampler limit unchecked (one sampler per texture, never read by Babylon's caps).
  - Do not use `setMaximumLimits`: it raises every limit without a cap.
- NodeMaterials and built-in helpers (grid, camera bounds, MSDF text) compile in the Engine's native language (GLSL or WGSL). Never depend on a downloaded GLSL→WGSL translator.
- The editor grid is one shader plane under the 3D eye (2D: the camera target), snapped to the major spacing. Each level (minor, major, ×10 steps) fades in per fragment from its on-screen cell size, so zoom, distance and grazing angles blend without a global fade; the plane's distance fade scales with eye height and stays inside the far clip ([`editor-grid.ts`](../../../packages/render/src/editor-grid.ts)). Every fragment pays for every level, and software GL (SwiftShader, as in CI) pays for each instruction while early-outs and loops cost it more than they skip, so keep per-level work minimal and straight-line: one `log` per fragment, levels composite three premultiplied sums (alpha, emphasis-weighted alpha, alpha along v) and colour resolves once, and level line widths stay at or under one pixel.
- Large-world rendering on, context MSAA off; `adaptToDeviceRatio: false`, resolution via `setHardwareScalingLevel` ([`hardware-scaling.ts`](../../../packages/render/src/hardware-scaling.ts)). Engine Settings scaling is both initial level and floor; only the Engine's sole rendering view feeds the dynamic-resolution valve.

## Frame path

- [`framegraph-forward-scene.ts`](../../../packages/render/src/framegraph-forward-scene.ts) (`ForwardSceneFrameGraph`) is the **only** scene draw path; there is no native `Scene.render` fallback. Every Play world, SceneLayer, editor viewport, preview and thumbnail owns a `SceneRenderCoordinator` ([`scene-render-coordinator.ts`](../../../packages/render/src/scene-render-coordinator.ts)). Native shader warm precedes graph preparation; preparation builds and probes, never draws.
- Task order (`taskNames()`): `Forward admitted shadows` → `Forward clear` → `Forward cull` → geometry tasks when a chain needs them → `Forward objects` → authored post-process, settings effects, shared outlines → `Scene post-process output` (only when a chain exists; then it is the view's only output writer; an auxiliary view without a chain writes its own scene targets in `Capture output`). Water scene copy splits the object pass ([Water](#water)).
- Unsupported, so preparation rejects and nothing draws: frozen active-mesh queues, camera post-processes, rig/multiple cameras, multisample/cube/array or caller-bound targets, custom render functions, unmanaged shadow generators. Editor scenes therefore freeze world matrices and materials but never the active-mesh queue.
- Strict readiness is probed only after invalidation, never per steady frame, except while a variant swap is pending (below). Anything that changes shader-relevant state outside Scene observables must call `markSceneReadinessDirty` ([`scene-readiness-signal.ts`](../../../packages/render/src/scene-readiness-signal.ts)). Readiness probes restore camera, matrices, UBO, viewport and render pass even when callbacks throw.
- Probes never replace a drawn Effect ([`isMeshFrameReady`](../../../packages/render/src/scene-perf.ts)): Babylon's hot swap (`allowShaderHotSwapping`, on by default) keeps a submesh drawing its previous, ready Effect while a newly requested variant compiles, and leaves its defines unprocessed, which is how a probe tells a swap. Replacing it would leave Babylon's frozen and same-frame readiness caches answering for an Effect still compiling. Inside `probeVariantSwaps(true, …)` ([`variant-swaps.ts`](../../../packages/render/src/variant-swaps.ts)) a swapping mesh is ready, drawing its previous Effect (the light block binds lights as data, so that Effect never binds a disposed light); everywhere else it waits for its new variant. A swap whose new variant failed to link, every fallback included (none of the Effects the mesh requested is still compiling and one has `getCompilationError()` with `allFallbacksProcessed()`), is over: Babylon draws the previous Effect for good, so the mesh is ready in every probe and the failure is logged once per Effect.
- Probes compile ahead on a parallel-compile driver (`KHR_parallel_shader_compile`; WebGPU has none; SwiftShader has none either, so each request on it links inside the probe that makes it). iPad WebKit WebGL2 exposes it and its new effects stay pending while they link, so the limit below throttles there as on D3D11; its heavy programs finish roughly one after another, and the first draw of each new program still blocks the thread (about 100 ms each in raw WebGL), which no readiness probe sees. Babylon's scans stop at the first unready mesh (ObjectRenderer) and task (`FrameGraph.isReady`), so a pass's variants would link one after another, and each pass only once every earlier pass is ready. While fewer than `COMPILE_AHEAD_LIMIT` effects are pending on the Engine ([`driver-compile.ts`](../../../packages/render/src/driver-compile.ts)), the forward graph also probes the tasks after its first unready one, and the object, transparent and geometry passes and the GPU pick pass the meshes after theirs (`requestCompilesAhead`), including the depth pre-pass that an unready colour variant holds back. The limit counts every compile pending on the Engine (camera-pass probes and previews included) and the probe that crosses it may start several. Each mesh is probed ahead once until its pass is ready, the forward graph's readiness is invalidated (`markReadinessDirty`) or the pick pass drops its objects; the results are discarded, so the in-order scans alone decide readiness.
- Mask, geometry and pick passes are light-neutral ([`light-neutral-tasks.ts`](../../../packages/render/src/light-neutral-tasks.ts)): never toggle `light.shadowEnabled` around a pass; each toggle dirties every material's light defines.
- Blended materials with `needDepthPrePass` draw their depth pre-pass under their own render pass id ([`transparent-depth-pre-pass.ts`](../../../packages/render/src/transparent-depth-pre-pass.ts)); sharing one draw wrapper made frozen materials draw the depth variant as colour.
- Presentation: the visible canvas changes only after a coherent draw; rebuilds, resizes and skipped frames hold the last image. First frame waits for GPU submission (WebGL2 polls an owned fence non-blockingly; never read GL errors before it signals) and the canvas copy.
- WebGPU pipeline deferral ([`webgpu-pipeline-deferral.ts`](../../../packages/render/src/webgpu-pipeline-deferral.ts)): a synchronous `createRenderPipeline` blocks the renderer while the GPU process compiles it (about 200 ms per pipeline on D3D12, serialized), and an Effect is ready on WebGPU as soon as it exists, so readiness probes never see it coming. The world view's coordinator (`deferPipelines`: editor, Play, exported player) opens a scope around its graph render that admits its graph's object passes, their blended depth pre-passes and the shared outline masks (`ownsObjectPass`; post-process draws under the camera's pass are not admitted). Its Full Quality captures and Fast captures open nested scopes only inside that one (`nested`), so under any other owner (previews, thumbnails, SceneLayers) they create pipelines synchronously. In a scope, a pipeline-cache miss starts `createRenderPipelineAsync` (counted in Babylon's miss statistics for that frame) and skips that draw; the coordinator reports the frame not rendered (the view holds its last image, `holdingForPipelines`) and draws nothing more until those pipelines exist, as for a scene that is not ready. A capture that skipped neither publishes nor consumes a manual request; nested skips count in the enclosing view, so it never presents a partial capture. Shadow maps (render once; a map's first draw in a steady frame waits for its casters' pipelines instead, and a drawn map leaves out a new caster's missing pipelines in an `isolated` scope, below), previews, thumbnails, pick passes and SceneLayers keep synchronous creation. After `PIPELINE_DEFERRAL_HOLD_CAP_MS` (2 s) of held frames a view starts no new deferrals (new misses compile synchronously, so a view whose pipelines keep changing still presents), and when no deferred pipeline has finished for `PIPELINE_DEFERRAL_STALL_MS` (10 s) the pending ones compile synchronously at their next draw. A steady frame (`render(false)` of a view that tolerates variant swaps) leaves a miss in a recorded geometry pass out of that pass instead (`omitsGeometryPass`; the scope's `omits`): its pipeline starts creating asynchronously whatever the cap (past the cap, only in a pass that has already drawn in the scope: a miss in one that has not compiles synchronously, as it could hold the view), the scope neither counts nor waits for it, and the frame presents (no `holdingForPipelines`, so no `onPipelineHold`) with that mesh missing from the geometry buffers (a few frames of SSAO, SSR, TAA velocity, volumetric or authored-chain depth and normal artefacts on it) until the pipeline exists. A geometry pass (the spatial effects' and the authored chain's geometry tasks) is recorded once it drew something (`drawsInPass`, counted on draws that drew) in a complete frame of the prepared graph (`noteCompleteFrame`), and forgotten while its spatial stages leave it idle, when the view is invalidated and when the graph is released, so a new graph (an effect or quality change, a resize with spatial effects or an authored chain), a first view of anything and a Fog-Volume-only pass coming back from idle hold as before: their first draws can miss every mesh's pipeline at once. A pass whose every draw in a frame was left out counts them as skips at `close()` too, so its buffers are never presented empty. Validated presentations (loading, a frame report) and auxiliary views omit nothing (a capture publishes what it draws; its skips count in the scene view). A left-out draw's creation also has its own stall clock (`startedAt`): after `PIPELINE_DEFERRAL_STALL_MS` it compiles synchronously at its next draw even while other creations keep the Engine-wide stall from coming, and `waiting()` stops waiting for it once counted at `close()` (`leftOut`), so a pipeline that never arrives cannot leave the mesh out, or hold the view, for good. Each left-out draw's creation still starts and finishes on the shared stall clock (`progressAt`), so a run of spawns or Material changes delays the Engine-wide stall's synchronous fallback for every other wait that reads it: a held view's pending pipelines, and a first shadow map draw waiting for its casters' pipelines until `deferredPipelinesStalled`. An invalidation of the view (a scene switch included) ends its hold and restarts the cap, so the next frame waits for none of the old frame's pipelines. After the first frame a steady frame meets few misses (WebGPU variant swaps below create their pipelines ahead), so the cap and its synchronous fallback bite mainly on loading and first-ready frames. A warm scope (`warm: true`) is for draws made only to create pipelines: every draw in a pass it admits is skipped, a hit as well as a miss; a miss starts `createRenderPipelineAsync` whatever the enclosing scopes' cap or a stall (never synchronously), its skips never count in an enclosing scope, and `warmed()` reports whether every draw found its pipeline. A lookup scope (`lookup`, a warm scope) is for draws made outside their pass, ahead of it: it replays a target captured in that pass (`capturePipelineTarget`: formats, sample count and Y flip through `_currentRenderTarget`, and the depth state its draws inherit) with the stencil test off, a draw starts no GPU pass meanwhile (`_getCurrentRenderPass` returns the open pass, if any), a miss starts no creation, and a node whose creation failed, or a cache that keeps nothing, is a miss (its draw would create the pipeline synchronously); `close()` restores the engine's state. The deferral also records each Effect a draw drew with (`effectDrawn`). A failed asynchronous creation compiles synchronously and reports its error the usual way. Each finished deferred creation is compile progress for every `DriverCompileWatch` on the Engine (`deferredPipelinesSettled`), so loading budgets renew while a held first frame's pipelines arrive; WebKit builds them one at a time (about a second each), async or not. The first-frame completion allowance counts only the pipelines the presented draw still created synchronously. In Play a hold that has lasted `PIPELINE_HOLD_PAUSE_DELAY_MS` (250 ms, counted over rendered frames; a shorter hold pauses nothing and the release is immediate) pauses the game's time like a blocking load: the Engine pauses its own game time, audio and particles while it keeps drawing (`onPipelineHold`), and the host adds the runtime pause reason `rendering` (editor Play and Preview Build through the session boundary; the exported player through its combined `setPaused`). Ticks, physics, scripts, timers and tweens stop; resuming resets the tick accumulator and discards the held interval, so nothing catches up. `rendering` is a time-only pause: hosts do not suppress or neutralize input for it, nothing exits pointer lock, and the runtime keeps queueing input (a held key stays held, a release during the hold lands); any other reason still resets and refuses input, also on top of a hold. The exported player's combined `setPaused` carries `reason: "rendering"` for it. A `rendering`-only pause never pauses the render scheduler or the view's game time from the host side: the frame that finds the pipelines ready must draw to end the hold.
- Variant swaps ([`scene-render-coordinator.ts`](../../../packages/render/src/scene-render-coordinator.ts)): after the first frame, a change to an existing Material's variant never holds the picture or pauses the game. A world view's steady frames (`deferPipelines`, not auxiliary, `render(false)`, on a world Scene: `sceneBindsPreviousEffects`, which `createEngine` sets with `setSceneBindsPreviousEffects` for every Scene neither presented through an RTT nor given preview studio lights) probe inside `probeVariantSwaps(true, …)`. A Material whose variant changes therefore draws its previous variant a few frames longer instead of holding the last image. Play, the exported player, Preview Build and the editor's world view share this path.
  - Tolerance accepts every hot swap, not only light changes: any define change on an existing Material (`NONUNIFORMSCALING` from a scale animation, a texture arriving) draws the old variant until the new one is ready, which is Babylon's own default (`allowShaderHotSwapping`), reading the current light block.
  - While a swap is pending each steady frame probes again (`recheckVariantSwaps`), so a Material adopts its new variant on the first frame that variant is ready, frozen ones included (the editor freezes library Materials, and a frozen NodeMaterial that swapped answers ready without asking again). A swap whose variant failed to link stops this re-probe.
  - A preparation nothing awaits (`requestPreparation`, whether a steady frame or a strict readiness question asked for it, such as Play's end-of-frame check finding a new output size first) probes as the view's steady frames do, since they are what draws once it is done; a strict question asks again afterwards. Until the view has drawn a tolerant steady frame (`warmsVariants`: loading, the starting-state draw, the first presentation) what draws next is a strict frame, so such a preparation probes strictly: a tolerant one would find the swaps and answer the strict frames that follow "not ready" without probing again. A caller joins a preparation already running for the generation whatever its tolerance: a strict owner (loading, a quality step) that joins a tolerant one still sees a swap in its own `isReady()` and presentation checks, and steady frames that join an owner's strict preparation wait for it, as they wait for the new resources it prepares.
  - Everything else waits for every requested variant: loading presentations (`render(true)`), `isReady()` (loading owners and Play's end-of-frame scalability confirmation, which therefore confirms only once the new variants draw), previews and thumbnails. A validated frame of a view that draws steady frames (a frame report's) first probes as a steady frame does: such frames repeat until one draws, and only a tolerant round admits a swap's new variant, so otherwise a report requested during a swap held the view for good (on WebGPU a variant no warm draw used meanwhile is admitted after `UNUSED_WARM_MS`). A probe that tolerates no swap re-probes rather than trust a pass that tolerated one, except right after a tolerant probe (this frame or the last, no input changed) found a swap: then the answer is "not ready" without walking the scene again. The probe records its own tolerance (`collectingEffects`), since a preparation marks its probe after the tolerance scope closed.
  - A tolerated probe clears a submesh's `_areLightsDisposed` before asking it: Babylon otherwise refuses to draw a previous Effect after one of its lights was disposed, and the layout binding never binds a disposed light.
  - A new shadow map (a light starting to cast, a map moved to another light or resumed from standby) holds nothing either. A changed shadow set needs no graph preparation: `ManagedShadowsTask` borrows the controller's maps by reference, so a frame marks readiness dirty (`restaleChangedShadows`) and its probe binds the set as it is. A map awaiting its first draw (`awaitsFirstDraw`, [`shadow-first-draw.ts`](../../../packages/render/src/shadow-first-draw.ts)) samples neutrally (darkness 1, lit) and draws only once every caster's depth variant is ready, checked before its refresh is consumed, since a render-once map drawn without some casters would keep the gap. Meanwhile a tolerant probe requests those depth variants without letting them fail: the task's own map check, the scene probe's render targets, and `Mesh.isReady`'s caster check (`deferCasterChecks` answers ready for every map's generator while it asks one mesh) each count it as a swap, so steady frames re-probe until it draws. A map that has drawn keeps drawing without a caster still compiling (a spawned or newly revealed one): Babylon skips that caster and resets the map's refresh, so the map redraws until it is ready. - Compile hold (any backend): strict readiness presents only when ready, so a wait the cases above do not cover (a WebGPU pipeline, a strict presentation) leaves the canvas on its last image while the driver links the new effects. A `deferPipelines` view (never an auxiliary one) reports that wait through `holdingForPipelines`, the same signal as a WebGPU deferral, so `onPipelineHold`, the Engine pause and the host's `rendering` reason apply unchanged (no parallel path, no catch-up on resume).
  - It starts at a frame not drawn because the scene probe failed, or the graph is still preparing or probing its passes' variants, while one of the view's own effects is pending on the driver: the Effects its readiness probes requested through `createEffect` (`requestedEffects` of the forward graph, filled by [`effect-requests.ts`](../../../packages/render/src/effect-requests.ts) inside `isReady`, `isOutlineReady` and the scene probe), so a preview's, thumbnail's or Custom GLSL probe's compile on the shared Engine never counts. Effects built outside those probes (a task's, while the graph is built) are not attributed. It then lasts until a frame draws, even after the effects finished, so the game does not resume under a frozen picture. A wait that compiles nothing from the start holds the image only: a graph rebuilt for a resize or a resolution step, a texture still decoding, and a link that completes inside the call (SwiftShader, which has no parallel compile) leave nothing pending. iPad WebKit WebGL2 keeps new effects pending while they link, so it holds; a draw's first use of a new program still blocks its thread, which no hold covers.
  - Read in `render()` each frame, never in `isReady()`. A drawn frame, a throw, no camera, an invalidation, disposal, a latched preparation failure or unsupported scene (`status.reason`), and a skipped draw that is not a readiness wait (the graph refusing a paused redraw) all end it. `createEngine`'s `dispose` releases a hold it still reports (`onPipelineHold(false)`). A loading first frame never raises it: `drawOwner` calls the world draw only once `isReady()`, and the load already pauses.
  - No cap on a link that is still pending, unlike `PIPELINE_DEFERRAL_HOLD_CAP_MS`: that cap makes a WebGPU view compile synchronously so it presents, whereas strict readiness has no synchronous way to present, and resuming the game under the picture of a compile that is still running is the outcome the pause exists to prevent. The report ends, with the image still held, when nothing is left to wait for: an effect of the run reports a compilation error (immediately), none of the view's effects was pending and no preparation ran for `COMPILE_HOLD_STALL_MS` (10 s, the analogue of `PIPELINE_DEFERRAL_STALL_MS`), or `SCENE_DRIVER_COMPILE_TIMEOUT_MS` (60 s) passed since it began (a hung link). That wait then starts no second hold until a frame draws; a failing or hung link would otherwise pause scripts for good while the picture never recovers. A preparation that times out latches a failure, which also ends it.
- Loading budgets ([`stall-deadline.ts`](../../../packages/render/src/stall-deadline.ts)): shader warm stall 4 s, first frame 20 s, driver compile 60 s, and `SCENE_PREPARATION_CEILING_MS` (300 s). They measure stalls, not duration: when one expires, `DriverCompileWatch` ([`driver-compile.ts`](../../../packages/render/src/driver-compile.ts)) renews it for compile progress since its last renewal, which is an Engine effect key that became ready (once per key: a released variant compiled again is none) or a parallel-compile driver's pending set that changed or has been pending for under 60 s. Finished keys are the only sign where links are synchronous (SwiftShader has no `KHR_parallel_shader_compile`, so Babylon's completion check in the Effect constructor already finds each program linked) and on WebGPU, whose effects are ready once created. iPad WebKit WebGL2 renews through the pending set like D3D11: its new effects stay pending until the link completes. Progress is per Engine: anything compiling on the shared Engine renews every wait on it, which is why the editor's thumbnail queue pauses while a blocking scene load (not a rendering update) is open ([asset-registry.md](asset-registry.md#thumbnails)). It is checked only at expiry, so a stuck wait fails between one and two bounds after its last progress; a preparation stuck in an invalidation loop whose first build compiled anything fails up to 60 s later than without progress (one renewal of the total bound). A watch shared by sequential waits (one per thumbnail capture or model instance) starts each wait from fresh progress (`restart`, through `renewOnCompileProgress`). No watch renews from its ceiling, 300 s after its wait began whatever was credited, so a wait that keeps compiling and never becomes ready still ends. The watch renews the shader-warm, material-texture (an RGBD decode, such as the BRDF texture's, waits for its post-process effect to compile), first-frame and model material waits; graph preparation: `SceneRenderCoordinator.prepare` (10 s per generation and 60 s across invalidation restarts, both renewed; the ceiling is checked at every expiry check) and the forward graph's readiness loop (10 s, with its own ceiling), each creating its watch after its first presentation-fence wait, because a watch asks every Engine effect for readiness; and, through `createHeldThreadBound`'s `renew`, the preview, thumbnail, `prewarmMaterial` and Custom GLSL waits below. Their timeout messages end with the watch's counts (variants compiled while waiting, still compiling and on the Engine, and whether the extension is exposed), which the Scene Load Report prints. A validated first draw's GPU completion has no progress signal: WebGPU builds every render pipeline that draw created in the GPU queue, inside its submitted-work wait, so the budget is 60 s plus `SCENE_PIPELINE_COMPLETION_ALLOWANCE_MS` (2 s) per pipeline it created (`WebGPUCacheRenderPipeline.NumCacheMiss` across the submission), at most the ceiling (`firstFrameCompletionMs`); its expiry names that count. WebGL2 counts none. The two first-frame waits add up: on WebGPU a load can spend up to the 300 s renewable wait for a validated draw and then up to another 300 s for that draw's completion, about 600 s in all.
- Held threads: a synchronous link also advances the wall clock, and so does a draw's first use of a new program on iPad WebKit WebGL2, where probes return before their links complete. The coordinator credits back to both its bounds any gap of at least `SCENE_THREAD_HELD_MS` between its checkpoints (`heldThreadMs`), and the graph loop credits the time inside each readiness probe; shorter gaps are polling and count, and shorter links renew through progress instead. Each credit has a `SCENE_THREAD_HELD_BUDGET_MS` budget, one per `prepare` call for the coordinator and one per readiness loop (`graph.prepare` call) for the graph. A gap is credited whatever caused it: in a hidden page, whose timers browsers align to a second or more, the coordinator's bound is credited, while the graph loop's, which counts the wall time outside its probes, still ends a never-ready preparation. Nothing above `prepare` is timer-bounded except a SceneLayer preparation's ceiling across renderer replacements (below). The readiness waits that probe the same way outside preparation credit through `createHeldThreadBound` (monotonic `performance.now()`) from a `HeldThreadBudget` (`createHeldThreadBudget`, `SCENE_THREAD_HELD_BUDGET_MS`): `waitUntilReady` ([`preview-readiness.ts`](../../../packages/render/src/preview-readiness.ts); the shader warm 4 s for a preview's meshes and its first presentable frame), the asset-thumbnail capture's loading and readback bound (30 s), `prewarmMaterial`'s compile poll (4 s) and Custom GLSL's probe-effect compile (15 s, with a separate 120 s for blocking textures, each with its own watch so one's renewal never spends the other's progress); all of them also renew on compile progress. On a parallel-compile driver (D3D11 through ANGLE) their own effect pending renews them too, until the same set has been pending `SCENE_DRIVER_COMPILE_TIMEOUT_MS`: a hung compile ends the 4 s waits after about 64 s and Custom GLSL's 15 s after about 75 s. A thumbnail capture's watch has the shorter `SCENE_CAPTURE_CEILING_MS` (90 s), which also ends the capture's own preview preparation (its `current` check), so unrelated compiles on the shared Engine cannot hold the serialized queue for 300 s. A capture ends `expired` (distinct from `failed` and `cancelled`, see [asset-registry.md](asset-registry.md#thumbnails)) when it reaches that ceiling (`reason: "ceiling"`) or one of its waits' bounds, or the coordinator's `PreparationTimedOut`, ends it (`reason: "bound"`) while it is still wanted; the editor's queue retries only a `ceiling` expiry, once, with `SCENE_CAPTURE_RETRY_CEILING_MS` (300 s), passed as the capture's `ceilingMs`. The per-wait bounds are the same on the retry. A one-shot capture (`captureAssetThumbnailPng`, `captureModelThumbnailPng`) shares one budget across all its sequential waits, so a capture that never becomes ready cannot hold the serialized thumbnail queue for a full budget at each step; every other wait has its own. `createStallDeadline` takes the same kind of budget (`prewarmMeshMaterials`, its own; `prepareInstanceMaterials`, one per model instance): a timer that fires a held gap late starts a fresh window and spends only the lateness, at least `SCENE_THREAD_HELD_MS`, so a stuck unit gets a fresh window per credited late fire (up to the budget over `SCENE_THREAD_HELD_MS`, plus one); its `renew` is asked at every fire, held or not, so progress a held window saw renews no later one. A `createHeldThreadBound` wait that never becomes ready fails after its bound plus its budget once nothing compiles, and the capture then ends `expired` and keeps the type icon. A capture's shared budget does not reach the `renderer.prepare` inside `renderPreviewFrame`, which keeps the coordinator's and the graph loop's own credit and renews on compile progress up to its ceiling: held credit across one capture can reach three budgets (about 180 s). Hidden pages: a gap is credited whatever caused it, so a stuck wait there ends after its bound plus the budget instead of at the bound.
- Opaque world visuals, models, the grid and debug draws share `RENDERING_GROUP.world` with no group depth clear (`configureEditorRenderingGroups`, [`sorting.ts`](../../../packages/render/src/sorting.ts)); helpers/billboards use `foreground`.
- SceneLayers are extra unlit orthographic Scenes on the same Engine, composited after the world output ([`scene-layer-compositor.ts`](../../../packages/render/src/scene-layer-compositor.ts)); world post-processing never touches them. Their camera preparation updates matrices only; never upload scene uniforms while another Scene's floating-origin context is current. `SceneLayerCompositor.prepare` follows the renderer a post-process rebuild, resize or re-create swaps in while it waits, and resolves for a removed layer (a layer load's scope rejects once the layer is removed), so a script's post-process change does not fail a runtime-settings transaction or a layer load. The caller's `assertCurrent` cancels it, and an error from a renderer that is still current (a timeout, a missing camera, a disposed Scene) rejects. Each replacement's coordinator starts fresh bounds, so `prepare` stops following with `PreparationTimedOut` once `SCENE_PREPARATION_CEILING_MS` has passed since its first pass began (wall time, not credited for held threads): replacement faster than the graph prepares (a script toggling post-processes, a long resize drag) still ends, at most one coordinator wait after the ceiling.
- Auxiliary views (`ForwardSceneFrameGraphOptions.auxiliary`, through `SceneRenderCoordinator`'s `auxiliary` option; only Full Quality Render Target Captures) are extra graphs on the same Scene for a non-active camera with an output target (colour only: it never needs depth). The scene view's graph draws them (`drawSceneAuxiliaryViews`, [`scene-auxiliary-views.ts`](../../../packages/render/src/scene-auxiliary-views.ts)) from its `Forward admitted shadows` task's `onAfterTaskExecute`: after Babylon's evaluation (world matrices, `_activeSkeletons` reset, particle steps) and the view's shadow maps, before the view's own objects. They execute their graph without `Scene.render` (no second animation, particle step or render-observer run); never admit lights or shadows (scene-wide, camera-ranked: only the scene view admits, or every material's light defines would churn per frame); never probe the scene (`isSceneFrameReady` binds shadow maps, refitting cascades); draw the owner's candidate list; and draw into own scene targets (or the chain's), writing the camera output only in the final copy so a monitor in view samples the previous image. Nothing that dirties lighting (a new shadow map, a light toggle) may happen inside their draw: it runs mid-graph for the scene view.
- Per-view sun maps: `SceneShadowController.attachView(camera)` (claimed by the capture at target creation, released with its view) mirrors every admitted sun map for that camera: same admitted size, cascades and settings, created by the same `createShadowGenerator` (hooks, defines, bias), keyed to the camera (`light._shadowGenerators`; Babylon binds `getShadowGenerator(activeCamera) ?? getShadowGenerator()`, so receivers drawn for the capture camera bind its own map), fitted to it as a scene view there would fit one, and redrawn in every pass the view draws (no render-once). A mirror is cascade tiles of the same shadow atlas, so it charges nothing (the atlas is charged once): it takes the largest tile size the atlas has room for beside the scene view's admitted and standby maps, halving at once, samples neutrally until its first draw (its tiles hold what their last map drew), and gives way when a scene view's map finds no room in the atlas (`ShadowViewMaps.yieldAtlasTiles`, before standby maps are released or the map halves), mirroring again at the sync's end from what is left; mirrors of released or replaced maps go before replacements are built (`ShadowViewMaps.prune`), so the atlas goes with its last tile. Refused at 256 (warned once per scene map), the view's receivers bind the scene map (`viewBoundGenerator` falls back to it) and the view asks again after a second or once the scene map changes: toggling the sun's `shadowEnabled` for the view would rebuild every unfrozen material's light defines twice a frame. `metrics()` counts their passes. A view's `ManagedShadowsTask` (`view`) draws only its own maps and receives the scene view's point/spot maps as drawn, never calling `refreshShadowMaps` (it would refit local depth and reset render-once for the capture camera). Its object passes report a camera-keyed map with the cascaded task name and its camera: Babylon's `_setLightsForShadow` writes every other map under the null key, which would hand the scene view the capture's map. `unsupportedManagedShadows` accepts camera keys only for `viewBoundGenerator` maps.
- Point/spot maps stay shared: they do not depend on the view, and `fitLocalShadowDepth` writes their depth range explicitly from the scene camera, so every view binds the drawn range. Differences from a camera at the capture: the near plane is the scene camera's, and which local lights get maps is ranked from the scene camera, like light admission.
- Cluster light data is sorted per camera and every graph redraws the mask before its objects; Babylon's `_updateLightData` flushes WebGPU work before each upload, so a view's draws submit with its own data. A failed auxiliary preparation retries at most once a second; a throwing auxiliary draw is caught per capture (warned once until a draw succeeds), which keeps its last image.
- GPU particle systems (`OwnedGPUParticleSystem`) step once per scene frame on their first draw; later draws that frame show the stepped buffers, so captures never step them again.
- Graph camera writes are counted per scene (`graphCameraWrites`), not per graph: Babylon's graph render, `setActiveCamera` and auxiliary swaps are never authored camera changes for any graph of the Scene.

## Loading and readiness

- Play and the exported player share `createSceneLoadReadiness` ([`scene-load-readiness.ts`](../../../packages/render/src/scene-load-readiness.ts)): `sceneLoading` opens a transaction with a monotonic load ID, `sceneRealized` closes the worker's assignment batch, then models, sample-ready textures, shader warm and first-frame presentation complete before `sceneModelsReady` acknowledges that ID. Superseded loads never acknowledge or report failures. Streamed instances use `createSceneStreamingReadiness`.
- Editor Play shows the loading dialog; Preview Build and exported players show no host loading UI (games author loading with SceneLayers) and only mirror phase/progress on `data-scene-load-*` attributes. A scene load's phases (`SceneLoadPhase`, [`scene-load-readiness.ts`](../../../packages/render/src/scene-load-readiness.ts)) run Preparing Scene, Loading Models, Loading Textures, Compiling Shaders, then Presenting First Frame; Compiling Shaders carries a count (`SceneLoadProgress.count`, shown as `(done/total)` by the editor's loading dialog). Compiling Shaders counts the warm-up's units (`prewarmMeshMaterials`: a Material's plain or instanced variant for one mesh, listed before the first, so units sharing an Effect finish at once); its later work (spawn warm-up, the graph's readiness probes) shows the full count. The editor viewport's own load (`runSceneViewportBlockingLoad`) counts Compiling Shaders the same way.
- Asset sources are scoped: Scene catalogs, `EngineHandle.acquireSceneSources` and script load handles acquire through one loader; unread deferred scenes stay unread. Source/CPU budgets and GPU budgets are separate.
- Native work (model decode/LOD, audio decode, cold texture/material/font preparation) shares one admission queue per Engine (`nativePreparationForEngine`, [`native-preparation.ts`](../../../packages/render/src/native-preparation.ts); defaults 2 concurrent, 64 MiB temporary). Priority order: gameplay (High), preload (Normal), background (Low). Later commands for a slot wait behind its cold assignment and apply in order. A Scene source's cold texture preparation (`acquireSceneSources`) acquires a 2D Texture in the material sampling (`MATERIAL_TEXTURE_SAMPLING`) and an environment cube as `{ isCube: true }`, the samplings Materials and environment lighting bind, so it warms their upload rather than a second one (`create-engine.play.test.ts`); a Sprite's pixel-art sampling is still uploaded when it is first acquired.
- Editor blocking loads realize in cooperative chunks (`runSceneWork`; yield after about 8 ms or 256 steps). Hidden Scene tabs defer construction until their canvas has a nonzero size.
- A world load compiles each lit Material once, against its final lighting, in the load's warm-up (`prewarmSceneMaterials`) and graph probes. Model and foliage instances that publish during the load compile nothing (`holdSceneInstanceCompiles` in [`glb-anim.ts`](../../../packages/render/src/glb-anim.ts); `prepareInstanceMaterials` still admits their textures): realization starts model loads before it creates the lights, fog and shadow maps, a new Material's light capacity is set at the warm-up's `syncSceneLighting`, and an unpublished instance is not yet a shadow receiver, so their compiles built variants the first frame never draws. The hold lasts from the editor's `loadSceneAsync` (while its generation is current) or Play's `sceneLoading` (while that load is) until the world warm-up starts or the load fails (the editor load rejecting, `sceneLoadFailed` reaching the Play Engine); instances published outside a load (drops, spawns, streams, foliage edits) compile before they publish, in the variants Babylon draws them with (next bullet).
- The warm-up (`prewarmMeshMaterials`) and `prepareInstanceMaterials` compile each mesh only in the variants Babylon draws it with (`drawnMaterialVariants`, [`drawn-variants.ts`](../../../packages/render/src/drawn-variants.ts)): plain, plus instanced for a mesh with instances, only instanced for a thin-instanced mesh (foliage), and nothing for a mesh without vertices (empty roots, model placeholders, geometry that arrives later, which the graph probes compile).
- Owned unlit editor helpers built on `StandardMaterial` (collider dashes, volume fills, nav mesh fill, billboards, the camera model, pivot markers) carry `HelperProgramPlugin` ([`helper-program.ts`](../../../packages/render/src/helper-program.ts), `shareHelperProgram`). Babylon links one program per Effect key, and a mesh's non-uniform scale (`NONUNIFORMSCALING`) or a material's transparency mode (`ALPHATEST_AFTERALLALPHACOMPUTATIONS`) changed the key without changing the source, so one shader linked once per combination in every pass that draws helpers. The plugin pins each define off only while the program cannot read it (`NORMAL` and `ALPHATEST` absent); a new unlit helper material calls `shareHelperProgram`. The class is in the `nativePlugins` of `shadow-material-policy.ts`: an unlisted plugin class takes the material out of GPU picking's stock-vertex-stage set.
- Particle preparation follows the held-thread and compile-progress rules of the Loading budgets and Held threads bullets above. `boundParticlePreparation` ([`particle-system-factory.ts`](../../../packages/render/src/particle-system-factory.ts)) bounds `ParticleService`'s wait for a bundle's slots (one per preparation; expiry fails the bundle) and `bindParticleMaterial`'s wait for the Material's build and effect (one per bind; expiry rejects and the service skips the slot). Each is a `createHeldThreadBound` of the 4 s shader-warm bound, checked every 16 ms (well under `SCENE_THREAD_HELD_MS`, so a longer gap between checks is a held thread), with its own `HeldThreadBudget` and `DriverCompileWatch`: a synchronous link that outlasts the bound is not charged, a wait that keeps finishing shaders renews up to `SCENE_PREPARATION_CEILING_MS`, and one that never readies fails after its bound plus the credited time. The Material build can outlast the bound (a Custom GLSL particle Material links a probe effect first). Progress is per Engine, so unrelated compiles on the shared Engine renew a preview's preparation too. Timeout messages end with the watch's counts and keep the words "timed out" (the particle proofs in `e2e/` retry on them).

## Rendering settings

- One lighting path; projects and Scenes carry no render path (a saved `renderPath` key is dropped on load, [`rendering-pipeline.ts`](../../../packages/core/src/rendering-pipeline.ts)). `sceneRenderingPipeline` ([`scene-rendering-pipeline.ts`](../../../packages/render/src/scene-rendering-pipeline.ts)) reports the project's requested GPU backend, the one the Engine runs and why they differ, for diagnostics and scalability readback.
- `settings.render.mode` is PBR or CEL. CEL is display-space with hard steps for bands, shadow visibility and highlights; there is no softness or Smooth option. Only graph Materials follow the mode: each is one graph whose `HapticLightingBlock` draws CEL as its `HAPTIC_CEL` define, re-prepared on a mode change, and nothing replaces a Scene's materials.
- Real-Time Reflections (SSR) read the geometry pass's reflectivity attachment (rgb F0, a glossiness; `PREPASS_REFLECTIVITY`, requested only by `spatial-effects-graph.ts`). Writers: PBR (Babylon; unlit writes zero), lit graph Materials (`GeometrySurfaceOutputBlock`: base color, metallic, roughness; unlit writes zero, as the built-in Mirror surface does), and Standard only with `SPECULARTERM` ([`standard-reflectivity.ts`](../../../packages/render/src/standard-reflectivity.ts): Babylon wrote every Standard surface's specular color, white by default, so unlit sprites and quads mirrored). CEL runs SSR whenever the project's Real-Time Reflections effect runs (one setting for both modes; there is no CEL-only switch, and a saved `cel.reflectionsEnabled` is dropped on load); AO stays PBR-only.
- Color pipeline (`render.effects.colorPipeline`, v1): `legacyDisplay` default; `sceneLinear` only for PBR. Babylon's image-processing pass is the only display encoding; each Display Color task owns its own `ImageProcessingConfiguration` (sharing the Scene's corrupts per-material processing). ACES hue shifts are expected; `neutral` holds hues.
- `resolveSceneRenderingQuality` ([`render-settings.ts`](../../../packages/render/src/render-settings.ts)) is cached per Scene by the identity of `SceneRendering.project`, `shadowOverrides`, `localQualityOverrides` and `qualityOverrides`: writers replace those inputs, never mutate them, and every caller shares the result (and `SceneRendering.shadows`, which aliases its `shadows`) read-only.
- Scalability categories, presets and the ownership registry are in core; `ScalabilitySession` holds non-persistent session overrides. Readback separates requested from effective; effective changes only after a renderer-confirmed ready frame. Backend changes reject with `restartRequired`. Artistic settings (CEL, IBL, outlines, output size) never mark a category Custom. Tiers are authored targets (Low budget Android, Medium A16, High desktop, Ultra high-end), not qualifications.

## Lighting and shadows

- Lights are data (decided): no light change compiles a shader. A light switching, spawning, moving, starting or stopping its shadows, or entering or leaving the light budget only writes the `HapticLights` block and the shadow atlas. Reason: Babylon bakes each light's type, shadow and filter into a receiver's defines (`LIGHT{i}`, `SHADOW{i}`, `SHADOWPCF{i}`), so each such change was a new program, which iPad WebKit links in seconds and then blocks on at its first draw. The lighting CI gate (`the lighting CI gate` in [`compile-hold-acceptance.test.ts`](../../../packages/render/src/compile-hold-acceptance.test.ts), a merge gate in CI's unit job) holds it: after the first presented frame, lights are switched, spawned, recoloured, moved, removed and pushed past the block's maximum, shadows of each atlas kind are started, moved, stopped and restarted, and a held actor is spawned. Under the synchronous, parallel-compile and WebGPU driver models no step compiles an Effect, waits on a pipeline or creates one in a shadow pass, and no compiled Effect carries a light define.
- One lighting path. There is no render-path setting and no light path chosen per material, Scene or device, and lighting enters a shader only in the lighting function. Every lit surface is a NodeMaterial built from a Material document, and engine code creates no lit `PBRMaterial`, `StandardMaterial` or `CelMaterial`. Built-in water draws the water starter; its `WaterMaterialPlugin` is unreachable until it is removed. A level's programs (its Materials with the mesh features they draw with, in each pass) are a bounded set, compiled behind its loading screen. Content arriving later compiles while it loads and stays hidden until ready (`reveal-pending.ts`). A settings change (quality level, render mode) may compile.
- Babylon `Light` objects stay as inert data sources: gizmos, picking, billboards, admission and the shadow controller read them, and no Material does.
- Falloff is physical for every surface. Not supported, because no Material document or the glTF loader can turn them on (the loader registers no `KHR_materials_*` extension but unlit):
  - specular colour, IES profiles, projection textures, lightmap modes and falloff types;
  - clear coat, sheen, iridescence, subsurface, anisotropy and refraction;
  - shadowed rect area lights.
- Shadow atlas decisions:
  - It is one atlas of tiles of different sizes, not a 2D array of equal layers, to keep memory within the mobile limits; filtering stays inside each tile.
  - A point light is six compare tiles filtered with PCF, so there are no cube maps and no Poisson fallback.
  - Contact Hardening (PCSS) reads the same depth texture without compare: through a WebGL2 sampler object (a Babylon patch hunk), or `textureLoad` in WGSL. No colour copy of depth exists, and no colour attachment.
  - Not supported, as nothing uses them: transparency shadows, frustum edge falloff, darkness as a setting, and the cascade debug define.
- If the light loops cost too much on the A16, the remedy is light culling: per-cluster light lists built on the CPU. Per-mesh lists fail on large surfaces and instanced batches.
- Device profile ([`device-profile.ts`](../../../packages/render/src/device-profile.ts)): the one place render code tells device classes apart (`isMobileGpuDevice`: an iPhone, iPad, iPod or Android user agent, or a Mac one with touch, which is how iPadOS reports, in every host). `deviceProfile()` gives the class's caps: the shadow map edge ceiling and the texture cache ceiling. Consumers read the profile, never the user agent.
- The texture cache ceiling (768 MiB on phones and tablets, the Medium level's budget; `TEXTURE_BYTE_CEILING` elsewhere) bounds whatever budget a quality level, the Engine Settings or a view sets (`ResourceCache.effectiveCeiling`), and `deviceTextureLimits` reports `textures: at most … on this device class` in `qualityLimits` when a level asks for more. It only trims unreferenced textures sooner; nothing a Scene holds is evicted.
- Shadow map edges have a device-class ceiling: `effectiveShadowSettings`'s `mapSizeCap` (`deviceProfile().shadowMapCap`, null on every device class: phones and tablets get the desktop's shadow and light limits). The shadow controller and the diagnostics both pass it, so admission and the reported limits agree; a ceiling lowers, never raises, an authored size, leaves budgets, passes and cascade counts alone and reports `shadow maps: at most … on this device class` in `qualityLimits`.
- Light admission ([`light-policy.ts`](../../../packages/render/src/light-policy.ts), [`scene-lighting.ts`](../../../packages/render/src/scene-lighting.ts)) is the light block's selection (`selectHapticLights`), within the scalability local-light budget: sun/fill first, then priority, camera distance with incumbent bonus, stable identity. Exclusion never changes authored Enabled. Graph Materials hold no light defines, so no light count or capacity is part of an Effect key.
- `HapticLightingBlock` ([`haptic-lighting-block.ts`](../../../packages/render/src/haptic-lighting-block.ts), [`haptic-lighting-shader.ts`](../../../packages/render/src/haptic-lighting-shader.ts)) is the one lighting path, on WebGL2 and WebGPU (GLSL and WGSL twins in one module, which change together; every shipped Engine has uniform buffers, and the Babylon unit tests give every NullEngine them, `test-support/light-block-engine.ts`). `material-compiler.ts` builds every lit surface with it: Haptic's own metallic-roughness function (GGX, height-correlated Smith, Schlick, Lambert, the split-sum environment BRDF table with multi-scatter compensation, horizon occlusion, Babylon's pre-scaled irradiance harmonics, box projection, the box relative to the floating origin as the surface positions are) over every light of one per-Scene `HapticLights` uniform block ([`haptic-lights.ts`](../../../packages/render/src/haptic-lights.ts), written each scene-lighting sync from the lights its admission left on (`selectHapticLights`, Forward's selection hook: ranked as Forward ranks them, then admitted per type up to `DeviceProfile.lightMaximum`, the same on phones and tablets, and within the scalability local lights; one fill; the rest are forward-excluded like budget-limited lights, yellow billboard included, and listed in `sceneLightingLimits`), and bound to each draw's Effect directly: a `UniformBuffer` bound through `bindToEffect` rebinds to that Effect on every update, which on WebGPU writes into a stale draw context). It is no Babylon light block, so its Materials hold no light defines. Point and spot lights fall off with the inverse square, windowed to zero at their range; a spot's cone is glTF's (`KHR_lights_punctual`): full inside its Inner Angle, zero past its Outer Angle, the cosine's linear step squared between (the inner angle's cosine sits in the spot record beside its shadow's first view), as the volumetric march's cone is, so a spot lights nothing outside its shadow's view. Environment Influence and Specular (a non-metal's F0 = 0.08 × Specular) are block inputs. CEL is the block's `HAPTIC_CEL` define, set from the Scene's render mode, so a CEL Material is the same graph (`followRenderMode` marks it dirty on a mode change, frozen or not): `cel-shader.ts`'s ramp, light mixing and hard highlights over the same records and falloffs, its own polynomial irradiance (`bindCelSettings`), and the display colour converted to linear so emissive, fog and the display conversion are PBR's. A highlight takes its light's colour times intensity. A Scene with its lights disabled (the Unlit viewport) writes no records. Rect area lights are records of their centre and half extents, shaded with Babylon's LTC tables (retained for the Scene while the block exists) and the standard LTC Fresnel; CEL evaluates them at roughness one half, as Babylon's light block does, and the fill's presence is `hapticFillDirection.w`. Their prepared emissions are layers of one always-bound 2D texture array ([`area-emission-array.ts`](../../../packages/render/src/area-emission-array.ts)): the first `DeviceProfile.areaEmissionLayers` distinct emissions among the admitted rect lights, rebuilt (an upload) when that set changes, the layer in each record; a light past the cap draws its flat colour and is listed in `sceneLightingLimits`. `AreaRectLightOwner` registers its pixels (`setRectLightEmission`) and keeps no texture of its own. Spot lights' shadows, point lights' cube faces and the sun's cascades are tiles of the Scene's shadow atlas ([`shadow-atlas.ts`](../../../packages/render/src/shadow-atlas.ts)): one depth-only target (4 bytes per texel), made with its first tile and released with its last, packed with square power-of-two tiles by a quadtree ([`shadow-atlas-allocator.ts`](../../../packages/render/src/shadow-atlas-allocator.ts)). Its edge (`shadowAtlasEdge`) is the largest power of two whose depth fits the shadow quality level's byte budget (Low and Medium 4096, 64 MiB; High and Ultra 8192, 256 MiB), within the device's texture limit and `DeviceProfile.shadowAtlasCap` (null on every device class, so High and Ultra are 8192 on phones and tablets too). The shadow controller admits these maps by the atlas's area (`ShadowAdmissionBudget.atlasEdge`; a tile needs no material sampler, one past the area is `budget-limited` for `shadow atlas space`, and the sun, admitted first, leaves room for the local maps planned into the atlas at the level's size, six tiles for a point light, but at most half the atlas, so local maps past it halve or wait rather than the sun's shadow), and the atlas takes its bytes from the budget once it holds a tile, leaving the rest to the other maps; an allocation key carries the atlas's edge, so a quality level of another edge rebuilds every atlas map, and a tile the packing cannot place fails its allocation, which frees standby maps or halves the tile as any failed allocation does. Casters' depth variants are asked for ahead instead (`ShadowCasterVariants`, [`shadow-caster-variants.ts`](../../../packages/render/src/shadow-caster-variants.ts), from Play's world presentation loading frames through `SceneShadowController.warmCasterVariants`, after the starting state has posed the casters, since a variant reads a caster's scaling): a map of each atlas kind (the sun's cascades, a spot light's tile, a point light's faces), built as an admitted map is (`createDetachedShadowGenerator` in `shadow-map-factory.ts`) on a stand-in light outside the Scene (`dontAddToScene`) with tiles in a private 256-texel atlas of the atlas's format (`createPrivateShadowAtlas`, `placeInPrivateAtlas`; out of the Scene's texture list, leased in the ledger), calls its readiness check for every caster in its first pass, whatever the light's reach; the controller's syncs call it again only for the casters it found not ready (the map's shaders loading, an Effect compiling, a depth wrapper's variant Material not yet ready, which the first call compiles), so a caster that never becomes ready costs one check per sync. Never drawn, the maps keep those Effects (in the casters' draw wrappers, or their depth wrappers) while they live, so a first shadow start of a kind compiles none; new shadow settings build them again, a lost context or the Scene disposes them. A caster that arrives later with a variant no caster had compiles it at its first cast. The same warm draws one scissored depth clear into the private atlas (`prepareTileClear`), so on WebGPU the clear quad's pipeline for the atlas's format exists before the Scene atlas's first tile clears, which would otherwise create it synchronously. A spot or point light's map is an `AtlasShadowGenerator` (a point light's six tiles one per cube face, in Babylon's order +X, -X, -Y, +Y, +Z, -Z, each a 90-degree view drawn and sampled as a spot light's is, filtered with PCF where Babylon's own cube maps fall back to Poisson sampling) and the sun's an `AtlasCascadedShadowGenerator` (Babylon's cascaded generator, built with the level's cascade count, one included, a tile per cascade): Babylon's generator and caster drawing, with its own render target object sharing the atlas's framebuffer, a pass per tile, each pass's viewport set to its tile after the bind and its clear scissored to the tile (on WebGPU only once the clear quad's shader has compiled). A spot record names its shadow view in the block, a point record its first view and face count (the block picks the face by the position's dominant axis from the light), and the sun's record marks the shadowed sun, whose cascades are the first four views (`hapticShadowViews`: per tile, the view-projection it was last drawn with, relative to the floating origin, the tile, the darkness, which stays neutral until the map has drawn, the filter and its quality, whether it is a cascade, whose depth clamps, receiver-plane bias, and Contact Hardening's terms: a perspective view's near and far planes or a cascade's corrections toward the first cascade (Babylon's `_lightSizeUVCorrection` and `_depthCorrection`, from the extents it was drawn with), and the light's size). The shadow functions are one source in two variants (`hapticShadowGlsl`, `hapticShadowWgsl`): the surfaces', and one bilinear compare tap for a position on no surface, the volumetric march's. Each atlas map records its views as it draws and the block's views are written again once it has (`watchShadowDraws`), so a map drawn after the block's write is sampled with the views it was drawn with. The sun's views are those of the map the rendering camera samples: its own in the atlas (a Full Quality capture's, `attachView`), else the scene view's; they are written again when the active camera changes to or from a camera with its own (`onActiveCameraChanged`, which the capture's view fires as it starts and ends), so the capture draws with its cascades and the scene view after it with its own. The block's buffer is not dynamic: on WebGPU a write after the frame's last update moves it to another buffer, so earlier draws keep the values they were bound with (a dynamic buffer has one, which every draw of the frame reads at its last values). The block samples a view with Babylon's PCF kernels (one, four or nine bilinear compare taps by filter quality, each kept a texel inside the tile), for a mesh that receives shadows, a light whose `shadowEnabled` is on and a Scene whose `shadowsEnabled` is. A view whose map uses Contact Hardening runs Babylon's PCSS on its tile (`hapticContactLit`): a blocker search of the atlas's depth over the light's size, then bilinear compare taps over a radius that grows with the blockers' distance, on Babylon's Poisson discs turned per position; a perspective view compares Babylon's depth metric, (clip z + near) / (near + far), recovering the blockers' from their stored depth through the view's planes. With receiver-plane bias (a cascade's under automatic bias) the search reads and taps compare against the receiver's plane, as PCF does, where Babylon's PCSS lets a flat receiver shadow itself. CEL draws Contact Hardening as PCF. The search reads the depth without compare: GLSL through a second uniform on the same depth texture (`hapticShadowAtlasDepth`, bound with `setDepthStencilTexture`), whose unit the patched WebGL engine gives a nearest sampler object without compare (`_samplerObjectFor`, installed per Engine by the block and made again after a lost context), every other unit none; WGSL loads it from the compare binding's texture (`textureLoad`). `e2e/haptic-contact-shadows.spec.ts` checks a spot light's, the sun's and a point light's against ray-cast masks of their blockers, and CEL's against its PCF. For the sun it chooses the cascade as Babylon does (the first whose far end lies beyond the position's view depth from the camera the cascades were drawn for), blends into the next over the cascade's last `cascadeBlendPercentage`, and fades out over the shadow distance's last `fadeFraction`; with automatic bias each tap compares against the receiver's plane, from the position's screen derivatives taken before any branch (WebGPU allows derivatives only in uniform control flow), and low quality then compares four texel centres. The block holds 52 views (four cascades, then 48 local tiles); a light whose views do not fit draws unshadowed. `e2e/render-target-quality.spec.ts` checks a Full Quality capture far from the scene camera against the scene view at its pose. Native materials keep Babylon's path.
- Only the first enabled directional light in scene order illuminates.
- `SceneShadowController` ([`shadow-controller.ts`](../../../packages/render/src/shadow-controller.ts)) owns all shadow maps in editor and Play, including the per-view sun maps of Full Quality captures (`attachView`); the managed bridge renders them unmanaged before `Forward objects`. Local maps render once and refresh on caster revision ([`shadow-map-refresh.ts`](../../../packages/render/src/shadow-map-refresh.ts)); a caster whose content can change without a tracked revision (skinning, morphs, updatable geometry, render hooks, alpha, unknown shaders) keeps every map it reaches drawing each frame. An `InstancedMesh` caches as its source would: its own pose and visibility, its source's geometry, sub-meshes, deformers, material and hooks (`canCacheShadowMaterial` in [`shadow-material-policy.ts`](../../../packages/render/src/shadow-material-policy.ts)), and an instance of a source with levels of detail keeps refreshing; a source with instances caches too. Being an instance, or having instances, does not by itself count as unknown content (an instance is posed by its own world matrix, drawn with its source's parts, and a map culls those parts whole for a mesh with instances): otherwise every map they reach would draw each frame, which on the software WebGPU adapter backs up the queue behind those passes, so later pipeline creations wait and views hold their image. Point/spot maps (`AtlasShadowGenerator`) move to another light of their kind (`moveTo`) or stand by instead of reallocating: a move or a standby return spares the atlas map a new tile allocation, render target, pass ids and caster draw wrappers on each admission change. A move keeps receivers' light order (`exchangeShadowReceivers` swaps the two lights in `scene.lights` and receivers' `lightSources`), which the light block's records follow. A map stands by whether the camera rejected its light (outside the relevant area, budget-limited) or the light block's selection left it out (`isForwardLightExcluded`): releasing it disposes the generator, and readmission would rebuild every caster's shadow draw wrappers (recompiling depth Effects that left the cache) and change the managed shadow task's generator set. Standby maps stay bound, so that set does not change. A new map starts neutral like a moved or resumed one (`neutralUntilRendered`), and its darkness returns to 0 when its last face first draws. Shadow maps keep anisotropy 1. Helpers (`isEditorHelperMesh`), skyboxes, debug overlays and water never cast. The controller keeps the caster registry, the public API and the apply half of `sync` (releases, map moves, standby, construction, the live reservation); beside it, `shadow-entry.ts` holds the per-light record and its allocation-key and cost helpers, `shadow-admission-plan.ts` the pure admission planner (`planShadowAdmission`: ranking, residency, the sun first, count, pass and memory budgets; `applyShadowAdmission` writes its decisions back), `shadow-map-factory.ts` map construction and instrumentation (`createShadowGenerator`: defines, bias, culled caster lists, draw counters; `createDetachedShadowGenerator`: a map no admission counts), and `shadow-view-maps.ts` the per-view sun maps (`ShadowViewMaps`). The controller reserves the scene's shadow bytes itself. `shadow-controller.ts` re-exports their public names.
- Custom-depth casters (authored WPO, masked and lattice materials use a `ShadowDepthWrapper`) share depth Effects: the patched wrapper keys each depth Effect by its source and defines, not a per-(subMesh, generator) random token, so every caster of one graph, including its private instances, shares one Effect per depth-define set.
  - Each wrapper entry holds one Effect reference and disposes it once (`AuthoredShadowDepthWrapper.retireEntry`), so a shared Effect is released when its last entry retires: mesh, material or wrapper disposal, a define or base-effect change, or its generator's disposal. The vertex array object is released only when the Effect itself dies.
  - `ShadowGenerator.dispose` never reaches a material's wrapper. A wrapper observes the shadow map's `onDisposeObservable` from the first entry it prepares for a generator and retires that generator's entries on every sub-mesh. That covers every disposal path (controller, `Light.dispose`, scene teardown) and a recreated map; a re-created generator acquires new references.
  - `NativeLatticeShadowDepthWrapper` keeps no entries: it delegates to one `AuthoredShadowDepthWrapper` per generation. Stock `ShadowDepthWrapper`, whose define change overwrites `mainDrawWrapper.effect` without disposing it, therefore runs only in tests.
- Directional Auto Bias adapts to the current projection and admitted map size; derived values are never serialized. It adds no normal inset (split normals would open contacts) except for casters marked with `markSmoothNormalShadowCaster` (landscape chunks), which draw with `SMOOTH_CASTER_NORMAL_BIAS_TEXELS` world texels so receiver-plane PCF does not self-shadow concave triangle edges (`shadow-bias.ts`). Point/spot automatic bias is unsupported (authored offsets only). The sun's cascades are built on its own Engine's support (every shipped Engine, WebGL2 and WebGPU, draws them), not Babylon's last-created Engine's (see the runtime member replacements below).
- Sun incidence sets directional shadow quality: a map texel and its PCF kernel stretch by 1 / cos along a face the sun meets at incidence cos, and an overhang's shadow lengthens likewise. The seeded sun (`DEFAULT_SCENE_SUN_POSITION` in [`skybox.ts`](../../../packages/core/src/skybox.ts)) therefore meets faces turned to the default camera at cos 0.6. The Basic 3D Mannequin shadow specs hold the drawn edge to the ray-cast one in metres (`mannequinShadowEdgeError`, [`mannequin-shadow-pixels.ts`](../../../e2e/mannequin-shadow-pixels.ts)); their sample classes scale with texel size and cos, so a grazing sun widens its own tolerance.
- Shadow admission lowers resolution to fit (256 px floor) and retries at half size on allocation failure; it never changes authored values. Quality presets and per-tier ceilings live in core [`shadows.ts`](../../../packages/core/src/shadows.ts).
- Shadow memory is the atlas: one depth-only texture of 4 bytes per texel (`SHADOW_ATLAS_BYTES_PER_TEXEL`, `shadowAtlasBytes`), charged to the shadow quality level's byte budget once it holds a tile; its tiles cost nothing more. Low and Medium's 4096 edge is 64 MiB, High and Ultra's 8192 is 256 MiB. `ENGINE_SHADOW_BUDGET` is 768 MiB and the managed ceiling (`MANAGED_RENDER_BYTE_LIMIT`) is 1 GiB.
- Editor light billboards are a status palette, not the light colour: white operating, yellow limited (past the light block's maximum or the Local Light Budget, or missing shadow allocation), red disabled/non-illuminating. Tint multiplies the diffuse texture (emissive would wash it white).
- Membership or shadow changes must dirty frozen materials' light/shadow defines; WebGPU graph materials rebind through [`webgpu-node-material-rebind.ts`](../../../packages/render/src/webgpu-node-material-rebind.ts).
- GPU allocations (shadow, cluster, water, area light, post-process, geometry) reserve in one Engine ledger before construction (`beginManagedRenderAllocation`, [`managed-render-resources.ts`](../../../packages/render/src/managed-render-resources.ts)); WebGPU releases after the end-frame destruction drain or a lost device (`releaseManagedRenderLeaseAfterDisposal`). Uncertain cleanup keeps the lease. Estimates, not measured VRAM. A Mirror surface's fixed 1×1 fallback texel (one per Scene, bound while its reflection has not drawn) stays outside the ledger, like held images.
- Rectangular area lights are unshadowed (no generator, light through walls). LTC tables are bundled ([`resources/`](../../../packages/render/src/resources/), CC BY 4.0, no CDN). Emission textures are prepared at authoring time into a versioned derived chunk; gameplay never runs the processor; missing data disables the emitter with a diagnostic.

## Resources

- One `ResourceCache` per Engine (`resourceCacheForEngine`) shared by world, SceneLayer and preview Scenes. Exact-generation leases with idempotent `release()`; reading a held resource never re-acquires. A texture lease also holds its sampling key (`invertY`, mips, filtering, alpha, anisotropy): when a sampling's last lease is released while other leases keep its entry, its wrapper is disposed, with its upload and extra object URL when no other sampling shares them, because entry eviction cannot reach it then. An unreferenced entry keeps every sampling until it is trimmed or flushed; a flush (`flushUnreferenced`, which every owner's `dispose` runs) also disposes a sampling left without leases in an entry that another lease holds again. Default 2 GiB accounted ceiling, trims unreferenced entries to 80% ([`perf-ceilings.ts`](../../../packages/render/src/perf-ceilings.ts)); live leases are never evicted; the largest live view cap wins. Geometry is accounted (`GEOMETRY_BYTE_CEILING`) but never evicted.
- Editor Play compares the Engine's texture cache before and after a session; a texture that outlives it is reported with its name, size, native references and ResourceCache entry (`describeEngineTexture`), whose lease count is the leases on the samplings that share that native texture, not on the entry. A KTX2 decoded to RGBA reports its last mip's size (Babylon 9.29), so a 1×1 report can be a full-size texture. A texture a live Scene outside the session still references is not Play's to release, so it is not reported: an editor preview opened mid-session (a Class graph's viewport) creates its own BRDF table on the shared Engine. Ownership decides it, by identity: `internalTexturesHeldByScene` collects what each other Scene in `engine.scenes` registers, its Materials sample, its environment sets and the per-Engine area-light LTC tables its `_ltcTextures` slot retains (textures built on the Engine, like the ResourceCache's, reach a Scene only through a Material or the environment), and for every render target among them its colour texture, multi render target attachments and depth/stencil texture, which are separate native textures. The session's own Scenes (`EngineHandle.ownedScenes()`: the world Scene and every Scene the SceneLayer compositor built, meaning layer Scenes, output-blit Scenes and retired generations still releasing, captured before disposal) never excuse what they hold, even one that outlived its disposal, and a texture no live Scene references stays a leak. `e2e/simulation-graph-debug.spec.ts` stops a Simulation after a Class graph first opened during it and expects no leak report. `create-engine.play-textures.test.ts` pins the default skybox, default material and sun shadow map to zero retention across cycles; textured materials, models and post-processing are not covered there. `resource-cache-texture.test.ts` pins that a handle's sampling of a texture is released while another handle still leases the texture in another sampling, and that a flush releases a sampling that went idle before another sampling leased the texture again.
- Content identity is the SHA-256 of an immutable installed Blob. Never fragment `blob:` URLs (Babylon escapes the fragment into the identity). Different upload keys (`invertY`, sampling, mips, cube) get separate wrappers from the same Blob.
- KTX2 block-compressed uploads ignore `invertY`, so `prepareTexture` builds them unflipped and flips V on the wrapper (`vScale = -1`, `vOffset = 1`). Samplers must apply the texture matrix. A Babylon change that sets `_invertVScale` for KTX2 would double-flip.
- WebGPU rejects ASTC/BC7 off the 4×4 grid: the patch decodes those Basis KTX2 to RGBA per texture; `configureKtx2DecoderRuntime` must leave `forceRGBA` undefined (not false) so the per-texture value wins. Compressed Textures encode block-aligned except atlases.
- Six-face cubes are created on the Engine, not the Scene; skybox materials null `reflectionTexture` on dispose so Play teardown cannot drop a cached cube. The skybox never calls `createDefaultSkybox`, never sets `scene.environmentTexture`, is not `infiniteDistance`.
- Babylon's cube upload runs when the last face decodes and never checks disposal. A cube released or evicted mid-load (`disposeTexture` in `resource-cache.ts`) drops its wrapper at once but keeps the native texture until that upload settles, bounded by the preparation deadline; disposing it earlier uploads to an unbound target ("no texture bound" warnings, then GL error 1282 at the next presentation).
- Publication of materials, texture parameters and sprite/skybox/model replacements waits for full lease preparation (byte accounting and budget admission). `Texture.isReady()` is not enough: Babylon's error sampler reports ready.
- Replacements are transactional: prepare the successor, keep the working predecessor, publish only on success; generation/owner checks drop late completions; failed requests stay latched until their inputs change.
- `MaterialLibrary` warms a new Material generation for the meshes bound to it only when it replaces a published one: the predecessor stays bound until the successor has compiled for them. A first acquisition warms nothing; its host compiles what it draws (the load's `prewarmSceneMaterials`, readiness probes, or a preview's own prepare-then-bind step), because warming at acquisition runs before the Scene's lighting, fog and transforms are final and builds variants nothing draws. A host that binds at acquisition and captures right after (the asset thumbnail) sets `warmFirstAcquisition`, so a program that cannot link fails the capture through `ready`. So `ready`, `isReady` and `compiledMaterialGuids` mean built with textures admitted, not linked.
- A program the Engine cannot link is reported where its Effect is first created: the load's warm-up rejects naming the Material and mesh, and `material.onError` (compiler `onLinkError`) reports the shader log, without JS frames, as `material.compile.failed` through `onTextureError` / `onMaterialDiagnostic` (`console.warn` when the host takes none). The library then retires the generation: it is disposed, so its meshes fall back to the default Material and readiness can pass, but its entry stays in its map so holders' reference counts carry to the next acquisition of the key. Without that, an unlinkable bound Material never reads ready and the Scene draws nothing, silently. Babylon hands a cached Effect to a second requester without its `onError`, so each compiled material also listens to `onEffectErrorObservable` and matches the Effect's first creator by build id (`nodeMaterial<buildId>`): materials sharing a program (a root, its Instances and per-component copies adopt one build id) retire together. A surface variant (outline mask, depth or normal capture, shadow depth) is a program of its own that its pass cannot draw without, so its link failure reaches the owner the same way, with the log naming the variant, and retires the generation. The owner is found by the entry's current key, which `adoptPreparedInstance` moves from the staging token to the component's, so an adopted copy retires too. A reported failure also drops the program from the compiler's shared-program registry, so a Material compiled after it builds its own Effect (and hears of its failure) instead of adopting the dead build id. A sharer the registry cannot reach would adopt the dead program without hearing of it, so the library latches the failed plan per asset and shading variant, shared by its instance keys (hash and diagnostics): `acquire` and `resolve` of that hash fail at once with the same diagnostics, compile nothing and report nothing again, until the hash changes (an edited graph, function or texture identity), `markDirty`, `forgetFailures` or `releaseScene`; releasing the key does not end it, because the next holder would adopt the same dead program. `forgetFailures` runs by itself when the Scene's receivers bind other lights or shadow maps (`notifySceneReceiversChanged`, [`scene-readiness-signal.ts`](../../../packages/render/src/scene-readiness-signal.ts)): `syncSceneLighting` after a different enabled-light set, shadow layout or light capacity, and every `invalidateShadowReceiverHandoffs` caller in the shadow controller (a map created, released, moved or retuned). A varying or uniform limit can fail a link for that set and not for another, with the plan hash unchanged. A refresh that changes none of them (the retirement's own) keeps the latch. Any failure of the plan itself latches (a build failure, a link failure, a shader error from the replacement warm-up or Custom GLSL's probe). A texture that is not ready does not (its own preparation reports it, and its identity is part of the hash), and neither does a stall (`MaterialCompileStalled`, diagnostic `material.compile.stalled`: no shader finished for the warm-up's or the probe's bound, which says nothing about the program); those requests compile again.
- Models: canonical bytes are GLB; [`gltf-loader.ts`](../../../packages/render/src/gltf-loader.ts) registers the glTF 2.0 loader and its extensions only. Draco/meshopt decoders are self-hosted, never a CDN. OBJ/FBX/STL are converted to GLB at import (`convert-*-to-glb.ts`). Containers load without the file's materials (`skipMaterials`), so nothing draws a loader `PBRMaterial`: a mesh draws its slot's Material asset or the engine default. Per-Scene template containers instantiate per actor. Model slots map by the glTF material index each primitive names (`modelMaterialIndexOf`, read from the primitive pointer in `_internalMetadata`, which instances and clones share), never child visit order; a file without materials draws every primitive with slot 0, and points and lines are hidden (Babylon keeps a primitive's draw mode on its material). `loadModelContainer` gives every triangle mesh without `NORMAL` flat normals (`addMissingFlatNormals`; indexed meshes are unfolded, and unindexed meshes skip Automatic LOD): surface Materials read the `normal` attribute, and a missing buffer reads as zero, which draws black.
- MeshComponent geometry and Material are separate references: a primitive with a Material keeps a null `meshAssetGuid`. `materialSource: "override"` distinguishes an explicit None (engine checker) from inherited Model slots; the picker's "Model Materials" value is UI-only and never saved.
- Runtime parameters (`setMaterialParameter`) share the compiled default until a component's first write, then `MaterialLibrary` compiles a private instance for that component only; saved assets and siblings never change. A None texture binds a neutral white sampler.
- Environment cubes reach render only as ENV or DDS: `.hdr` panoramas become prefiltered RGBA16F DDS at import ([asset-registry.md](asset-registry.md#importers)), so render has no HDR, panorama or filtering path.
- The scene environment controller leases one cache source and clones only its CubeTexture view ([`environment-lighting.ts`](../../../packages/render/src/environment-lighting.ts)); intensity goes through `scene.iblIntensity`. Missing irradiance is derived once per cube; pending or failed uploads join readiness and are never thrown from a frame.
- Skybox source: the controller takes `acquireExisting` on the first enabled, visible skybox mesh's cube (no second upload), draws it in `CUBIC_MODE` with the reflection matrix `RotationY(Environment Rotation) × inverse(sky rotation)` so lighting matches the drawn sky, and follows sky changes from its before-render hook (the mesh list is rescanned only when it changed). A turned sky only rewrites the view's matrix in place: no define reads it and unfrozen materials rebind it every frame, so the hook dirties no material and signals no readiness change, and forces a rebind only on frozen materials' own draw wrappers, whose uniform buffers skip it otherwise. A sky whose cube is still uploading holds readiness and keeps the previous view; a failed sky disables its mesh, which drops the lighting.
- Preview sky ([`preview-environment.ts`](../../../packages/render/src/preview-environment.ts)): `installPreviewEnvironment` draws the engine default sky in Model, Animation, Skeleton, Material and opt-in Particle previews and lights the preview from it through the same controller (`applyEnvironmentLighting` in skybox mode), so a preview frame waits for the sky's upload and filtering like a Scene's. Without it a metal reflects nothing and draws black apart from direct highlights. Thumbnail hosts and Prefab Preview do not call it.
- Reflection probes ([`reflection-probes.ts`](../../../packages/render/src/reflection-probes.ts)): each `ReflectionProbeComponent` captures static meshes (`reflectionProbeStaticActors` in core: plain Actors whose components never move, under static parents; Water and helpers excluded) into a cube render target drawn outside the view's graph like a Fast capture (`drawOutsideSceneView`), one probe per frame, once edits and mesh changes settle (`REFLECTION_PROBE_RECAPTURE_DELAY_MS`) and only when the static mesh set changed (a forced recapture after any authored edit, a Play load or the Recapture Reflection Probes node). The cube is filtered by the shared prefilter path with its own irradiance, then box-projected onto the probe's world AABB. Per-mesh selection ([`mesh-environment.ts`](../../../packages/render/src/mesh-environment.ts)): a pinned patch of PBR and Node `isReadyForSubMesh`/`bindForSubMesh` swaps the scene's `_environmentTexture` backing field to the mesh's cube (the smallest published probe box holding its bounding-sphere centre), so each submesh compiles for its own cube's defines and binds it; a cube switch between consecutive draws of one material, or a change to the cube's box (`markMeshEnvironmentChanged` bumps its revision), forces a rebind (`_forceRebindOnNextCall`, which also refreshes frozen UBOs). A mesh whose probe changes dirties its material; the resolver appearing (first publish) or going (last published probe removed) dirties every material, since selection only dirties meshes it assigned before (probe cubes are engine-bound, so their box setters dirty nothing). Instanced batches use their source mesh's probe. Probes never hold readiness; until a capture publishes, meshes reflect the scene's environment.
- Sky filtering ([`environment-prefilter.ts`](../../../packages/render/src/environment-prefilter.ts)): the controller lights from a GGX-prefiltered copy of the sky, at most 256 per face in half-float, one per Engine and sky upload. Babylon's `hdrFiltering` shader writes every mip, mip 0 included, with the lobe PBR samples it for (`lodGenerationScale` 0.8), and reads the source mip matching each sample, so 64 samples suffice and the face downsample needs no extra pass. The target reserves under the `environment` managed category. While filtering, readiness holds and the previous view stays; a device without prefiltering or float targets, an exhausted budget or a failed filter lights from the unfiltered sky.
- Automatic LOD ([`model-lod.ts`](../../../packages/render/src/model-lod.ts)): index-only levels sharing the master's vertex buffers, generated off-thread by meshoptimizer, never persisted or exported; selection in `customLODSelector`. No texture streaming (Babylon has no residency API).
- WebGPU lifetime: everything a Scene, preview or Play session allocates must return to the device when it closes; the project Engine lives for the whole session, so any retention grows until allocation fails or the device is lost. WebGPU destroys released buffers and textures at the next frame end, and Babylon disposes a draw wrapper's Effect one end frame after that wrapper, so an Engine with no rendering client would keep a closed Scene allocated until another view draws. A non-owning client's `dispose` therefore calls `drainEngineAfterRelease` ([`idle-engine-drain.ts`](../../../packages/render/src/idle-engine-drain.ts)): the shared Engine runs empty frames until that client's release settles (managed leases wait for an end frame), then three more, then prunes the caches. It gives up if the release has not settled after 5 s, or no frame follows within a second of settling, leaving the rest to the next client's frames; it removes only its own loop, so a client that starts mid-drain keeps rendering.
- Babylon's global WebGPU bind-group and render-pipeline caches never evict. [`webgpu-cache-pruning.ts`](../../../packages/render/src/webgpu-cache-pruning.ts) records the buffers, textures and Effects each Engine releases and drops their entries at a frame end once enough have accumulated (or enough frames have passed) and when an idle drain ends; ids are never reused, so no lookup can hit a pruned entry, and a wrong prune only costs a cache miss. Two exceptions, both misses only: `Texture.Parse` restores `internalTextureUniqueId` whenever the JSON carries it (`Texture._SerializeInternalTextureUniqueId` only gates writing it; Haptic never feeds Babylon serialization to `Texture.Parse`, since asset payloads never hold it), and an unbound slot keys as id 0 plus the range start, so releasing buffer or texture 0 also prunes every unbound-slot entry. Never `ResetCache()` or disable either cache (bind groups would be rebuilt per draw). WebKit backs each bind group with Metal argument buffers.
- Babylon never disposes a deleted WebGPU pipeline context, and never deletes the context of a released Effect outside its compiled-effect cache (an `EffectWrapper` without the shader store). [`webgpu-resource-release.ts`](../../../packages/render/src/webgpu-resource-release.ts) disposes it in both cases so the Effect's leftover-uniform `UniformBuffer`, which keeps one GPU buffer per draw context that used it, leaves `engine._uniformBuffers`.

## Play presentation and editor views

- The Play Scene starts with camera and light only; actors come from `assignMesh` plus snapshots. Play always draws the latest published snapshot, no interpolation (render and tick share the ~60 Hz cap). `SnapshotSampler` ([`snapshot-sync.ts`](../../../packages/render/src/snapshot-sync.ts)) ignores unpublished buffers and is cleared on scene change; snapshot TRS is world space; new geometry stays hidden until a snapshot poses it. One slot is one visual; when an actor's last Play renderable stops rendering (Render In Game off, Editor Only on) and no capture, audio, particle or rigid body fallback assignment takes its place, the runtime replaces it with an empty `assignMesh` (`meshKind: null`), sent only for a slot whose last `assignMesh` carried a visual (fog-only and probe-only actors get their own empty view-owner assignment).
- The runtime re-sends an actor's `assignMesh` with every component property write, unchanged values included (a script writing a Text3D's text every tick). `applyAssignMesh` ([`snapshot-assign-mesh.ts`](../../../packages/render/src/snapshot-assign-mesh.ts)) keeps the slot's visual for a command equal to the assignment that visual was built for (`showsAssignment`: equal as later style, control, painter and text reveal commands left it), while the visual is still the one the slot shows or prepares in that host Scene, the binding's install revision is the one it was built at (`meshAssetInstallRevision`: the inputs `meshAssetFingerprint` hashes, compared by identity through a weakly keyed number per map, since an install replaces them; the record keeps the number, never a superseded map or its bytes, and holds its visual weakly) and neither its staged construction nor its model load failed; anything else rebuilds, and a failed preparation is tried again. A rebuild would hand the world view a mesh that has not drawn, hidden until it is known ready, and restart a staged visual's preparation before it adopts. A real change still rebuilds; the new visual, replacing one that had shown, waits for no drawn shadow map to list it (`noteReplacesDrawnVisual`, frame path above). A material command's restart of a staged preparation rebuilds whatever the slot shows. The decision is the renderer's, since only it knows what it built, with which installed bytes and in which Scene; script writes still call `refreshComponent` for unchanged values, which can have effects of their own (a written Layer or Mask makes the collider Custom).
- Snapshot apply runs once per applied snapshot identity (`{frameId, layoutGeneration}`); audio pose and listener sync live there, not in render admission.
- Main-thread apply: [`snapshot-apply.ts`](../../../packages/render/src/snapshot-apply.ts) keeps the per-snapshot apply and the slot lifecycle (migrate, retire, dispose) and re-exports by name the public API of the modules behind it, which importers and `index.ts` reach only through it. In dependency order, each importing only those before it and none importing `snapshot-apply.ts`: [`snapshot-binding.ts`](../../../packages/render/src/snapshot-binding.ts) (`SnapshotSceneBinding`, `SlotKeyedMap`, `SlotRootMap`: `binding.meshes`, which indexes its roots on every write so Play outlines exclude other slots' roots without copying every slot, component mesh names), [`snapshot-visibility.ts`](../../../packages/render/src/snapshot-visibility.ts) (snapshot visibility, helper metadata, world copies of overlay slots), [`snapshot-materials.ts`](../../../packages/render/src/snapshot-materials.ts) (Material assignment, parameters, retained owners), [`snapshot-illumination.ts`](../../../packages/render/src/snapshot-illumination.ts) (helper lights and cameras, active camera), [`snapshot-spring-arms.ts`](../../../packages/render/src/snapshot-spring-arms.ts) (spring-arm lag), [`snapshot-component-commands.ts`](../../../packages/render/src/snapshot-component-commands.ts) (component poses and per-component commands), [`snapshot-visual-factory.ts`](../../../packages/render/src/snapshot-visual-factory.ts) (`createPlayVisual`, `createPlayMesh`) and [`snapshot-assign-mesh.ts`](../../../packages/render/src/snapshot-assign-mesh.ts) (`applyAssignMesh` and its strategies). Each keeps its per-binding and per-mesh WeakMaps private behind accessors.
- Overlay Play: size from the overlay box with `engine.setSize`; `clearBeforeCopy`; disable other enabled Scene views until Play closes (restore exactly those); `scene.autoClear = true`; `skipPointerMovePicking` on world scenes. Custom resolution with Black Bars locks the framebuffer and letterboxes with `fitContainedRect`, never CSS `object-fit: fill`; Play restores the hardware scale captured before it started.
- Engine Settings `postProcessingEnabled` gates only editor viewports and in-editor Play, never exported games or the Material editor preview.
- `visibilitychange` (and Capacitor app state) pauses the render scheduler, game tick and texture encode queue. A blocking overlay counts as closed only with `data-closed` or `hidden`; Base UI marks open backdrops `aria-hidden`.
- Editor scenes use `ScenePerformancePriority.BackwardCompatible` plus `applyEditorMaterialFreeze`; Play uses `Intermediate` and `playMode` skips the editor freeze so packed textures can rebuild. Intermediate marks every mesh `alwaysSelectAsActiveMesh`; Play's world Scene clears it before each cull on meshes added since (`play-view-culling.ts`, `settlePlayViewCulling` from `CameraOutputCullTask`), so the camera culls by view. Kept always drawn: meshes the engine marks (`drawWhateverTheView`: particle emitters, spring-arm debug lines), geometry-less meshes, skyboxes and infinite-distance meshes, meshes with deforming bounds (`hasDeformingShadowBounds`), thin instances and water. SceneLayers and editor Scenes are unchanged. A texture-load rebuild must unfreeze → build → reapply authored blend → mark dirty with dirty-block off → refreeze.
- Editor apply is incremental through `EditorSceneSync` ([`editor-scene-sync.ts`](../../../packages/render/src/editor-scene-sync.ts)); work stays proportional to the change. Material rebinding reports net changes only (`withNetMaterialChanges`); unchanged post-process stacks and in-place light uniform edits keep the prepared graph. A transform-only edit (`isTransformOnlySceneEdit`) re-realizes only the actors whose pose changed (`EditorSceneSync.applyPoses`), refreezing the actor roots under them and running the Scene-wide cable and illumination passes; it falls back to the full apply while a realization, visual replacement or model load is in flight, when the Scene has an overlay layout (a move can relayout other actors), and when a moved actor's visual fingerprint changes (a 2D Panel's scale).
- Full editor loads and actor visuals (mesh names, origin hierarchies, transforms, freeze, cable previews, `applySceneToBabylonScene`) live in [`scene-loader.ts`](../../../packages/render/src/scene-loader.ts). It delegates actor classification to `scene-visual-classify.ts`, rebuild fingerprints to `scene-visual-fingerprint.ts`, the per-component mesh factory to `scene-component-mesh.ts` and Mesh collision dashes to `mesh-collision-dashes.ts`, and re-exports their public names. A component's fingerprint kind must change whenever the factory would build a different mesh, because `EditorSceneSync` rebuilds only on a fingerprint change.
- Editor canvases render continuously at the viewport cap and freeze when hidden, off-screen, resizing, under a Dialog/AlertDialog/Sheet, while Play/Preview Build runs, or while Save All runs ([`render-scheduler.ts`](../../../packages/render/src/render-scheduler.ts), [`apps/editor/src/lib/viewport-render-gate.ts`](../../../apps/editor/src/lib/viewport-render-gate.ts)). Static previews idle after a ready frame.
- Gates on an editor canvas compose; none ends another. `setPaused` (one flag per Engine handle, written by Play, scene loads and the app lifecycle pause through `EditorSchedulerRegistry.setPaused`) also pauses its audio and particles. Obstruction leases (`acquireObstruction`, reference-counted) only stop ready frames: loading frames still present under them, and while a Play scene or Scene Layer load is pending, owners already ready keep drawing under its blocker (`shouldRenderReadyOwners`), each frame then leaving the main thread free for as long as it took (`noteRendered`'s end time), so a world whose frames run long (software GL draws the Feature Test main scene at about 3 s a frame) cannot starve the load's source preparation, which awaits storage between frames; a frame that fits its cadence is not held back. Every gate also leaves the main thread free after a frame that held it past its own work (on software GL with software compositing the browser waits there for the GPU to finish the frame, about 3 s for the Feature Test main scene): from the second frame in a row whose next check comes at least `HELD_THREAD_MS` (500 ms) after its work ended, the next frame waits as long, up to a second, so input, timers, worker replies and a test driver's commands still run between such frames (one such gap alone may be a long task after the frame). The count is dropped when Play pauses or the view's visibility changes. Scene edits still reach Babylon under a lease, because the viewport's scene load applies them through `EditorSceneSync` (`loadScene`, or `loadSceneAsync` yielding on timers) when the document changes, not in a frame. Save All holds one lease on every scene and Prefab viewport registered with `EditorSchedulerRegistry` (`registerScheduler`; viewports mounted during the hold included) through [`editor-frame-hold.ts`](../../../apps/editor/src/lib/editor-frame-hold.ts), because each storage await in it resumes only after any frame drawn meanwhile. Play's game view, Preview Build, a Simulation's view, asset previews and thumbnails never register, so a save never holds them. The selected camera's or capture's lens preview (`EditorDebugOverlay`) takes no timed passes while its Engine is paused (`applyPause` calls `setPaused`), so a game never pays for it, nor while its viewport is off screen (`RenderScheduler.isShown`). It redraws at the **Camera Preview Frame Rate (FPS)** Engine Setting (default 30), read each tick. A camera lens draws no editor helpers (`isEditorHelperMesh`), and the preview RTT's `getCustomRenderList` applies the scene cull's `visibility > 0` and layer-mask checks, which an explicit render list skips.
- Picking: viewport taps use a 1×1 GPU object-ID pass ([`gpu-object-id-picker.ts`](../../../packages/render/src/gpu-object-id-picker.ts)) that follows skinning, morphs and WPO and pins the floating-origin context to its scene while it draws (outside `Scene.render` Babylon uses the last scene to render, the gizmo layer in the editor, whose full-view matrices would sample the viewport centre). Babylon writes an object id only where fragment alpha exceeds 0.4 but writes depth regardless, so the pass draws pickable meshes hidden through `visibility` (actor-origin pick spheres) at 0.999 visibility for the probe and draw: otherwise they would go unpicked and hide what lies behind them, such as their billboard; marquee, Play `pickAt`, brushes and transform tools use the CPU ray ([`picking.ts`](../../../packages/render/src/picking.ts)).
- Meshes without a Material draw `installEngineDefaultMaterial`: a NodeMaterial compiled from `engineDefaultMaterialDocument()` (a procedural 16-cell grey checker, lit, with an Emission parameter that 2D sets to 1), so it lights, shades in CEL and Unlit mode and casts shadows as an authored Material does. Primitives keep `mesh.material === null` so the Inspector shows None.
- Editor selection, gizmos and debug overlays never change Scene membership (pre-created hidden guides, entity-free cameras/RTTs); a membership change costs a whole-scene readiness probe.

## Water

- One `WaterDefinition` is shared by renderer, worker and editor (core `water.ts`). Physics, queries and buoyancy never read quality, the GPU FFT or GPU state: every look, Custom Material included, evaluates the CPU spectrum field of core [`water-spectrum.ts`](../../../packages/core/src/water-spectrum.ts) (JONSWAP wind sea plus swell, deterministic hashed Gaussians so every quality tier and the worker share one ocean; 64² and 32² grids at `WATER_SPECTRUM_PHYSICS_RATE`, frames blended, Catmull-Rom sampled). The GPU spectrum (`water-fft-spectrum.ts`) builds the same modes at its own size and drops bins the CPU grids cannot hold, so short render-only detail is the only difference.
- `WaterClock` (runtime driver) advances with the simulation step; the renderer pairs water time with the applied snapshot frame (`setSceneWaterTime` / `sampleSceneWaterFrame`). Editor and previews use real time.
- Rendering gates on the device-effective `sceneWaterQualityDeviceClamp(scene)`, never requested values; `sceneWaterQualityRevision` change re-plans each FrameGraph ([`render-settings.ts`](../../../packages/render/src/render-settings.ts)). `clampWaterQualityToDevice` is the single device gate.
- `WaterMaterialPlugin` ([`water-material.ts`](../../../packages/render/src/water-material.ts)) compiles one look per material through defines; tiers use numeric `SLATE_WATER_QUALITY` with one `#if … >= n` per line so Babylon's define-keyed cache stays correct; zero-valued features compile out. Defines change only on quality, pipeline, asset or flatness changes, never per frame. Its shader source lives beside it: defines and tuning constants in `water-shader-defines.ts`, source chunks in `water-shader-chunks.ts`, per-language assembly and injections in `water-shader-source.ts`; per-Scene placeholders, lighting and binding data in `water-scene-state.ts`; GPU wave uniforms and `WaterVertexWaves` in `water-vertex-waves.ts`. `water-material.ts` re-exports their public names.
- To see which water variants a run requests, set `globalThis.__slateWaterCompileLog = []` before the scene loads: every define change appends the look, REFRACTION/SSR/planar/blend/FFT, shadow, depth-pre-pass and prepass defines, the render pass id and the caller (`WaterVariantRequest`). Nothing is recorded without it.
- Built-in water writes a zero normal and zero F0 into the scene effects' geometry pass (`WATER_EFFECTS_GEOMETRY_DEFINE`, set only in pass ids [`spatial-geometry-passes.ts`](../../../packages/render/src/spatial-geometry-passes.ts) registers for `SpatialEffectsGraph`; the authored post-process geometry pass keeps its normal): the AO march treats a zero normal as no surface and SSR skips zero F0. Its per-pixel FFT normals do not match the displaced mesh in view depth, so AO would darken it in view-dependent blotches and bands behind far crests. Its coverage there is its edge fades, not its transmittance, so its surface fills the buffers at every view angle.
- Refraction/screen-space reflections read a per-view scene copy ([`water-scene-copy.ts`](../../../packages/render/src/water-scene-copy.ts)) registered by render pass id before the first readiness probe; copy-sampling water draws only in `Forward transparent`. Which variant built-in water draws depends on the pass (REFRACTION/SSR compile only into the copy's pass, the depth pre-pass has its own), so the shader warm-up and the pre-graph strict probe skip it (`isBuiltInWaterMesh`) and only the graph's own probe compiles it, under the real pass id: a probe under any other pass compiles a variant nothing draws, and every one is a slow link. Planar mirror ([`water-planar-reflection.ts`](../../../packages/render/src/water-planar-reflection.ts)) is drawn capture-style, entity-free, for one flat body per view that mirrors objects (`waterMeshReflectsObjects`: built-in water, or a Custom Material with a Water Reflection node, Object Reflections on); both look it up while they draw (the lookup is the demand) through one shader source (`planarLookupSource`), Water Reflection under `SLATE_WATER_NODE_PLANAR`, which follows `WaterNodeSurface.flat`; its mirror camera, oblique projection, target and pass are [`planar-mirror.ts`](../../../packages/render/src/planar-mirror.ts), shared with Mirror components. FFT ([`water-fft.ts`](../../../packages/render/src/water-fft.ts)) is fragment-shader passes on both backends, demand-driven (built-in water, or a Custom Material with a Water Waves node): the whole surface (three cascades, displacement, derivatives with per-layer mipmaps, and a ping-pong turbulence foam target accumulated from the Jacobian, each cascade recovering over its spectrum `foamPeriods` entry). Crest foam is the cascades' turbulence below calm weighted by `WATER_FOAM_WEIGHTS` (long waves first) past `waterFoamThreshold` (core: Crest Foam's share of the sum's Gaussian model, calibrated on GPU readback), bound per asset by `waterFoamThresholdOf` to built-in `slateWaterShape.x` and the Water Waves node's foam uniform `.z`. Devices without float render targets draw water flat (`WaterQualityDeviceClamp.spectrum`). All reserve in the ledger's `water` category.
- [`water-mesh.ts`](../../../packages/render/src/water-mesh.ts) creates water surfaces and runs their per-frame update (placement, culling bounds, CPU waves, copy intent, the Custom Material path, picking). Beside it: the per-surface model in `water-mesh-surface.ts`, the scene water clock in `water-scene-clock.ts`, the rest-grid layout and cell budgets in `water-mesh-grid.ts`, per-vertex rest data and its uploads in `water-mesh-rest-data.ts`, the scene blend registry, blend kernel, Global blend rows and normals' fit in `water-mesh-blend-data.ts`, and the blend index sync and budgeted blend refresh in `water-mesh-blend.ts`. `water-mesh.ts` re-exports their public names, and code outside these modules imports only it.
- `settleSceneWater` ([`water-mesh.ts`](../../../packages/render/src/water-mesh.ts)) runs the water update as an early run (it advances neither the clock nor the drawn flags the frame's own run consumes), so blend, placement (`flat`) and the sky reflection view are final before a surface's variants are first probed. The before-render update fires after the strict probes; left to it, those values change the defines of variants already compiled, and every one compiles again. Copy intent is counted when the surface is created (`createWaterMesh`) and re-synced by the update only when enablement changes through an ancestor or `setEnabled`, and by `updateWaterMeshDefinition` when an asset edit moves Refraction or Object Reflections. Call sites: `prewarmSceneMaterials` (always, before the load's warm-up and graph probes), the render loop on frames that draw the world (only when a surface was created or its enablement changed since the last update: editor edits and drops, Play spawns; load frames leave it to the load's settle), and a published scene stream (its roots are held disabled until then, and the update skips disabled surfaces). The syncs are idempotent with the before-render update, and a Scene without water does nothing. `prepareSceneStream` skips built-in water in its warm-up like the load does.
- Bodies within Water Blend Distance blend via core `water-blend.ts`; only the owning body draws and answers queries. A body takes part out to the full distance (`waterBlendReach`) and fades out of the union shoreline over its outer half, where the union's smooth maximum (radius R) no longer pulls: a fade inside the rounding cuts corners into stepped tabs. A grid's outer vertices past its own reach still evaluate the kernel (`outside`), owning nothing, so shoreline and ownership interpolate toward true values. Colours fade over a wider coverage than shares; each surface keeps up to `WATER_BLEND_COLOR_PARTNERS` differently coloured neighbours (alike-coloured ones share a slot) with per-vertex shares (`slateWaterBlend.w`, `slateWaterBlendColors`), read by built-in water and by the Water Colors node (`WaterNodeSurface.partners`). Custom Material water hides what it does not own through its Water Cut block (below).
- Built-in water displaces on the GPU from a static rest grid (`evaluateWaterVertex` in core is the CPU reference); Custom Material water opts in only through a **Water Waves** node. CPU picking hits the rest grid. The other water material nodes ([`water-node-blocks.ts`](../../../packages/render/src/water-node-blocks.ts): Water Colors, Foam, Depth Fade, Scene Color, Reflection) are fragment blocks that read the mesh's `WaterNodeSurface` (asset, and the terrain and contact fields every water mesh builds) and the pass's scene copy (`SLATE_WATER_NODE_COPY`, same per-pass rule as built-in; an alpha-blended Custom Material whose graph reads the copy counts in the copy intent). Their per-pixel wave inputs come from the graph's Water Waves block. They share built-in water's shader sources where they draw the same thing: the bank, depth and edge fades (`waterEdgeSource`, Water Depth Fade's Edge Fade) with the four-tap shoreline under the waves (`shorelineSource`; the nodes read whether the asset has waves from `slateWaterFieldStep.w`), the refraction bend and silhouette fallback (`silhouetteFallbackSource`, Water Scene Color, whose Color is pre-divided by the Material's own fog, the Scene Fog block's factor and linear fog colour (`sceneFogKeep`, `sceneFogColor`), so any linear share of it keeps the background's fog once in every channel, as built-in water's refracted light does), the planar lookup, and the aerial perspective and horizon haze (`aerialPerspectiveSource`, `horizonHazeSource`, Water Reflection), the horizon lift of the reflected ray (`horizonLiftSource`), and the slope-variance roughness (`slopeVarianceSource`, Water Reflection's Roughness output, which blurs its reflection and goes to the Material Output's Roughness in the starter); Water Reflection's Normal output is the half vector toward the lifted ray, which the starter mixes back to Water Waves' Normal under foam, as built-in water lights its foam along the facet. A vertex-and-fragment block gets no automatic varyings for its inputs, so `WaterWavesBlock` passes its rest point and normal itself. The compiler adds a **Water Cut** block (`WaterCutBlock`) to every Surface Material, whatever its nodes; on any mesh that is not water it compiles away. On water it removes what built-in water's `cutSource` removes: the nearest `WATER_REMOVAL_SLOTS` removal volumes reaching the mesh (`selectWaterRemovals`, shared with the plugin), known terrain above the geometry's waterline (the Water Waves node's vertex height through a hidden Water Surface block on the GPU path, the displaced vertices' own otherwise), and a blending neighbour's water (bank distance and ownership margin). Its draw with colour writes off, the blended depth pre-pass under its own render pass id, sets `DEPTHPREPASS` (`WATER_DEPTH_PRE_PASS_DEFINE`): removed water is discarded there and the program returns before the look, the Water Waves node's per-pixel spectrum included. The colour pass discards at the very end (`_injectAtEnd`), after every derivative of the look was taken with the whole quad running. With Water Waves, a blending surface also culls vertices deep in water it never draws (`waterBlendCullSource`, built-in water's cull). In the scene effects' geometry pass it sets `WATER_EFFECTS_GEOMETRY_DEFINE` as built-in water does and, after the output's geometry writes, writes the encoded zero normal and zero reflectivity (`geometryOutputWrite`), so AO and SSR skip the water whatever its graph; the Material's geometry writes are opaque, so its surface fills the buffers at every angle. Every translucent Surface Material also gets a hidden **Water Coverage** block (`WaterCoverageBlock`) between its colour and its fog: on water, outside Scene Linear (`IMAGEPROCESSINGPOSTPROCESS`), it raises the coverage by the brightest channel (to at most 1) and lowers the colour as far, built-in water's raise without the scene copy, so light brighter than an 8-bit target shows over the background instead of clipping; elsewhere it compiles away. The water starter is two-sided, as built-in water is. Built-in shading has one look; stylized water is a Custom Material. Built-in water draws with the water starter itself: `builtInWaterMaterial` ([`water-template.ts`](../../../packages/render/src/water-template.ts)) compiles it once per Scene and every water mesh without a Custom Material shares it (the callers of `createWaterMesh` pass it), and `isBuiltInWaterMesh` counts it as built-in water, which the view's graph warms under the passes that draw it. [`e2e/water-template.spec.ts`](../../../e2e/water-template.spec.ts) checks its look scenario by scenario: it draws over the lake and nowhere else, deep water is darker and bluer than shallows, the environment cube warms it, glints saturate toward the sun, and fog mixes the unfogged lake toward the fog colour by Babylon PBR's rule. The starter graph `createWaterMaterialDocument` (shader-graph) draws the built-in look from the nodes, which share its formulas with built-in shading (`subsurfaceSource`, `fresnelSource`, `reflectionKeepSource`, `transmittanceSource` with `waterAbsorption`, the body light `sceneWaterBodyLight`, built-in's `slateWaterLight.w`, and the shore and contact foam `edgeFoamHelpers`, which the Water Foam block reads from the Water Waves block's hidden `edgeTurbulence` output, in `water-material.ts`; both flow their foam noise by the current plus `waterFoamDrift`, the downwind drift along Wave Direction, bound in built-in `slateWaterMotion.yz` and `slateWaterClock.yz`), so keep them in step: a river drawn by the starter that ends inside a built-in lake shows any difference as a seam where ownership hands over. Water meshes never cast shadows (`neverCastsShadows`).
- Grid geometry (except Global Water Volume and a spectrum Ocean) is world-anchored and never depends on the camera. A spectrum Ocean grades its grid around the camera (`oceanBudget`, capped by `WATER_OCEAN_CELL_BUDGET`) and rebuilds it when the camera moves `OCEAN_RECENTRE_SHARE` of the dense region. The worker's `WaterWorld` keeps step and script-query evaluations in separate states.
- Object contacts ([`water-contact-field.ts`](../../../packages/render/src/water-contact-field.ts)): `WaterContactField` is a per-surface, CPU-built, height-aware signed-distance texture (four layers across the wave envelope). Waves never rebake it; objects, the surface and the envelope do. Contact Resolution caps its cells per side (Low 256, Medium 512, High and Ultra 1024).
- Contact cost cap: `WATER_CONTACT_FRAME_BUDGET_MS` bounds window rebuilds per scene and frame, across surfaces (`WaterContactField.drain`). A moved object queues only the window its movement can change (its slice bounds before and after, grown by the contact range); windows that overlap merge and keep their age, and a cell keeps its last result until its window is built. Order: seen before unseen, nearer before farther, any window waiting past `OVERDUE_MS` first (oldest first), and always at least one window per frame, so none starves. Windows past 64 cells a side are cut into blocks, so a frame overshoots the cap by at most one block. Cadence falls with distance and view: a seen window waits 0 to `FAR_MAX_MS` before it runs (ramping from `FAR_START` to `FAR_END` metres from the nearest camera), an unseen one `OFFSCREEN_MS`, which coalesces bursts of moves; surfaces no camera sees skip their contact update altogether (`updateSceneWater`).
- Full rebuilds (first build, `force`, reshaped body, changed envelope, range or Contact Resolution, a changed cell size) run at once but are counted against the frame. An object that outgrows the allocation carries the kept cells over to the new one (same lattice) and queues only what changed; a moved surface re-cuts every cell at most every `SURFACE_MOVE_MS` as one queued window.
- No duplicate contact work between bodies: a window in which no body draws the surface is not built (`WaterFieldSurface.draws`: a blending neighbour owns the water there, as under an Ocean over Global Water Volume) and stays queued until `drawStamp` (the blend index revision) changes. It samples each window's centre and corners and treats any point the blend cannot place as drawn. Initial and forced builds still cover every cell.
