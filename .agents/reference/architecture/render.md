# Render

Contributor reference for Haptic's main-thread Babylon renderer: Engine ownership, the frame path, resources, lighting, Play presentation, feature owners and the Babylon 9.29 workarounds that must survive upgrades.

## Ownership and boundaries

| Area | Owner |
| --- | --- |
| Every Babylon object (Engine, Scenes, materials, textures, FrameGraphs, particles, audio voices) | [`packages/render/src/`](../../../packages/render/src/) (`@haptic/render`) |
| Engine/session construction | [`create-engine.ts`](../../../packages/render/src/create-engine.ts) (`createEngine`, `createAppEngine`; handle and option types in `create-engine-types.ts`, editor viewport camera, gizmos, handles and gestures in `editor-viewport-tools.ts`, Play pointer, touch, wheel and key input in `play-game-input.ts`, per-slot outlines, deformers, fog volumes, reflection probes and area lights in `play-visual-bindings.ts`, e2e mesh readouts in `play-handle-inspection.ts`), [`apps/editor/src/lib/project-engine.ts`](../../../apps/editor/src/lib/project-engine.ts) (`createProjectEngineSession`), [`backend-engine-session.ts`](../../../packages/render/src/backend-engine-session.ts), [`webgpu-engine.ts`](../../../packages/render/src/webgpu-engine.ts) |
| Render path, color pipeline, scalability, shadow presets (Babylon-free) | [`packages/core/src/`](../../../packages/core/src/) (`render-path.ts`, `render-effects.ts`, `scalability.ts`, `shadows.ts`, `render-setting-ownership.ts`) |
| Water/cable/wave math shared with the worker | [`packages/core/src/`](../../../packages/core/src/) (`water.ts`, `water-blend.ts`, `cable-simulation.ts`), [`packages/runtime/src/water-world.ts`](../../../packages/runtime/src/water-world.ts) |

- The game worker ([`packages/runtime/`](../../../packages/runtime/)) never imports Babylon. It sends render commands (`assignMesh`, `assignMaterial`, `assignParticle`, `debugDraw`, …) and snapshot buffers through [`packages/bridge/`](../../../packages/bridge/); render applies them.
- UI packages (`ui`, `editor-kit`, `graph-ui`) never import Babylon (ESLint `boundary/ui-packages`); they talk through the engine command bus.
- Babylon-free IR packages (`shader-graph`, `particle-graph`, `assets`) own schemas; render lowers or applies them. Never store Babylon serialization as an asset payload.
- Construct `Texture` only in [`resource-cache.ts`](../../../packages/render/src/resource-cache.ts) (ESLint `boundary/render-texture-cache`).
- The game HUD / UserInterface system is removed; Print HUD is DOM (`print-hud` in core). SceneLayers are the only in-game UI path ([scene-layers.md](scene-layers.md)).

## One Engine per project

- One project Engine on a hidden constructor canvas. **Never create a second WebGL/WebGPU context** (context caps). Scene viewport and Play bind visible canvases with `registerView(canvas, undefined, true)` and present as below; Material/Model/Animation/Skeleton/Particle/Prefab previews and thumbnails render to an RTT and blit (`createRttCanvasBlitter`, `flipReadPixelsRgba` in [`flip-read-pixels.ts`](../../../packages/render/src/flip-read-pixels.ts)). Editor code obtains it with `ensureSharedEngine`.
- Only exception: Preview Build's iframe (its own cold Engine). Do not add preview Engines.
- Previews must not `registerView` or `scene.render()` to the default framebuffer; Scene/Play own it. Do not move the Scene viewport to an RTT: Play blits from the Scene Engine framebuffer.
- View presentation ([`direct-view-presentation.ts`](../../../packages/render/src/direct-view-presentation.ts), driven by [`registered-view-admission.ts`](../../../packages/render/src/registered-view-admission.ts)): while exactly one enabled registered view has a layout box (`viewCanvasHasLayoutBox`; a hidden dock tab's view stays enabled but is neither admitted nor counted), the Engine canvas itself is placed over that view's canvas (same box at device-pixel offsets, `pointer-events: none`, `aria-hidden`) and shown, with no per-frame copy (on WebKit a copy is a CPU blit with a CPU/GPU sync). Input, picking (`mapCanvasPointer`, GPU pick, CPU ray) and gizmos keep using the view canvas, whose bitmap keeps the presented size. Two or more such views, a view canvas in another document (a popout window), WebGL1, a multisampled default framebuffer or WebGPU main pass, or `setDirectViewPresentationEnabled(false)` copy the Engine canvas into each view's 2D canvas instead. Only the editor's project Engine presents directly, on either backend: its session is created with `presentViewsDirectly` (`createProjectEngineSession`; checked per frame through `Presentation.allowDirect`). The exported player and Preview Build run their own Engine session, which copies, because the player and its pixel checks read the view canvas.
- Z-order: the placed Engine canvas is the view canvas's next sibling, positioned absolutely with no `z-index`. An absolutely positioned overlay that comes before the view canvas in the DOM and has no `z-index` now paints under the Engine canvas; give viewport overlays a `z-index` or place them after the view canvas.
- Direct held frames (WebGL2): each coherent frame blits the default framebuffer into the view's held renderbuffer; an incoherent frame, a view step that resized the buffer, or an `engine.setSize` outside a view step, blits it back before the browser presents. A step whose loop declined to draw (`Presentation.dirty`, render on demand) blits nothing: the default framebuffer is preserved. A view that stops being covered (another sole view, the copy fallback, release) gets its held image in its own canvas once, so it keeps its last frame. Releasing a view untracks its canvas, and parking a disposed Engine's canvas removes it instead of returning it to the document. While a view is covered, nothing may draw to the default framebuffer outside that view's step. Test builds write the presented image into a covered view canvas before `drawImage`, `getImageData`, `toDataURL`, `toBlob` or `createImageBitmap` read it (`installDirectViewReadSync`).
- WebGPU direct frames ([`webgpu-held-image-store.ts`](../../../packages/render/src/webgpu-held-image-store.ts)): the store touches Babylon only from the first direct step (`engage`), so a copying Engine session keeps stock members. While a view is presented directly, Babylon's main pass renders into one of two owned textures (swap-chain format, canvas size) instead of the canvas texture: `_startMainRenderPass` runs with a `_context` whose `getCurrentTexture()` returns the texture that does not hold the last coherent frame, and `_configureContext` adds `COPY_DST`. A coherent frame flushes, acquires the canvas texture and copies into it; any other frame never acquires the canvas, which keeps showing its last image (no held-image copy back). Main passes outside a direct step (the attachment pass `setSize` runs) also land in the draw target, never on screen; a coherent step must draw the whole backbuffer, as on WebGL2. After a resize or reconfiguration clears the canvas, the held texture is copied back once, unscaled into the top-left corner, until the next coherent frame: a shrink shows a crop of the held frame that fills the view; a grow shows it at its old size with transparent bands to the right and below, where the view canvas shows through. A view that stops being covered gets that overlap region 1:1 (`restoresUnscaled`), which its canvas box stretches. A coherent frame the store cannot present (it turned off while the frame drew, so the frame is in the canvas) is copied like a non-direct step instead of re-showing the held image. Replaced textures are destroyed at the end of their frame (Babylon submits before end-frame observers); disposing the store submits pending work and destroys its textures at once, since no later frame may come; context loss drops them without destroying and re-arms the first-copy check. Fallback: the store creates nothing (copy path) when an internal is missing or MSAA is on (`webGpuPresentationInternals`), and turns itself off, restores `_startMainRenderPass` / `_configureContext` and leaves presentation to copies when the redirected main pass throws (that frame re-renders into the canvas) or binds anything but the owned texture, when Babylon's configure needs more than `context.configure`, or when a validation scope reports that the `COPY_DST` configuration or the first copy failed. That last case also reconfigures the canvas Babylon's way, which clears it: at the store's next `clear` (the presenter has parked the Engine canvas by then), or at once when nothing is presented. A lost device never turns it off. `webgpu-held-image-store.test.ts` pins the Babylon source shapes involved.
- Held images are a fixed presentation cost outside the managed ledger, like the Engine's own framebuffer: one RGBA8 renderbuffer per held view on WebGL2, two canvas-size swap-chain-format textures on WebGPU (4 bytes per pixel each, about 22 MB apiece at 2732×2048). They exist while a view is presented directly and go when presentation copies or the view is released.
- View canvases take their 2D context with `VIEW_CANVAS_2D_ATTRIBUTES` (`willReadFrequently: false`, [`registered-view-admission.ts`](../../../packages/render/src/registered-view-admission.ts)), and any 2D canvas the page reads back (`getImageData`, e.g. glyph rasterization in [`text2d-bitmap.ts`](../../../packages/render/src/text2d-bitmap.ts)) declares `willReadFrequently: true`. After readbacks on default 2D canvases, Chromium creates later default contexts unaccelerated, and each view copy then becomes a synchronous GPU readback.
- Closing a Scene tab disposes its Scene and cache retains, never the Engine. Closing the project disposes the Engine.
- Shared views size the framebuffer with `engine.setSize` from the view's CSS box, never `engine.resize()` (it follows the hidden constructor canvas). Resize only on integer CSS size change; ignore zero sizes. A view whose canvas has no layout box (a hidden dock tab) is not admitted: it neither sizes the Engine (that would collapse it to 1×1) nor draws, because a 1×1 frame turns the water scene copy off, re-plans the graph and compiles the variants it then draws.
- Backend is project-wide (`settings.render.gpuBackend`: `auto | webgl2 | webgpu`, normalized default `webgl2`). A Scene never changes backend in place; `createBackendEngineSession` falls back WebGPU→WebGL2 on a fresh canvas. Custom GLSL in the emitted material closure forces WebGL2 (`webGpuMaterialCompatibilityReason`). Backend changes wait for Play/Preview Build to stop; uncertain cleanup blocks any new allocation (never publish a partially released context).
- A lost WebGPU device is never restored in place: Babylon 9.29 rebuilds every resource before its new device exists. [`webgpu-engine.ts`](../../../packages/render/src/webgpu-engine.ts) sets `doNotHandleContextLost` (textures keep no source bytes for a restore), marks the Engine lost, notifies `onContextLostObservable` (Babylon does neither under that flag; the direct presenter relies on it to vacate the Engine canvas and drop its held textures) and settles `BackendEngineSession.deviceLost`. Retry's new Engine gets its own presenter and store. The editor's project Engine controller ([`project-engine.ts`](../../../apps/editor/src/lib/project-engine.ts)) then publishes `deviceLost`, detaches every client and offers Retry. [`project-rendering-recovery.ts`](../../../apps/editor/src/lib/project-rendering-recovery.ts) stops Play or Simulate at once, discarding Simulate's Keep Changes (its capture needs the lost Engine). Preview Build has its own Engine: Retry asks the user to stop it instead. Retry waits, bounded, for the stopped game's release, reports a quarantined or still-releasing game instead of allocating, then creates a new Engine. Release must never depend on a frame of a lost Engine: frame-gated lease releases also settle on context loss. `isUsableEngine` rejects a WebGPU Engine with `_contextWasLost`. WebGL2 keeps Babylon's in-place restore: a lost WebGL2 Engine stays usable, and its views reload on `onContextRestoredObservable`.
- The exported player and Preview Build get the same `doNotHandleContextLost` Engine but no Retry: a lost device stops their drawing for good, and [`player-backend.ts`](../../../apps/player/src/player-backend.ts) reports `render.device.lost` (logged; Preview Build forwards it to the editor).
- A WebGPU request that fails to initialize falls back to WebGL2 with the request unchanged; the controller publishes `webGpuFallbackReason` (not for a material compatibility switch) and the editor shows it once per Engine.
- WebGPU devices request two limits and keep every other at its default (`adapterRequiredLimits` in [`webgpu-engine.ts`](../../../packages/render/src/webgpu-engine.ts), the construction path of every product Engine: the editor's project Engine, Retry after a lost device, the exported player and Preview Build). Neither request exceeds the adapter's value, so the device request cannot be refused for it.
  - `maxInterStageShaderVariables` at the adapter's maximum. Babylon's WGSL fragment inputs always declare `@builtin(front_facing)` and Dawn counts it, so the default 16 leaves 15 user varyings; each cascade and spot shadow adds PBR varyings.
  - `maxUniformBuffersPerShaderStage` at `min(adapter, REQUESTED_UNIFORM_BUFFERS_PER_SHADER_STAGE)` (20), only when the adapter offers more than the default 12. Babylon declares one uniform buffer per light in the vertex shader, so this limit sets `forwardLightBudget` (limit − 4: 8 slots at 12, 16 at the cap). D3D12 adapters report 12 and stay at 8 slots; Metal reports more (44 on Apple GPUs). Babylon's note that the limit "cannot be raised through requiredLimits" holds for D3D12 only. At 8 slots a scene with more lights swaps them by camera distance. A swap keeps every other light's index ([Lighting and shadows](#lighting-and-shadows)); it compiles nothing only between lights with the same slot defines and no shadow map, and otherwise recompiles every lit material for a light set not seen before (a revisited set reuses its Effects). The cap bounds the shader size on large adapters; scenes beyond it use Clustered Forward. Babylon's known light bindings cover 32 lights.
  - `maxSampledTexturesPerShaderStage` and `maxSamplersPerShaderStage` stay at their defaults (16). Plain lights cost no sampler, so extra slots need none; shadow maps, area-light tables and projection textures share `MATERIAL_SAMPLER_RESERVE` headroom (8). Raising only the texture limit would also let pipelines exceed the sampler limit unchecked (one sampler per texture, never read by Babylon's caps), and would admit more shadow maps.
  - Do not use `setMaximumLimits`: it raises every limit and changes budgets such as `forwardLightBudget` without a cap.
- NodeMaterials and built-in helpers (grid, camera bounds, MSDF text) compile in the Engine's native language (GLSL or WGSL). Never depend on a downloaded GLSL→WGSL translator.
- The editor grid is one shader plane under the 3D eye (2D: the camera target), snapped to the major spacing. Each level (minor, major, ×10 steps) fades in per fragment from its on-screen cell size, so zoom, distance and grazing angles blend without a global fade; the plane's distance fade scales with eye height and stays inside the far clip ([`editor-grid.ts`](../../../packages/render/src/editor-grid.ts)).
- Large-world rendering on, context MSAA off; `adaptToDeviceRatio: false`, resolution via `setHardwareScalingLevel` ([`hardware-scaling.ts`](../../../packages/render/src/hardware-scaling.ts)). Engine Settings scaling is both initial level and floor; only the Engine's sole rendering view feeds the dynamic-resolution valve.

## Frame path

- [`framegraph-forward-scene.ts`](../../../packages/render/src/framegraph-forward-scene.ts) (`ForwardSceneFrameGraph`) is the **only** scene draw path; there is no native `Scene.render` fallback. Every Play world, SceneLayer, editor viewport, preview and thumbnail owns a `SceneRenderCoordinator` ([`scene-render-coordinator.ts`](../../../packages/render/src/scene-render-coordinator.ts)). Native shader warm precedes graph preparation; preparation builds and probes, never draws.
- Task order (`taskNames()`): `Forward admitted shadows`, `Clustered light mask` → `Forward clear` → `Forward cull` → geometry tasks when a chain needs them → `Forward objects` → authored post-process, settings effects, shared outlines → `Scene post-process output` (only when a chain exists; then it is the view's only output writer; an auxiliary view without a chain writes its own scene targets in `Capture output`). Water scene copy splits the object pass ([Water](#water)).
- Unsupported, so preparation rejects and nothing draws: frozen active-mesh queues, camera post-processes, rig/multiple cameras, multisample/cube/array or caller-bound targets, custom render functions, unmanaged shadow generators. Editor scenes therefore freeze world matrices and materials but never the active-mesh queue.
- Strict readiness is probed only after invalidation, never per steady frame, except while a variant swap is pending (below). Anything that changes shader-relevant state outside Scene observables must call `markSceneReadinessDirty` ([`scene-readiness-signal.ts`](../../../packages/render/src/scene-readiness-signal.ts)). Readiness probes restore camera, matrices, UBO, viewport and render pass even when callbacks throw.
- Probes never replace a drawn Effect ([`isMeshFrameReady`](../../../packages/render/src/scene-perf.ts)): Babylon's hot swap (`allowShaderHotSwapping`, on by default) keeps a submesh drawing its previous, ready Effect while a newly requested variant compiles, and leaves its defines unprocessed, which is how a probe tells a swap. Replacing it would leave Babylon's frozen and same-frame readiness caches answering for an Effect still compiling. Inside `probeVariantSwaps(true, …)` ([`variant-swaps.ts`](../../../packages/render/src/variant-swaps.ts)) a swapping mesh is ready when its previous Effect binds by its own light layout (`bindsAsPreviousEffect`); everywhere else it waits for its new variant. A swap whose new variant failed to link, every fallback included (none of the Effects the mesh requested is still compiling and one has `getCompilationError()` with `allFallbacksProcessed()`), is over: Babylon draws the previous Effect for good, so the mesh is ready in every probe and the failure is logged once per Effect.
- Probes compile ahead on a parallel-compile driver (`KHR_parallel_shader_compile`; WebGPU has none; SwiftShader has none either, so each request on it links inside the probe that makes it). iPad WebKit WebGL2 exposes it and its new effects stay pending while they link, so the limit below throttles there as on D3D11; its heavy programs finish roughly one after another, and the first draw of each new program still blocks the thread (about 100 ms each in raw WebGL), which no readiness probe sees. Babylon's scans stop at the first unready mesh (ObjectRenderer) and task (`FrameGraph.isReady`), so a pass's variants would link one after another, and each pass only once every earlier pass is ready. While fewer than `COMPILE_AHEAD_LIMIT` effects are pending on the Engine ([`driver-compile.ts`](../../../packages/render/src/driver-compile.ts)), the forward graph also probes the tasks after its first unready one, and the object, transparent and geometry passes and the GPU pick pass the meshes after theirs (`requestCompilesAhead`), including the depth pre-pass that an unready colour variant holds back. The limit counts every compile pending on the Engine (camera-pass probes and previews included) and the probe that crosses it may start several. Each mesh is probed ahead once until its pass is ready, the forward graph's readiness is invalidated (`markReadinessDirty`) or the pick pass drops its objects; the results are discarded, so the in-order scans alone decide readiness.
- Mask, geometry and pick passes are light-neutral ([`light-neutral-tasks.ts`](../../../packages/render/src/light-neutral-tasks.ts)): never toggle `light.shadowEnabled` around a pass; each toggle dirties every material's light defines.
- Blended materials with `needDepthPrePass` draw their depth pre-pass under their own render pass id ([`transparent-depth-pre-pass.ts`](../../../packages/render/src/transparent-depth-pre-pass.ts)); sharing one draw wrapper made frozen materials draw the depth variant as colour.
- Presentation: the visible canvas changes only after a coherent draw; rebuilds, resizes and skipped frames hold the last image. First frame waits for GPU submission (WebGL2 polls an owned fence non-blockingly; never read GL errors before it signals) and the canvas copy.
- WebGPU pipeline deferral ([`webgpu-pipeline-deferral.ts`](../../../packages/render/src/webgpu-pipeline-deferral.ts)): a synchronous `createRenderPipeline` blocks the renderer while the GPU process compiles it (about 200 ms per pipeline on D3D12, serialized), and an Effect is ready on WebGPU as soon as it exists, so readiness probes never see it coming. The world view's coordinator (`deferPipelines`: editor, Play, exported player) opens a scope around its graph render that admits its graph's object passes, their blended depth pre-passes and the shared outline masks (`ownsObjectPass`; post-process draws under the camera's pass are not admitted). Its Full Quality captures and Fast captures open nested scopes only inside that one (`nested`), so under any other owner (previews, thumbnails, SceneLayers) they create pipelines synchronously. In a scope, a pipeline-cache miss starts `createRenderPipelineAsync` (counted in Babylon's miss statistics for that frame) and skips that draw; the coordinator reports the frame not rendered (the view holds its last image, `holdingForPipelines`) and draws nothing more until those pipelines exist, as for a scene that is not ready. A capture that skipped neither publishes nor consumes a manual request; nested skips count in the enclosing view, so it never presents a partial capture. Shadow maps (render once; a map's first draw in a steady frame waits for its casters' pipelines instead, and a drawn map leaves out a new caster's missing pipelines in an `isolated` scope, below), previews, thumbnails, pick passes and SceneLayers keep synchronous creation. After `PIPELINE_DEFERRAL_HOLD_CAP_MS` (2 s) of held frames a view starts no new deferrals (new misses compile synchronously, so a view whose pipelines keep changing still presents), and when no deferred pipeline has finished for `PIPELINE_DEFERRAL_STALL_MS` (10 s) the pending ones compile synchronously at their next draw. A steady frame (`render(false)` of a view that tolerates variant swaps) leaves a miss in a recorded geometry pass out of that pass instead (`omitsGeometryPass`; the scope's `omits`): its pipeline starts creating asynchronously whatever the cap (past the cap, only in a pass that has already drawn in the scope: a miss in one that has not compiles synchronously, as it could hold the view), the scope neither counts nor waits for it, and the frame presents (no `holdingForPipelines`, so no `onPipelineHold`) with that mesh missing from the geometry buffers (a few frames of SSAO, SSR, TAA velocity, volumetric or authored-chain depth and normal artefacts on it) until the pipeline exists. A geometry pass (the spatial effects' and the authored chain's geometry tasks) is recorded once it drew something (`drawsInPass`, counted on draws that drew) in a complete frame of the prepared graph (`noteCompleteFrame`), and forgotten while its spatial stages leave it idle, when the view is invalidated and when the graph is released, so a new graph (an effect or quality change, a resize with spatial effects or an authored chain), a first view of anything and a Fog-Volume-only pass coming back from idle hold as before: their first draws can miss every mesh's pipeline at once. A pass whose every draw in a frame was left out counts them as skips at `close()` too, so its buffers are never presented empty. Validated presentations (loading, a frame report) and auxiliary views omit nothing (a capture publishes what it draws; its skips count in the scene view). A left-out draw's creation also has its own stall clock (`startedAt`): after `PIPELINE_DEFERRAL_STALL_MS` it compiles synchronously at its next draw even while other creations keep the Engine-wide stall from coming, and `waiting()` stops waiting for it once counted at `close()` (`leftOut`), so a pipeline that never arrives cannot leave the mesh out, or hold the view, for good. Each left-out draw's creation still starts and finishes on the shared stall clock (`progressAt`), so a run of spawns or Material changes delays the Engine-wide stall's synchronous fallback for every other wait that reads it: a held view's pending pipelines, and a first shadow map draw waiting for its casters' pipelines until `deferredPipelinesStalled`. An invalidation of the view (a scene switch included) ends its hold and restarts the cap, so the next frame waits for none of the old frame's pipelines. After the first frame a steady frame meets few misses (WebGPU variant swaps below create their pipelines ahead), so the cap and its synchronous fallback bite mainly on loading and first-ready frames. A warm scope (`warm: true`) is for draws made only to create pipelines: every draw in a pass it admits is skipped, a hit as well as a miss; a miss starts `createRenderPipelineAsync` whatever the enclosing scopes' cap or a stall (never synchronously), its skips never count in an enclosing scope, and `warmed()` reports whether every draw found its pipeline. The deferral also records each Effect a draw drew with (`effectDrawn`). A failed asynchronous creation compiles synchronously and reports its error the usual way. Each finished deferred creation is compile progress for every `DriverCompileWatch` on the Engine (`deferredPipelinesSettled`), so loading budgets renew while a held first frame's pipelines arrive; WebKit builds them one at a time (about a second each), async or not. The first-frame completion allowance counts only the pipelines the presented draw still created synchronously. In Play a hold that has lasted `PIPELINE_HOLD_PAUSE_DELAY_MS` (250 ms, counted over rendered frames; a shorter hold pauses nothing and the release is immediate) pauses the game's time like a blocking load: the Engine pauses its own game time, audio and particles while it keeps drawing (`onPipelineHold`), and the host adds the runtime pause reason `rendering` (editor Play and Preview Build through the session boundary; the exported player through its combined `setPaused`). Ticks, physics, scripts, timers and tweens stop; resuming resets the tick accumulator and discards the held interval, so nothing catches up. `rendering` is a time-only pause: hosts do not suppress or neutralize input for it, nothing exits pointer lock, and the runtime keeps queueing input (a held key stays held, a release during the hold lands); any other reason still resets and refuses input, also on top of a hold. The exported player's combined `setPaused` carries `reason: "rendering"` for it. A `rendering`-only pause never pauses the render scheduler or the view's game time from the host side: the frame that finds the pipelines ready must draw to end the hold.
- Variant swaps ([`scene-render-coordinator.ts`](../../../packages/render/src/scene-render-coordinator.ts)): after the first frame, a change to an existing Material's variant never holds the picture or pauses the game. A world view's steady frames (`deferPipelines`, not auxiliary, `render(false)`, on a Scene that binds previous Effects: `sceneBindsPreviousEffects`, a world Scene with the light hooks, uniform buffers and Forward) probe inside `probeVariantSwaps(true, …)`. A light switching on or off or despawning, a shadow lost, light inventory growth, a Forward kind swap or an area emission texture arriving therefore draws the previous variant a few frames longer, bound by its own light layout (Lighting and shadows), instead of holding the last image. Play, the exported player, Preview Build and the editor's world view share this path.
  - Tolerance accepts every hot swap, not only light changes: any define change on an existing Material (`NONUNIFORMSCALING` from a scale animation, a texture arriving) draws the old variant until the new one is ready, which is Babylon's own default (`allowShaderHotSwapping`), bound with the current lights by its own layout.
  - Seat-bound previous Effects (fixed-shape lighting, or ones compiled before the switch was turned off) are never tolerated: `bindSeats` binds seats from the current slot table and has no placeholders for a map or texture a seat lost, so their Materials wait for the new variant as before.
  - While a swap is pending each steady frame probes again (`recheckVariantSwaps`), so a Material adopts its new variant on the first frame that variant is ready, frozen ones included (the editor freezes library Materials, and a frozen NodeMaterial that swapped answers ready without asking again). A swap whose variant failed to link stops this re-probe.
  - A preparation nothing awaits (`requestPreparation`, whether a steady frame or a strict readiness question asked for it, such as Play's end-of-frame check finding a new output size first) probes as the view's steady frames do, since they are what draws once it is done; a strict question asks again afterwards. Until the view has drawn a tolerant steady frame (`warmsVariants`: loading, the load rehearsal, the first presentation) what draws next is a strict frame, so such a preparation probes strictly: a tolerant one would find the swaps a rehearsal step asks for and answer the strict frames that follow "not ready" without probing again. A caller joins a preparation already running for the generation whatever its tolerance: a strict owner (loading, a quality step) that joins a tolerant one still sees a swap in its own `isReady()` and presentation checks, and steady frames that join an owner's strict preparation wait for it, as they wait for the new resources it prepares.
  - Everything else waits for every requested variant: loading presentations (`render(true)`), `isReady()` (loading owners and Play's end-of-frame scalability confirmation, which therefore confirms only once the new variants draw), previews and thumbnails. A probe that tolerates no swap re-probes rather than trust a pass that tolerated one, except right after a tolerant probe (this frame or the last, no input changed) found a swap: then the answer is "not ready" without walking the scene again. The probe records its own tolerance (`collectingEffects`), since a preparation marks its probe after the tolerance scope closed.
  - A tolerated probe clears a submesh's `_areLightsDisposed` before asking it: Babylon otherwise refuses to draw a previous Effect after one of its lights was disposed, and the layout binding never binds a disposed light.
  - A new shadow map (a light starting to cast, a map moved to another light or resumed from standby) holds nothing either. A changed shadow set needs no graph preparation: `ManagedShadowsTask` borrows the controller's maps by reference, so a frame marks readiness dirty (`restaleChangedShadows`) and its probe binds the set as it is. A map awaiting its first draw (`awaitsFirstDraw`, [`shadow-first-draw.ts`](../../../packages/render/src/shadow-first-draw.ts)) samples neutrally (darkness 1, lit) and draws only once every caster's depth variant is ready, checked before its refresh is consumed, since a render-once map drawn without some casters would keep the gap. Meanwhile a tolerant probe requests those depth variants without letting them fail: the task's own map check, the scene probe's render targets, and `Mesh.isReady`'s caster check (`deferCasterChecks` answers ready for every map's generator while it asks one mesh) each count it as a swap, so steady frames re-probe until it draws. A map that has drawn keeps drawing without a caster still compiling (a spawned or newly revealed one): Babylon skips that caster and resets the map's refresh, so the map redraws until it is ready. Receivers swap to their shadowed variants as for any light change; one that adopts before the map draws reads it as lit. No second graph exists, so nothing is held twice. Strict probes (loading, presentations) still wait for every caster. On WebGPU a steady frame's map also waits for its casters' depth pipelines (first shadow map draws, below).
  - Spawns (decision 3).   - Light changes (decision 5). A Play-mode load (editor Play, Preview Build and the exported player) rehearses the light changes gameplay can make, behind its loading screen ([`load-rehearsal.ts`](../../../packages/render/src/load-rehearsal.ts), created by `prewarmSceneMaterials` after the world graph prepares): for every authored light (`authoredLight:`), in scene order, switching it off (or on), and for a lit directional, point or spot light, starting (or stopping) its shadows through the shadow controller with its own priority; and one light of each kind Play may spawn added. Those come from the owned sources' `spawnableLights` ([`spawnable-lights.ts`](../../../packages/render/src/spawnable-lights.ts), `spawnableLightsOfLoad` in the hosts' source preparations: editor Play's startup, session and Scene preparations, the player's startup and acquired sources): the Light and Hemispheric Fill Light components of the prefab templates of the Classes they hold (`spawnableLightsFromScripts`), and, when the load may spawn a Class it does not hold (`spawnsUnseenClasses`), a generic point and spot light, each with and without shadows, in that Class's place (`UNSEEN_CLASS_LIGHTS`; a Spawn Actor's Class is taken never to carry a directional or hemispheric light). A Class the load does not hold is Load On Demand (a Class only a Spawn Actor names arrives with its spawn's preload, after the rehearsal), and the signal is the same in both hosts, erring toward yes: an asset of the load's catalog closure depends (softly) on a Class asset none of its compiled Classes belongs to (editor Play reads the registry's `dependenciesFor`, the player its manifest entries' `dependencies`), or a compiled Class's Spawn Actor (`ctx.spawnActorAsync`, the source text Spawn Actor compiles to) takes its Class from anything but a string naming a Class the load holds (a variable, a pin, an engine base Class). A spawned light's kind is its light type and, for a shadow-capable one, whether it casts shadows (of several templates of a kind, the one with the highest shadow priority): nothing else Play sets on a light changes a receiver's defines, and every map of a type takes the scene's shadow settings. Its step builds it as Play builds a spawned light part (`createPlayLight`), lit (one authored off or dark compiles what switching it on asks for), at the active camera and, for a spot, facing its way, so the Forward budget ranks it nearest and a shadow map ranks it at its own priority, as a spawn at the player, and reaching as far as the shadow distance whatever its template's range: a local map draws only the casters within its light's range, the camera can be far from them (high above, behind a third-person pawn) where a real spawn near the player draws those around it, and a caster no rehearsal map draws has its depth variant compiled (the readiness probe asks every caster's) but not drawn, so a real spawn's map would create its WebGPU pipeline synchronously in the shadow pass and iPad WebKit would pay its first draw then. Range changes no define, and at the camera the stand-in is inside the shadows' relevant area whatever its range; the revert disposes it and the admission restore below puts the slots, maps and light order back. A step that adds a light would raise the light inventory, the most lights the Scene has held, which sizes every lit Material's light capacity (`MAXLIGHTCOUNT`) and never shrinks, so every lit Material would compile again, and so would a later spawn without the rehearsal: a load with spawnable lights reserves one more light than the Scene holds before anything compiles (`reserveSceneLightInventory`, first in `prewarmSceneMaterials`), and the scene's warm-up, the spawnable warm-up, the starting state and every step compile at the capacity a spawn of one light leaves (the reservation first stops a previous load's rehearsal, whose applied stand-in would count among the Scene's lights). The starting state draws first; the rehearsal then waits, without drawing, until no Full Quality capture view that draw created is still preparing (`RenderTargetCaptures.preparing`, `createLoadRehearsal`'s `settled`; a loading frame never publishes a capture, and a view whose preparation failed, such as one the rendering budget refused, retries only from its own draw, so it counts as settled), and draws again while the meshes hold anything undrawn: a view the load first draws, with its own graph and passes, so builds its draw wrappers' defines in the starting state. Built during a step, they would list that step's defines in another order (`MaterialDefines` lists keys in creation order), and since the defines text keys the Effect cache, the starting state would compile and first-draw every Material again for that view once the step is reverted. Then one change at a time: the step is applied and marks readiness dirty, the world presentation's loading frames wait for the view's strict readiness (which requests the step's variants on the meshes' own draw wrappers: the receivers' variants, a new map's casters' depth variants, defines order included), strict frames draw them (a program's first use; on WebGPU the deferral creates their pipelines first and the frame draws once they exist; a shadow pass creates its pipelines synchronously) while the meshes hold an Effect no rehearsal frame drew (a frame counts as drawing the Effects the meshes held when it drew; its post-draw probe can request more, which the next ready frame draws), and the step is reverted. A step whose meshes hold only Effects an earlier rehearsal frame drew is reverted without drawing. A revert also puts back the admission history the step found, taken as it was applied, since both admissions rank by history (an admitted light keeps its place against a slightly nearer one, a shadow map stays where it was admitted for `SHADOW_MIN_RESIDENCY_MS`) and the step made its own (a waiting light took the switched-off light's Forward slot or shadow map): the Forward selection (`forwardLightSelection` / `restoreForwardLightSelection`), then the shadow maps (`SceneShadowController.snapshotAdmission` / `restoreAdmission`, which admits at once as a sync at the snapshot's time would: its camera, its holders as incumbents with their residency, standby only for its holders, their admission times back), then the `scene.lights` order the admissions' exchanges permute (`restoreSceneLightOrder`: the recorded lights' relative order within the places they hold, a light added since keeping its place; it re-sorts the receivers). The shadow restore ranks as of the snapshot, not now: a residency that ran out since moves the map once more at the next sync, from the snapshot's arrangement, which is the order a load without the step reaches; ranked now, the map would move straight from the step's arrangement and its exchange would leave the lights in other slots. A standby map the step released (a map kept for a light that lost its admission) cannot come back, since only a lost admission makes one: the step is reported as `unrestored` (as is any step after whose revert a recorded holder holds no map, a failed reallocation among them), and the scene presents without that map until the light is admitted again. The next admissions then carry on, and the first presented frame admits and draws exactly what a load without the rehearsal does (lit lights, shadow maps, receivers' defines). These frames are drawn in `drawOwner` but never presented (the canvas is cleared, as for the loading frames before them), and each restarts the first-frame timeout. The Effects the meshes hold in the starting state and in each step keep one extra reference until the rehearsal is released (`release`, from `endLoadRehearsal`: the next world load's `sceneLoading`, a superseded or failed presentation) or the Scene is disposed: a reverted shadow step disposes its map, whose depth draw wrappers would otherwise release their Effects, programs and pipelines at the end of that frame. Play keeps one Scene across its loads, so a level's retained Effects must go with the next load. After the rehearsal a rehearsed change compiles nothing, creates no pipeline and draws its variants at once. Budgets: `LOAD_REHEARSAL_STEP_BUDGET` (48) changes, ordered with the first change of each authored kind (light class and change) leading, then the spawned lights, then the other authored changes in scene order. There are at most fourteen authored kinds and seven spawned ones (the generic ones among them), so the budget always keeps every kind and a spawned light takes only a place a repeat would have had: one budget bounds the load's time, and what is reported as `omitted` repeats a rehearsed kind (identical lights' changes usually ask for variants an earlier one compiled); a step whose variants are not ready to draw within `LOAD_REHEARSAL_STEP_MS` (10 s) is reverted, skipped and reported as `timedOut`, unless a shader finished meanwhile: compile progress renews the step's budget as it renews loading waits, on one `DriverCompileWatch` for the whole rehearsal. The whole rehearsal ends `LOAD_REHEARSAL_CEILING_MS` (120 s) after its first frame, its applied step reverted and reported as timed out and the rest as left out, well inside the first presentation's own compile watch (`SCENE_PREPARATION_CEILING_MS`, 300 s from `presentFirstFrame`), whose renewals every rehearsal frame's restart relies on. Combinations (two lights off, a light off while another casts, two lights spawned at once, an actor with two lights: a rehearsal covers one extra light of each kind) are not rehearsed: their count grows exponentially. Nor are a spawned light of a kind neither a held Class nor the generic set carries (a directional or hemispheric light or a rectangular area light of a Class loaded on demand, one a script adds to a held Class's actor), a spawn that displaces another light than its stand-in did (far from the camera, with the Forward budget or the local shadow maps full), the spawned actor's own meshes against its light (fresh meshes, its invisible origin and light helper included, which the camera pass's scene probe prepares with that light among theirs while the spawnable warm-up compiled them without it: they compile at the spawn, a visible one hidden until ready), or other runtime state changes (a Material swapped by a script, scale animations, render settings, quality steps). `loadRehearsalStats()` reports the steps, those that drew, those it could not fully restore, the Effects compiled (new Engine cache entries), the WebGPU pipelines created (Babylon's cache misses) and its duration; the FeatureTest performance route records it per scene. The editor's world view and SceneLayers do not rehearse.

Once the view draws steady frames (`ForwardSceneFrameGraph.warmsVariants`, cleared by an invalidation), an Effect its readiness rounds request (strict ones included: Play's end-of-frame question often asks first) that no draw has drawn with (`effectDrawn`) is cold: it reports not ready in the view's main object pass and blended depth pre-pass (`registerPipelineWarmPasses`), so Babylon's hot swap keeps the previous Effect and a spawn stays hidden; in other passes (the camera's probe pass, shadow maps, geometry passes, whose misses a steady frame leaves out instead: WebGPU pipeline deferral above) it is ready at once. A caster stays new until a real draw of the map has drawn it whole; a drawn caster keeps drawing, a depth variant of its own it has not drawn included (a Material swap whose colour variant is ready, a mesh's first instances), which its draw still creates synchronously, since leaving it out would drop a shadow the map holds. The wait ends at the deferral's stall: past the Engine's stall, or `PIPELINE_DEFERRAL_STALL_MS` after its own creation started while other creations keep the Engine progressing (as for a left-out geometry draw), the next draw compiles the pipeline synchronously; the view never holds. A frame that may not wait (strict frames, one that publishes a manual capture) redraws a map that left casters out (`leavesOutCasters`) with all of them, creating their pipelines in the draw, and a manual Fast capture that would publish such a map waits one frame for that, as for a held first draw (a light switched off or casting none counts for neither). A caster no longer listed is forgotten, so a pipeline that arrives or never does keeps no map drawing.

- Compile hold (any backend): strict readiness presents only when ready, so a wait the cases above do not cover (a WebGPU pipeline, a strict presentation) leaves the canvas on its last image while the driver links the new effects.   - It starts at a frame not drawn because the scene probe failed, or the graph is still preparing or probing its passes' variants, while one of the view's own effects is pending on the driver: the Effects its readiness probes requested through `createEffect` (`requestedEffects` of the forward graph, filled by [`effect-requests.ts`](../../../packages/render/src/effect-requests.ts) inside `isReady`, `isOutlineReady` and the scene probe), so a preview's, thumbnail's or Custom GLSL probe's compile on the shared Engine never counts. Effects built outside those probes (a task's, while the graph is built) are not attributed. It then lasts until a frame draws, even after the effects finished, so the game does not resume under a frozen picture. A wait that compiles nothing from the start holds the image only: a graph rebuilt for a resize or a resolution step, a texture still decoding, and a link that completes inside the call (SwiftShader, which has no parallel compile) leave nothing pending. iPad WebKit WebGL2 keeps new effects pending while they link, so it holds; a draw's first use of a new program still blocks its thread, which no hold covers.

A drawn frame, a throw, no camera, an invalidation, disposal, a latched preparation failure or unsupported scene (`status.reason`), and a skipped draw that is not a readiness wait (the graph refusing a paused redraw) all end it. `createEngine`'s `dispose` releases a hold it still reports (`onPipelineHold(false)`). A loading first frame never raises it: `drawOwner` calls the world draw only once `isReady()`, and the load already pauses.

The report ends, with the image still held, when nothing is left to wait for: an effect of the run reports a compilation error (immediately), none of the view's effects was pending and no preparation ran for `COMPILE_HOLD_STALL_MS` (10 s, the analogue of `PIPELINE_DEFERRAL_STALL_MS`), or `SCENE_DRIVER_COMPILE_TIMEOUT_MS` (60 s) passed since it began (a hung link). - Loading budgets ([`stall-deadline.ts`](../../../packages/render/src/stall-deadline.ts)): shader warm stall 4 s, first frame 20 s, driver compile 60 s, and `SCENE_PREPARATION_CEILING_MS` (300 s). They measure stalls, not duration: when one expires, `DriverCompileWatch` ([`driver-compile.ts`](../../../packages/render/src/driver-compile.ts)) renews it for compile progress since its last renewal, which is an Engine effect key that became ready (once per key: a released variant compiled again is none) or a parallel-compile driver's pending set that changed or has been pending for under 60 s. Finished keys are the only sign where links are synchronous (SwiftShader has no `KHR_parallel_shader_compile`, so Babylon's completion check in the Effect constructor already finds each program linked) and on WebGPU, whose effects are ready once created. iPad WebKit WebGL2 renews through the pending set like D3D11: its new effects stay pending until the link completes. Progress is per Engine: anything compiling on the shared Engine renews every wait on it, which is why the editor's thumbnail queue pauses while a blocking scene load (not a rendering update) is open ([asset-registry.md](asset-registry.md#thumbnails)). It is checked only at expiry, so a stuck wait fails between one and two bounds after its last progress; a preparation stuck in an invalidation loop whose first build compiled anything fails up to 60 s later than without progress (one renewal of the total bound). A watch shared by sequential waits (one per thumbnail capture or model instance) starts each wait from fresh progress (`restart`, through `renewOnCompileProgress`). No watch renews from its ceiling, 300 s after its wait began whatever was credited, so a wait that keeps compiling and never becomes ready still ends. The watch renews the shader-warm, material-texture (an RGBD decode, such as the BRDF texture's, waits for its post-process effect to compile), first-frame and model material waits; graph preparation: `SceneRenderCoordinator.prepare` (10 s per generation and 60 s across invalidation restarts, both renewed; the ceiling is checked at every expiry check) and the forward graph's readiness loop (10 s, with its own ceiling), each creating its watch after its first presentation-fence wait, because a watch asks every Engine effect for readiness; and, through `createHeldThreadBound`'s `renew`, the preview, thumbnail, `prewarmMaterial` and Custom GLSL waits below. Their timeout messages end with the watch's counts (variants compiled while waiting, still compiling and on the Engine, and whether the extension is exposed), which the Scene Load Report prints. A validated first draw's GPU completion has no progress signal: WebGPU builds every render pipeline that draw created in the GPU queue, inside its submitted-work wait, so the budget is 60 s plus `SCENE_PIPELINE_COMPLETION_ALLOWANCE_MS` (2 s) per pipeline it created (`WebGPUCacheRenderPipeline.NumCacheMiss` across the submission), at most the ceiling (`firstFrameCompletionMs`); its expiry names that count. WebGL2 counts none. The two first-frame waits add up: on WebGPU a load can spend up to the 300 s renewable wait for a validated draw and then up to another 300 s for that draw's completion, about 600 s in all.
- Held threads: a synchronous link also advances the wall clock, and so does a draw's first use of a new program on iPad WebKit WebGL2, where probes return before their links complete. Each credit has a `SCENE_THREAD_HELD_BUDGET_MS` budget, one per `prepare` call for the coordinator and one per readiness loop (`graph.prepare` call) for the graph. A gap is credited whatever caused it: in a hidden page, whose timers browsers align to a second or more, the coordinator's bound is credited, while the graph loop's, which counts the wall time outside its probes, still ends a never-ready preparation. ## Loading and readiness

- Play and the exported player share `createSceneLoadReadiness` ([`scene-load-readiness.ts`](../../../packages/render/src/scene-load-readiness.ts)): `sceneLoading` opens a transaction with a monotonic load ID, `sceneRealized` closes the worker's assignment batch, then models, sample-ready textures, shader warm and first-frame presentation complete before `sceneModelsReady` acknowledges that ID. - Editor Play shows the loading dialog; Preview Build and exported players show no host loading UI (games author loading with SceneLayers) and only mirror phase/progress on `data-scene-load-*` attributes.
- Asset sources are scoped: Scene catalogs, `EngineHandle.acquireSceneSources` and script load handles acquire through one loader; unread deferred scenes stay unread. Source/CPU budgets and GPU budgets are separate.
- Native work (model decode/LOD, audio decode, cold texture/material/font preparation) shares one admission queue per Engine (`nativePreparationForEngine`, [`native-preparation.ts`](../../../packages/render/src/native-preparation.ts); defaults 2 concurrent, 64 MiB temporary). Priority order: gameplay (High), preload (Normal), background (Low). Later commands for a slot wait behind its cold assignment and apply in order.
- Editor blocking loads realize in cooperative chunks (`runSceneWork`; yield after about 8 ms or 256 steps). Hidden Scene tabs defer construction until their canvas has a nonzero size.
- A world load compiles each lit Material once, against its final lighting, in the load's warm-up (`prewarmSceneMaterials`) and graph probes. Model and foliage instances that publish during the load compile nothing (`holdSceneInstanceCompiles` in [`glb-anim.ts`](../../../packages/render/src/glb-anim.ts); `prepareInstanceMaterials` still admits their textures): realization starts model loads before it creates the lights, fog and shadow maps, a new Material's light capacity is set at the warm-up's `syncSceneLighting`, and an unpublished instance is not yet a shadow receiver, so their compiles built variants the first frame never draws. The hold lasts from the editor's `loadSceneAsync` (while its generation is current) or Play's `sceneLoading` (while that load is) until the world warm-up starts or the load fails (the editor load rejecting, `sceneLoadFailed` reaching the Play Engine); instances published outside a load (drops, spawns, streams, foliage edits) compile before they publish, in the variants Babylon draws them with (next bullet).
- The warm-up (`prewarmMeshMaterials`) and `prepareInstanceMaterials` compile each mesh only in the variants Babylon draws it with (`drawnMaterialVariants`, [`drawn-variants.ts`](../../../packages/render/src/drawn-variants.ts)): plain, plus instanced for a mesh with instances, only instanced for a thin-instanced mesh (foliage), and nothing for a mesh without vertices (empty roots, model placeholders, geometry that arrives later, which the graph probes compile).
- Owned unlit editor helpers built on `StandardMaterial` (collider dashes, volume fills, nav mesh fill, billboards, the camera model, pivot markers) carry `HelperProgramPlugin` ([`helper-program.ts`](../../../packages/render/src/helper-program.ts), `shareHelperProgram`). Babylon links one program per Effect key, and a mesh's non-uniform scale (`NONUNIFORMSCALING`) or a material's transparency mode (`ALPHATEST_AFTERALLALPHACOMPUTATIONS`) changed the key without changing the source, so one shader linked once per combination in every pass that draws helpers. The plugin pins each define off only while the program cannot read it (`NORMAL` and `ALPHATEST` absent); a new unlit helper material calls `shareHelperProgram`. The class is in the `nativePlugins` of `clustered-material-policy.ts` and `shadow-material-policy.ts`: an unlisted plugin class sends the scene to Forward and takes the material out of GPU picking's stock-vertex-stage set.
- Particle preparation follows the held-thread and compile-progress rules of the Loading budgets and Held threads bullets above. `boundParticlePreparation` ([`particle-system-factory.ts`](../../../packages/render/src/particle-system-factory.ts)) bounds `ParticleService`'s wait for a bundle's slots (one per preparation; expiry fails the bundle) and `bindParticleMaterial`'s wait for the Material's build and effect (one per bind; expiry rejects and the service skips the slot). Each is a `createHeldThreadBound` of the 4 s shader-warm bound, checked every 16 ms (well under `SCENE_THREAD_HELD_MS`, so a longer gap between checks is a held thread), with its own `HeldThreadBudget` and `DriverCompileWatch`: a synchronous link that outlasts the bound is not charged, a wait that keeps finishing shaders renews up to `SCENE_PREPARATION_CEILING_MS`, and one that never readies fails after its bound plus the credited time. The Material build can outlast the bound (a Custom GLSL particle Material links a probe effect first). Progress is per Engine, so unrelated compiles on the shared Engine renew a preview's preparation too. Timeout messages end with the watch's counts and keep the words "timed out" (the particle proofs in `e2e/` retry on them).

## Rendering settings

- Render path is project-owned `settings.render.renderPath` (`auto | forward | clusteredForward`, default `forward`). A per-Engine session request (`EngineHandle.setRenderPath`, console `renderpath`) overrides it and is never persisted; Scene documents carry no path. Auto/clustered admission: [`scene-render-path.ts`](../../../packages/render/src/scene-render-path.ts), [`clustered-material-policy.ts`](../../../packages/render/src/clustered-material-policy.ts). Owned unlit helper ShaderMaterials must call `registerClusteredUnlitMaterial` or they force Forward.
- `settings.render.mode` is PBR or CEL. CEL is display-space with hard steps for bands, shadow visibility and highlights; there is no softness or Smooth option. CEL material replacement is event-driven (no per-frame `scene.meshes` scan) and invalidates readiness only when it actually replaces something.
- Real-Time Reflections (SSR) read the geometry pass's reflectivity attachment (rgb F0, a glossiness; `PREPASS_REFLECTIVITY`, requested only by `spatial-effects-graph.ts`). Writers: PBR (Babylon; unlit writes zero), lit graph Materials (`GeometrySurfaceOutputBlock`: base color, metallic, roughness; unlit writes zero), Standard only with `SPECULARTERM` ([`standard-reflectivity.ts`](../../../packages/render/src/standard-reflectivity.ts): Babylon wrote every Standard surface's specular color, white by default, so unlit sprites and quads mirrored), and the CEL adapter (`celSourceReflectivity`: the source's factors through `slateCelReflectivity` and `slateCelTextures.w`; texture-driven metalness, specular or reflectivity reads as none unless CEL Reflection Textures apply). CEL runs SSR only with `cel.reflectionsEnabled` (default off; `celReflections` in `planSceneEffects`); AO stays PBR-only. `SceneRendering.celReflections` (CEL with reflections in the plan) is published to `listeners` with the mode, once per change and after the replan; CEL graph surfaces connect their CEL output's base color, metallic and roughness reflectivity inputs only then (one output: a NodeMaterial allows a single `CelLightBlock`, and `attachedBlocks` keeps every block a build reached), because those inputs' textures would otherwise bind on every flat CEL draw. `cel.reflectionTexturesEnabled` (default off) sets `SceneRendering.celReflectionTextures` (only with `celReflections`; published the same way): the native adapter then puts its source's map (`celSourceReflectivityMap`: PBR metallic workflow `metallicTexture` with Babylon's metal/roughness channel flags, specular-glossiness `reflectivityTexture`, Standard `specularTexture`; none for unlit sources) in its own `specularTexture` slot, so Babylon's `SPECULAR` define, UV set and texture matrix apply, and binds `slateCelReflectivityMetal` / `Gloss` / `Map`. The `slateCel` shaders declare that slot's varying and sampler only under `PREPASS_REFLECTIVITY` and drop the forward specular-map reads, so only the geometry pass samples it; with the setting off or reflections not running the slot is empty and every variant's defines are the factor-only ones. The adapter follows the flag in `isReadyForSubMesh` (readiness is cached per render id, so a change applies from the next frame; a frozen adapter is marked dirty). Graph Materials ignore the setting: their Metallic and Roughness inputs, textured or not, connect whenever `celReflections` is set.
- Color pipeline (`render.effects.colorPipeline`, v1): `legacyDisplay` default; `sceneLinear` only for PBR. Babylon's image-processing pass is the only display encoding; each Display Color task owns its own `ImageProcessingConfiguration` (sharing the Scene's corrupts per-material processing). ACES hue shifts are expected; `neutral` holds hues.
- Scalability categories, presets and the ownership registry are in core; `ScalabilitySession` holds non-persistent session overrides. Readback separates requested from effective; effective changes only after a renderer-confirmed ready frame. Backend changes reject with `restartRequired`. Artistic settings (CEL, IBL, outlines, render path, output size) never mark a category Custom. Tiers are authored targets (Low budget Android, Medium A16, High desktop, Ultra high-end), not qualifications.

## Lighting and shadows

- Conventional light slots are bounded by device uniform-block limits before shaders compile ([`forward-light-budget.ts`](../../../packages/render/src/forward-light-budget.ts), [`scene-lighting.ts`](../../../packages/render/src/scene-lighting.ts); three blocks reserved). Admission keeps sun/fill, then priority, camera distance with incumbent bonus, stable identity. It also keeps the admitted local lights' mix of slot kinds (`forwardSlotClass`: a bound shadow map, then type and the other per-light defines; a forward-dropped light keeps its standby map and so its kind, while a shadow caster first admitted without a map counts as unshadowed until its map exists), because a new mix compiles a new shader for every lit material the first time: when the ranked selection would change the mix, each kind first refills the places it held (`keepAdmittedSlotKinds` in [`light-policy.ts`](../../../packages/render/src/light-policy.ts)), unless that keeps a light more than `FORWARD_KIND_CHANGE_DISTANCE_RATIO` (1.25) times farther from the camera than the nearest light the ranked selection admits instead; so a nearer light of another kind can stay off until it is that much nearer. The places come from the whole previous selection, also lights no longer eligible, so a disabled spot hands its place to the next spot rather than a point. Going back needs the same margin. Clustered Forward and `requireLightSorting` scenes (Babylon sets it for any nonzero light `renderPriority`) rank only. Exclusion never changes authored Enabled. A lit material's `maxSimultaneousLights` (and so `MAXLIGHTCOUNT`, part of every lit Effect key) is `min(slots, max(4, light inventory))`, where the inventory is the most lights the Scene has held, enabled or not; it never shrinks. Under fixed-shape lighting it is at least the layout's seats, which per-kind high-water marks can make larger than that (every seat must expand). It is at least the admitted set, which the slots, the scalability local-light budget (plus sun/fill) and the sampler headroom all bound. Enabling or disabling lights and budget swaps leave it unchanged, so a receiver whose own lights are unchanged keeps its Effect; a light beyond the inventory dirties every lit material once. Babylon strips the unused copies of each per-light include, so a larger value compiles the same source, but it expands them per Effect in JS first: do not pad it to the slot count. WebGPU slots are the granted per-stage uniform buffer limit less four (see [One Engine per project](#one-engine-per-project)).
- Budget swaps keep shader slots ([`forward-light-slots.ts`](../../../packages/render/src/forward-light-slots.ts)): Babylon splices a disabled light out of `mesh.lightSources` and appends an enabled one, which would shift every later light's index and give each lit material new defines. `syncForwardLightPolicy` decides every light before toggling any; each local light the budget admits takes the `scene.lights` position, and the index in every receiver both lights can affect, of one the budget drops (equal slot signature first), so Babylon's resyncs change nothing there. A budget admission without a partner moves to the end of `scene.lights`, where Babylon appends it. Authored Enabled, intensity and parent changes, sun and fill lights, Clustered Forward and `requireLightSorting` scenes keep Babylon's order. An exchange dirties no material (`scene-lighting.ts` accepts it as it does a shadow handoff) only when both lights have equal slot signatures, neither has a shadow map, and every mesh holds both or neither: a mesh only one of them can light loses or gains a light, so its later slots shift. Otherwise the receivers refresh, and the policy then puts the local lights in canonical order (`canonicalizeForwardLightSlots`): within the `scene.lights` positions local lights hold, the enabled ones by slot class (shadow map bound, then receiver signature), then creation, and the unlit ones after them; every receiver out of that order is re-sorted (`sortReceiverLightSources`) and dirtied, unless its re-sort only permutes lights with one slot signature (same defines). A receiver's light defines then depend only on which lights reach it, so a light set the budget returns to (after any chain of exchanges) asks for the Effects it compiled before; without it each different-kind exchange leaves the set in another slot arrangement, a new shader for every lit material. Only budget transitions that refresh receivers anyway reorder: a preserved exchange keeps the arrangement (same class, same defines), and authored changes never trigger it. `lightSources` rebuilds (`addMesh`, `addLight`, `layerMask`) reproduce a mesh's order only while it follows `scene.lights` order, so every lighting refresh in `scene-lighting.ts` (outside Clustered Forward and `requireLightSorting`) re-sorts receivers that an append outside a budget swap left out of it (an authored enable, a re-enabled sun or fill after the local lights), and a re-enabled light asks for the Effects its slot compiled before. Since the policy reorders `scene.lights`, order-sensitive readers (clustered authored order, shadow diagnostics, the limited-lights list) use creation order (`compareLightCreation`, light `uniqueId`).
- Fixed-shape forward lighting is behind an Engine switch, off by default (`setFixedShapeLightingEnabled`, [`fixed-light-admission.ts`](../../../packages/render/src/fixed-light-admission.ts)). It applies to world Scenes (`setFixedShapeLightingWorldScene`, set by `createEngine` for every Scene neither presented through an RTT nor given preview studio lights: editor world view, Play, the exported player and Preview Build) outside Clustered Forward; previews, thumbnails and Prefab Preview stay legacy. It replaces the Forward budget's selection (ranking and `keepAdmittedSlotKinds`) with per-class admission, and native PBR and Standard materials bind lights by seat (below). Slot exchanges, canonical order and toggles still run for the materials that bind through `lightSources` (node materials and the CEL adapter). With the switch off nothing changes: no seat define is set, the seat hooks hand every call to Babylon (and clear seat defines a switch left behind, so the defines text and Effect key are Babylon's own), and the derived light include's seat code sits in `#if` blocks that the shader processor removes. Console `fixedlights` switches it for a Play session (the Play view restores the Engine's state); test builds read `haptic:test-fixed-shape-lighting` from localStorage at Engine creation (perf route `HAPTIC_PERF_FIXED_LIGHTS`) and the viewport test host has `setFixedShapeLighting`.
- Fixed layout (core [`fixed-light-layout.ts`](../../../packages/core/src/fixed-light-layout.ts), Babylon-free): seat classes are data (`FIXED_LIGHT_CLASSES`, canonical order SUN, FILL, SPOT_SHADOW, POINT_SHADOW, LOCAL_SPOT, LOCAL_POINT, AREA), each hosting one light kind, because a seat compiles its kind's code (spot cone math only in spot seats). Each class seats min(cap, inventory): caps per device class from the Forward light budget (WebGL2; WebGPU at the default 8 slots; WebGPU above it, Apple, capped at `RAISED_WEBGPU_FIXED_LIGHT_SEATS`, 16); shadow classes size by shadow casters of their kind, and LOCAL_SPOT and LOCAL_POINT share the remaining slots one seat each in turn for the spots and points the shadow seats leave (the inventory counts spots and points apart). Overflow is type-matched: a shadowed spot beyond its class takes a LOCAL_SPOT seat with the shadow off, a point a LOCAL_POINT seat. Capacity trade: when the slots bind, a light of one kind can be limited while the other kind's seats are empty (a spot never takes a point seat). Local shadow seats stay within the effective `maxLocalLights` and the layout within the lighting sampler headroom, trimmed in `trim` order (area emission, point then spot shadow seats, area seats, the sun's shadow); trimmed casters light unshadowed in LOCAL. The inventory counts every light, enabled or not, and shadow casters (`requestsShadow`) only while scene shadows are on; it never shrinks during the Scene's life (the `MAXLIGHTCOUNT` inventory's lifetime), so toggles, swaps and turning shadows off keep the layout. The layout key (seats, shadow and texture per class, filter, cascades) changes only on inventory growth or a filter, cascade, local-shadow or device change.
- Fixed admission each sync ranks candidates as the legacy budget does and admits them while every admitted light can still have a seat (checked over each set of kinds), within the scalability local lights and the bound textures' samplers ([`fixed-light-seats.ts`](../../../packages/render/src/fixed-light-seats.ts)). A light keeps its seat while it stays legal; a light holding an admitted map (`SceneShadowController.generator`, so as of the controller's last sync) takes a seat of its map's shadow class, displacing a light without such a map or a lower-ranked one that did not shadow there; the rest take seats in classes without shadow seating, then free shadow seats with the shadow off. Lights left out are forward-excluded like budget-limited ones (yellow billboard, standby maps) and listed with their reason in `sceneLightingLimits`. `fixedLightSlotTable(scene)` exposes every seat (class, index, light, shadow active) with a revision for the binding phase. While the switch is on, the Material editor's Compiler Results warns (`material.samplerBudget`) when a lit Material binds more samplers than `fixedShapeMaterialSamplerBudget` (the material reserve) leaves it.
- Seat binding ([`fixed-light-binding.ts`](../../../packages/render/src/fixed-light-binding.ts), [`fixed-light-shader.ts`](../../../packages/render/src/fixed-light-shader.ts)): `setFixedShapeLightingWorldScene` installs `scene._materialLightHooks`, which the patched `PrepareDefinesForLights`, `BindLights` and `AreLightsTexturesReady` ask first. For `PBRMaterialDefines` / `StandardMaterialDefines` on an Engine with uniform buffers, seat j is shader light j: `LIGHTj`, its class's one type define and `SLATE_FIXED_LIGHTj`, prepared through Babylon's `PrepareDefinesForLight` with a stand-in light per kind (default falloff and lightmap mode, white specular, no shadow), plus `SLATE_FIXED_LIGHTS`, `MAXLIGHTCOUNT` = layout seats and `LIGHTCOUNT` = seats prepared, so the Effect key depends on the layout only. Binding follows the drawn Effect's own defines (parsed once per Effect): each seat binds its light through `Light._bindLight` when the seat's light reaches the mesh (`isEnabled() && canAffectMesh`), else a per-Engine, per-kind empty-seat buffer (the kind's own uniform layout, black, range -1, finite stand-in data far overhead). A seat is active while `vLightDiffuse.a` (the range `_bindLight` writes) is not negative. The guard is compile-time (`setFixedShapeLightGuard`, per Engine): `multiply` (default, no branch) evaluates every seat and multiplies `shadow`, which scales every contribution, by the active flag, and adds it to `numLights`, so an empty seat adds exactly zero; `branch` (`SLATE_FIXED_LIGHT_BRANCH`) runs each seat behind a uniform branch. A light switching on or off, moving to another seat of its class or replaced by a new light of its class changes bindings only, never an Effect. Not yet fixed: a shadow-class seat (and the sun's seat when its class is shadowed) adds its light's `SHADOW*` defines while that light's shadow is active there (shadow sampling follows the light, so gaining or losing it recompiles, as on the legacy path; a same-settings hand-off within the class does not), and AREA seats keep Babylon's per-light defines, packed in seat order. Node materials (graph lighting blocks) and the CEL adapter (`CelMaterial.isReadyForSubMesh` runs inside `withLegacyLightDefines`) keep the `lightSources` path in the same Scene. `syncSceneLighting` refreshes lit materials when the switch, layout, guard or a shadowed or area seat's light, shadow or texture changes (`fixedLightDefinesSignature`); lights moving through unshadowed seats only rebind.
- Previous-Effect binding (the same hooks, `bindLights`): a swapping Material draws an Effect built for earlier lights. Light blocks differ in size by kind (directional smallest, then point and hemispheric, then spot), so Babylon's `BindLights` (`lightSources[i]` into slot i) would bind another kind's smaller buffer (WebGL2 INVALID_OPERATION, "a uniform buffer that is too small"; a WebGPU validation error), misread an equal-size one, or leave a slot or sampler on whatever its binding point or unit last held. The hook parses each Babylon-path Effect's light layout once (per shader light: kind, shadow sampling, light textures). When the mesh's lights no longer match it, it binds by that layout: each shader light takes the mesh's light at its index if that light is of its kind, else the next unused light of its kind, else the kind's empty buffer (black, so it adds nothing; an area one is a small quad far overhead). A shadow map or light texture the bound light cannot supply (a released map, changed cascades or filter, a receiver no longer receiving) gets a 1×1 placeholder of the sampler's type ([`shadow-sampler-placeholders.ts`](../../../packages/render/src/shadow-sampler-placeholders.ts), allocated once a probe sees a swap, before a frame's passes but after that frame's own readiness probe, the first to see a swap that Forward admission alone started; a swap no probe saw keeps the unit's last texture). Each placeholder is filled once as Babylon clears an empty shadow map (white, depth at the far plane, the map's comparison function, reversed with a reversed depth buffer), so a light whose map is gone still lights: PCF, PCSS and Poisson cube taps find no occluder (an unfilled texture reads zero, an occluder at the light), and white leaves a projection, IES or emission texture without effect. Haptic sets no ESM filter, for which an empty map is zero. A restored WebGL context fills them again. Placeholders rather than deferred generator disposal: `Light.dispose` disposes its own generators, so a despawned caster's map is gone whatever the controller does. Effects with a clustered container keep Babylon's binding; Clustered Forward Scenes never tolerate swaps. When the lights match, Babylon binds as usual.
- Only the first enabled directional light in scene order illuminates.
- Material, lighting, shadow, area-light and water samplers share `MATERIAL_SAMPLER_RESERVE` (8) ([`light-sampler-budget.ts`](../../../packages/render/src/light-sampler-budget.ts)).
- `SceneShadowController` ([`shadow-controller.ts`](../../../packages/render/src/shadow-controller.ts)) owns all shadow maps in editor and Play, including the per-view sun maps of Full Quality captures (`attachView`); the managed bridge renders them unmanaged before `Forward objects`. Local maps render once and refresh on caster revision ([`shadow-map-refresh.ts`](../../../packages/render/src/shadow-map-refresh.ts)); a caster whose content can change without a tracked revision (skinning, morphs, updatable geometry, render hooks, alpha, unknown shaders) keeps every map it reaches drawing each frame. An `InstancedMesh` caches as its source would: its own pose and visibility, its source's geometry, sub-meshes, deformers, material and hooks (`canCacheShadowMaterial` in [`shadow-material-policy.ts`](../../../packages/render/src/shadow-material-policy.ts)), and an instance of a source with levels of detail keeps refreshing; a source with instances caches too. Being an instance, or having instances, does not by itself count as unknown content (an instance is posed by its own world matrix, drawn with its source's parts, and a map culls those parts whole for a mesh with instances): otherwise every map they reach would draw each frame, which on the software WebGPU adapter backs up the queue behind those passes, so later pipeline creations wait and views hold their image. Point/spot maps are pooled `ReusableShadowGenerator`s that retarget or stand by instead of reallocating. A map stands by whether the camera rejected its light (outside the relevant area, budget-limited) or the Forward light budget disabled it (`isForwardLightExcluded`): releasing it disposes the generator, and readmission would rebuild every caster's shadow draw wrappers (recompiling depth Effects that left the cache) and change the managed shadow task's generator set. Standby maps stay bound, so that set does not change. A new map starts neutral like a moved or resumed one (`neutralUntilRendered`), and its darkness returns to 0 when its last face first draws. Shadow maps keep anisotropy 1. Helpers (`isEditorHelperMesh`), skyboxes, debug overlays and water never cast.
- Per-slot receiver defines: each generator's `prepareDefines` sets `SLATE_SHADOW_AUTO{n}` and `SLATE_SHADOW_FADE{n}` (`false` for a non-cascaded map). Babylon resets only its own `SHADOW*{n}` family when a slot's light changes, so a leftover value adds no shader code but changes the defines text, the Effect cache key, and links an identical program again. `trackShadowSlotDefines` ([`shadow-slot-defines.ts`](../../../packages/render/src/shadow-slot-defines.ts)) therefore clears both in `toString` of every defines object a generator has prepared, for any slot without `SHADOW{n}`; a slot's defines depend only on the light now in it, whether a fill took the slot or the light count shrank past it. Any new slot-indexed receiver define joins that list.
- Custom-depth casters (authored WPO, masked and lattice materials use a `ShadowDepthWrapper`) share depth Effects: the patched wrapper keys each depth Effect by its source and defines, not a per-(subMesh, generator) random token, so every caster of one graph, including its private instances, shares one Effect per depth-define set.
  - Each wrapper entry holds one Effect reference and disposes it once (`AuthoredShadowDepthWrapper.retireEntry`), so a shared Effect is released when its last entry retires: mesh, material or wrapper disposal, a define or base-effect change, or its generator's disposal. The vertex array object is released only when the Effect itself dies.
  - `ShadowGenerator.dispose` never reaches a material's wrapper. A wrapper observes the shadow map's `onDisposeObservable` from the first entry it prepares for a generator and retires that generator's entries on every sub-mesh. That covers every disposal path (controller, `Light.dispose`, scene teardown) and a recreated map; a re-created generator acquires new references.
  - `NativeLatticeShadowDepthWrapper` keeps no entries: it delegates to one `AuthoredShadowDepthWrapper` per generation. Stock `ShadowDepthWrapper`, whose define change overwrites `mainDrawWrapper.effect` without disposing it, therefore runs only in tests.
- Directional Auto Bias adapts to the current projection and admitted map size; derived values are never serialized. It adds no normal inset (split normals would open contacts) except for casters marked with `markSmoothNormalShadowCaster` (landscape chunks), which draw with `SMOOTH_CASTER_NORMAL_BIAS_TEXELS` world texels so receiver-plane PCF does not self-shadow concave triangle edges (`shadow-bias.ts`). Point/spot automatic bias is unsupported (authored offsets only). If the owning engine or Babylon's last-created-engine gate rejects cascades, the sun keeps a single map without touching authored settings.
- Sun incidence sets directional shadow quality: a map texel and its PCF kernel stretch by 1 / cos along a face the sun meets at incidence cos, and an overhang's shadow lengthens likewise. The seeded sun (`DEFAULT_SCENE_SUN_POSITION` in [`skybox.ts`](../../../packages/core/src/skybox.ts)) therefore meets faces turned to the default camera at cos 0.6. The Basic 3D Mannequin shadow specs hold the drawn edge to the ray-cast one in metres (`mannequinShadowEdgeError`, [`mannequin-shadow-pixels.ts`](../../../e2e/mannequin-shadow-pixels.ts)); their sample classes scale with texel size and cos, so a grazing sun widens its own tolerance.
- Shadow admission lowers resolution to fit (256 px floor) and retries at half size on allocation failure; it never changes authored values. Quality presets and per-tier ceilings live in core [`shadows.ts`](../../../packages/core/src/shadows.ts).
- Editor light billboards are a status palette, not the light colour: white operating, yellow limited (Forward capacity or missing shadow allocation), red disabled/non-illuminating. Tint multiplies the diffuse texture (emissive would wash it white).
- Membership or shadow changes must dirty frozen materials' light/shadow defines; WebGPU graph materials rebind through [`webgpu-node-material-rebind.ts`](../../../packages/render/src/webgpu-node-material-rebind.ts).
- GPU allocations (shadow, cluster, water, area light, post-process, geometry) reserve in one Engine ledger before construction (`beginManagedRenderAllocation`, [`managed-render-resources.ts`](../../../packages/render/src/managed-render-resources.ts)); WebGPU releases after the end-frame destruction drain or a lost device (`releaseManagedRenderLeaseAfterDisposal`). Uncertain cleanup keeps the lease. Estimates, not measured VRAM. Fixed 1×1 placeholders (the shadow sampler placeholders the volumetric march and previous-Effect binding share, one set per Scene) stay outside the ledger, like held images.
- Rectangular area lights are unshadowed (no generator, light through walls). LTC tables are bundled ([`resources/`](../../../packages/render/src/resources/), CC BY 4.0, no CDN). Emission textures are prepared at authoring time into a versioned derived chunk; gameplay never runs the processor; missing data disables the emitter with a diagnostic.

## Resources

- One `ResourceCache` per Engine (`resourceCacheForEngine`) shared by world, SceneLayer and preview Scenes. Exact-generation leases with idempotent `release()`; reading a held resource never re-acquires. Default 2 GiB accounted ceiling, trims unreferenced entries to 80% ([`perf-ceilings.ts`](../../../packages/render/src/perf-ceilings.ts)); live leases are never evicted; the largest live view cap wins. Geometry is accounted (`GEOMETRY_BYTE_CEILING`) but never evicted.
- Editor Play compares the Engine's texture cache before and after a session; a texture that outlives it is reported with its name, size, native references and ResourceCache entry (`describeEngineTexture`). A texture a live Scene outside the session still references is not Play's to release, so it is not reported: an editor preview opened mid-session (a Class graph's viewport) creates its own default checker and BRDF table on the shared Engine. Ownership decides it, by identity: `internalTexturesHeldByScene` collects what each other Scene in `engine.scenes` registers, its Materials sample and its environment sets (textures built on the Engine, like the ResourceCache's, reach a Scene only through a Material or the environment), and for every render target among them its colour texture, multi render target attachments and depth/stencil texture, which are separate native textures. The session's own Scenes (`EngineHandle.ownedScenes()`: the world Scene and every Scene the SceneLayer compositor built, meaning layer Scenes, output-blit Scenes and retired generations still releasing, captured before disposal) never excuse what they hold, even one that outlived its disposal, and a texture no live Scene references stays a leak. `e2e/simulation-graph-debug.spec.ts` stops a Simulation after a Class graph first opened during it and expects no leak report. `create-engine.play-textures.test.ts` pins the default skybox, default material and sun shadow map to zero retention across cycles; textured materials, models and post-processing are not covered.
- Content identity is the SHA-256 of an immutable installed Blob. Never fragment `blob:` URLs (Babylon escapes the fragment into the identity). Different upload keys (`invertY`, sampling, mips, cube) get separate wrappers from the same Blob.
- KTX2 block-compressed uploads ignore `invertY`, so `prepareTexture` builds them unflipped and flips V on the wrapper (`vScale = -1`, `vOffset = 1`). Samplers must apply the texture matrix. A Babylon change that sets `_invertVScale` for KTX2 would double-flip.
- WebGPU rejects ASTC/BC7 off the 4×4 grid: the patch decodes those Basis KTX2 to RGBA per texture; `configureKtx2DecoderRuntime` must leave `forceRGBA` undefined (not false) so the per-texture value wins. Compressed Textures encode block-aligned except atlases.
- Six-face cubes are created on the Engine, not the Scene; skybox materials null `reflectionTexture` on dispose so Play teardown cannot drop a cached cube. The skybox never calls `createDefaultSkybox`, never sets `scene.environmentTexture`, is not `infiniteDistance`.
- Babylon's cube upload runs when the last face decodes and never checks disposal. A cube released or evicted mid-load (`disposeTexture` in `resource-cache.ts`) drops its wrapper at once but keeps the native texture until that upload settles, bounded by the preparation deadline; disposing it earlier uploads to an unbound target ("no texture bound" warnings, then GL error 1282 at the next presentation).
- Publication of materials, texture parameters and sprite/skybox/model replacements waits for full lease preparation (byte accounting and budget admission). `Texture.isReady()` is not enough: Babylon's error sampler reports ready.
- Replacements are transactional: prepare the successor, keep the working predecessor, publish only on success; generation/owner checks drop late completions; failed requests stay latched until their inputs change.
- `MaterialLibrary` warms a new Material generation for the meshes bound to it only when it replaces a published one: the predecessor stays bound until the successor has compiled for them. A first acquisition warms nothing; its host compiles what it draws (the load's `prewarmSceneMaterials`, readiness probes, or a preview's own prepare-then-bind step), because warming at acquisition runs before the Scene's lighting, fog and transforms are final and builds variants nothing draws. A host that binds at acquisition and captures right after (the asset thumbnail) sets `warmFirstAcquisition`, so a program that cannot link fails the capture through `ready`. So `ready`, `isReady` and `compiledMaterialGuids` mean built with textures admitted, not linked.
- A program the Engine cannot link is reported where its Effect is first created: the load's warm-up rejects naming the Material and mesh, and `material.onError` (compiler `onLinkError`) reports the shader log, without JS frames, as `material.compile.failed` through `onTextureError` / `onMaterialDiagnostic` (`console.warn` when the host takes none). The library then retires the generation: it is disposed, so its meshes fall back to the default Material and readiness can pass, but its entry stays in its map so holders' reference counts carry to the next acquisition of the key. Without that, an unlinkable bound Material never reads ready and the Scene draws nothing, silently. Babylon hands a cached Effect to a second requester without its `onError`, so each compiled material also listens to `onEffectErrorObservable` and matches the Effect's first creator by build id (`nodeMaterial<buildId>`): materials sharing a program (a root, its Instances and per-component copies adopt one build id) retire together. A surface variant (outline mask, depth or normal capture, shadow depth) is a program of its own that its pass cannot draw without, so its link failure reaches the owner the same way, with the log naming the variant, and retires the generation. The owner is found by the entry's current key, which `adoptPreparedInstance` moves from the staging token to the component's, so an adopted copy retires too. A reported failure also drops the program from the compiler's shared-program registry, so a Material compiled after it builds its own Effect (and hears of its failure) instead of adopting the dead build id. A sharer the registry cannot reach would adopt the dead program without hearing of it, so the library latches the failed plan per asset and shading variant, shared by its instance keys (hash and diagnostics): `acquire` and `resolve` of that hash fail at once with the same diagnostics, compile nothing and report nothing again, until the hash changes (an edited graph, function or texture identity), `markDirty`, `forgetFailures` or `releaseScene`; releasing the key does not end it, because the next holder would adopt the same dead program. `forgetFailures` runs by itself when the Scene's receivers bind other lights or shadow maps (`notifySceneReceiversChanged`, [`scene-readiness-signal.ts`](../../../packages/render/src/scene-readiness-signal.ts)): `syncSceneLighting` after a different enabled-light set, shadow layout or light capacity, and every `invalidateShadowReceiverHandoffs` caller in the shadow controller (a map created, released, moved or retuned). A varying or uniform limit can fail a link for that set and not for another, with the plan hash unchanged. A refresh that changes none of them (the retirement's own) keeps the latch. Any failure of the plan itself latches (a build failure, a link failure, a shader error from the replacement warm-up or Custom GLSL's probe). A texture that is not ready does not (its own preparation reports it, and its identity is part of the hash), and neither does a stall (`MaterialCompileStalled`, diagnostic `material.compile.stalled`: no shader finished for the warm-up's or the probe's bound, which says nothing about the program); those requests compile again.
- Models: canonical bytes are GLB; [`gltf-loader.ts`](../../../packages/render/src/gltf-loader.ts) registers the glTF 2.0 loader and its extensions only. Draco/meshopt decoders are self-hosted, never a CDN. OBJ/FBX/STL are converted to GLB at import (`convert-*-to-glb.ts`). Per-Scene template containers instantiate per actor with Babylon automatic material cloning disabled; construction materials are keyed by mesh, not `mesh.metadata` (clones share metadata). Model slots map by glTF `/materials/N` pointer, then name, then next unused index, never child visit order. `loadModelContainer` gives every triangle mesh without `NORMAL` flat normals (`addMissingFlatNormals`; indexed meshes are unfolded, and unindexed meshes skip Automatic LOD): surface Materials read the `normal` attribute, and a missing buffer reads as zero, which draws black.
- MeshComponent geometry and Material are separate references: a primitive with a Material keeps a null `meshAssetGuid`. `materialSource: "override"` distinguishes an explicit None (engine checker) from inherited Model slots; the picker's "Model Materials" value is UI-only and never saved.
- Runtime parameters (`setMaterialParameter`) share the compiled default until a component's first write, then `MaterialLibrary` compiles a private instance for that component only; saved assets and siblings never change. A None texture binds a neutral white sampler.
- Environment cubes reach render only as ENV or DDS: `.hdr` panoramas become prefiltered RGBA16F DDS at import ([asset-registry.md](asset-registry.md#importers)), so render has no HDR, panorama or filtering path.
- The scene environment controller leases one cache source and clones only its CubeTexture view ([`environment-lighting.ts`](../../../packages/render/src/environment-lighting.ts)); intensity goes through `scene.iblIntensity`. Missing irradiance is derived once per cube; pending or failed uploads join readiness and are never thrown from a frame.
- Skybox source: the controller takes `acquireExisting` on the first enabled, visible skybox mesh's cube (no second upload), draws it in `CUBIC_MODE` with the reflection matrix `RotationY(Environment Rotation) × inverse(sky rotation)` so lighting matches the drawn sky, and follows sky changes from its before-render hook (the mesh list is rescanned only when it changed). A sky whose cube is still uploading holds readiness and keeps the previous view; a failed sky disables its mesh, which drops the lighting.
- Reflection probes ([`reflection-probes.ts`](../../../packages/render/src/reflection-probes.ts)): each `ReflectionProbeComponent` captures static meshes (`reflectionProbeStaticActors` in core: plain Actors whose components never move, under static parents; Water and helpers excluded) into a cube render target drawn outside the view's graph like a Fast capture (`drawOutsideSceneView`), one probe per frame, once edits and mesh changes settle (`REFLECTION_PROBE_RECAPTURE_DELAY_MS`) and only when the static mesh set changed (a forced recapture after any authored edit, a Play load or the Recapture Reflection Probes node). The cube is filtered by the shared prefilter path with its own irradiance, then box-projected onto the probe's world AABB. Per-mesh selection ([`mesh-environment.ts`](../../../packages/render/src/mesh-environment.ts)): a pinned patch of PBR and Node `isReadyForSubMesh`/`bindForSubMesh` swaps the scene's `_environmentTexture` backing field to the mesh's cube (the smallest published probe box holding its bounding-sphere centre), so each submesh compiles for its own cube's defines and binds it; a cube switch between consecutive draws of one material forces a rebind (`_forceRebindOnNextCall`, which also refreshes frozen UBOs). A mesh whose probe changes dirties its material. Instanced batches use their source mesh's probe. Probes never hold readiness; until a capture publishes, meshes reflect the scene's environment.
- Sky filtering ([`environment-prefilter.ts`](../../../packages/render/src/environment-prefilter.ts)): the controller lights from a GGX-prefiltered copy of the sky, at most 256 per face in half-float, one per Engine and sky upload. Babylon's `hdrFiltering` shader writes every mip, mip 0 included, with the lobe PBR samples it for (`lodGenerationScale` 0.8), and reads the source mip matching each sample, so 64 samples suffice and the face downsample needs no extra pass. The target reserves under the `environment` managed category. While filtering, readiness holds and the previous view stays; a device without prefiltering or float targets, an exhausted budget or a failed filter lights from the unfiltered sky.
- Automatic LOD ([`model-lod.ts`](../../../packages/render/src/model-lod.ts)): index-only levels sharing the master's vertex buffers, generated off-thread by meshoptimizer, never persisted or exported; selection in `customLODSelector`. No texture streaming (Babylon has no residency API).
- WebGPU lifetime: everything a Scene, preview or Play session allocates must return to the device when it closes; the project Engine lives for the whole session, so any retention grows until allocation fails or the device is lost. WebGPU destroys released buffers and textures at the next frame end, and Babylon disposes a draw wrapper's Effect one end frame after that wrapper, so an Engine with no rendering client would keep a closed Scene allocated until another view draws. A non-owning client's `dispose` therefore calls `drainEngineAfterRelease` ([`idle-engine-drain.ts`](../../../packages/render/src/idle-engine-drain.ts)): the shared Engine runs empty frames until that client's release settles (managed leases wait for an end frame), then three more, then prunes the caches. It gives up if the release has not settled after 5 s, or no frame follows within a second of settling, leaving the rest to the next client's frames; it removes only its own loop, so a client that starts mid-drain keeps rendering.
- Babylon's global WebGPU bind-group and render-pipeline caches never evict. [`webgpu-cache-pruning.ts`](../../../packages/render/src/webgpu-cache-pruning.ts) records the buffers, textures and Effects each Engine releases and drops their entries at a frame end once enough have accumulated (or enough frames have passed) and when an idle drain ends; ids are never reused, so no lookup can hit a pruned entry, and a wrong prune only costs a cache miss. Two exceptions, both misses only: `Texture.Parse` restores `internalTextureUniqueId` whenever the JSON carries it (`Texture._SerializeInternalTextureUniqueId` only gates writing it; Haptic never feeds Babylon serialization to `Texture.Parse`, since asset payloads never hold it), and an unbound slot keys as id 0 plus the range start, so releasing buffer or texture 0 also prunes every unbound-slot entry. Never `ResetCache()` or disable either cache (bind groups would be rebuilt per draw). WebKit backs each bind group with Metal argument buffers.
- Babylon never disposes a deleted WebGPU pipeline context, and never deletes the context of a released Effect outside its compiled-effect cache (an `EffectWrapper` without the shader store). [`webgpu-resource-release.ts`](../../../packages/render/src/webgpu-resource-release.ts) disposes it in both cases so the Effect's leftover-uniform `UniformBuffer`, which keeps one GPU buffer per draw context that used it, leaves `engine._uniformBuffers`.

## Play presentation and editor views

- The Play Scene starts with camera and light only; actors come from `assignMesh` plus snapshots. Play always draws the latest published snapshot, no interpolation (render and tick share the ~60 Hz cap). `SnapshotSampler` ([`snapshot-sync.ts`](../../../packages/render/src/snapshot-sync.ts)) ignores unpublished buffers and is cleared on scene change; snapshot TRS is world space; new geometry stays hidden until a snapshot poses it. One slot is one visual.
- Snapshot apply runs once per applied snapshot identity (`{frameId, layoutGeneration}`); audio pose and listener sync live there, not in render admission.
- Main-thread apply: [`snapshot-apply.ts`](../../../packages/render/src/snapshot-apply.ts) keeps the per-snapshot apply and the slot lifecycle (migrate, retire, dispose) and re-exports by name the public API of the modules behind it, which importers and `index.ts` reach only through it. In dependency order, each importing only those before it and none importing `snapshot-apply.ts`: [`snapshot-binding.ts`](../../../packages/render/src/snapshot-binding.ts) (`SnapshotSceneBinding`, `SlotKeyedMap`, component mesh names), [`snapshot-visibility.ts`](../../../packages/render/src/snapshot-visibility.ts) (snapshot visibility, helper metadata, world copies of overlay slots), [`snapshot-materials.ts`](../../../packages/render/src/snapshot-materials.ts) (Material assignment, parameters, retained owners), [`snapshot-illumination.ts`](../../../packages/render/src/snapshot-illumination.ts) (helper lights and cameras, active camera), [`snapshot-spring-arms.ts`](../../../packages/render/src/snapshot-spring-arms.ts) (spring-arm lag), [`snapshot-component-commands.ts`](../../../packages/render/src/snapshot-component-commands.ts) (component poses and per-component commands), [`snapshot-visual-factory.ts`](../../../packages/render/src/snapshot-visual-factory.ts) (`createPlayVisual`, `createPlayMesh`) and [`snapshot-assign-mesh.ts`](../../../packages/render/src/snapshot-assign-mesh.ts) (`applyAssignMesh` and its strategies). Each keeps its per-binding and per-mesh WeakMaps private behind accessors.
- Overlay Play: size from the overlay box with `engine.setSize`; `clearBeforeCopy`; disable other enabled Scene views until Play closes (restore exactly those); `scene.autoClear = true`; `skipPointerMovePicking` on world scenes. Custom resolution with Black Bars locks the framebuffer and letterboxes with `fitContainedRect`, never CSS `object-fit: fill`; Play restores the hardware scale captured before it started.
- Engine Settings `postProcessingEnabled` gates only editor viewports and in-editor Play, never exported games or the Material editor preview.
- `visibilitychange` (and Capacitor app state) pauses the render scheduler, game tick and texture encode queue. A blocking overlay counts as closed only with `data-closed` or `hidden`; Base UI marks open backdrops `aria-hidden`.
- Editor scenes use `ScenePerformancePriority.BackwardCompatible` plus `applyEditorMaterialFreeze`; Play uses `Intermediate` and `playMode` skips the editor freeze so packed textures can rebuild. A texture-load rebuild must unfreeze → build → reapply authored blend → mark dirty with dirty-block off → refreeze.
- Editor apply is incremental through `EditorSceneSync` ([`editor-scene-sync.ts`](../../../packages/render/src/editor-scene-sync.ts)); work stays proportional to the change. Material rebinding reports net changes only (`withNetMaterialChanges`); unchanged post-process stacks and in-place light uniform edits keep the prepared graph. A transform-only edit (`isTransformOnlySceneEdit`) re-realizes only the actors whose pose changed (`EditorSceneSync.applyPoses`), refreezing the actor roots under them and running the Scene-wide cable and illumination passes; it falls back to the full apply while a realization, visual replacement or model load is in flight, when the Scene has an overlay layout (a move can relayout other actors), and when a moved actor's visual fingerprint changes (a 2D Panel's scale).
- Full editor loads and actor visuals (mesh names, origin hierarchies, transforms, freeze, cable previews, `applySceneToBabylonScene`) live in [`scene-loader.ts`](../../../packages/render/src/scene-loader.ts). It delegates actor classification to `scene-visual-classify.ts`, rebuild fingerprints to `scene-visual-fingerprint.ts`, the per-component mesh factory to `scene-component-mesh.ts` and Mesh collision dashes to `mesh-collision-dashes.ts`, and re-exports their public names. A component's fingerprint kind must change whenever the factory would build a different mesh, because `EditorSceneSync` rebuilds only on a fingerprint change.
- Editor canvases render continuously at the viewport cap and freeze when hidden, off-screen, resizing, under a Dialog/AlertDialog/Sheet, or while Play/Preview Build runs ([`render-scheduler.ts`](../../../packages/render/src/render-scheduler.ts), [`apps/editor/src/lib/viewport-render-gate.ts`](../../../apps/editor/src/lib/viewport-render-gate.ts)). Static previews idle after a ready frame. The selected camera's or capture's lens preview (`EditorDebugOverlay`) takes no timed passes while its Engine is paused (`applyPause` calls `setPaused`), so a game never pays for it.
- Picking: viewport taps use a 1×1 GPU object-ID pass ([`gpu-object-id-picker.ts`](../../../packages/render/src/gpu-object-id-picker.ts)) that follows skinning, morphs and WPO and pins the floating-origin context to its scene while it draws (outside `Scene.render` Babylon uses the last scene to render, the gizmo layer in the editor, whose full-view matrices would sample the viewport centre); marquee, Play `pickAt`, brushes and transform tools use the CPU ray ([`picking.ts`](../../../packages/render/src/picking.ts)).
- Meshes without a Material draw `installEngineDefaultMaterial` (lit grey checker PBR); primitives keep `mesh.material === null` so the Inspector shows None.
- Editor selection, gizmos and debug overlays never change Scene membership (pre-created hidden guides, entity-free cameras/RTTs); a membership change costs a whole-scene readiness probe.

## Water

- One `WaterDefinition` is shared by renderer, worker and editor (core `water.ts`). Physics, queries and buoyancy never read quality, the GPU FFT or GPU state: every look, Custom Material included, evaluates the CPU spectrum field of core [`water-spectrum.ts`](../../../packages/core/src/water-spectrum.ts) (JONSWAP wind sea plus swell, deterministic hashed Gaussians so every quality tier and the worker share one ocean; 64² and 32² grids at `WATER_SPECTRUM_PHYSICS_RATE`, frames blended, Catmull-Rom sampled). The GPU spectrum (`water-fft-spectrum.ts`) builds the same modes at its own size and drops bins the CPU grids cannot hold, so short render-only detail is the only difference.
- `WaterClock` (runtime driver) advances with the simulation step; the renderer pairs water time with the applied snapshot frame (`setSceneWaterTime` / `sampleSceneWaterFrame`). Editor and previews use real time.
- Rendering gates on the device-effective `sceneWaterQualityDeviceClamp(scene)`, never requested values; `sceneWaterQualityRevision` change re-plans each FrameGraph ([`render-settings.ts`](../../../packages/render/src/render-settings.ts)). `clampWaterQualityToDevice` is the single device gate.
- `WaterMaterialPlugin` ([`water-material.ts`](../../../packages/render/src/water-material.ts)) compiles one look per material through defines; tiers use numeric `SLATE_WATER_QUALITY` with one `#if … >= n` per line so Babylon's define-keyed cache stays correct; zero-valued features compile out. Defines change only on quality, pipeline, asset or flatness changes, never per frame. Its shader source lives beside it: defines and tuning constants in `water-shader-defines.ts`, source chunks in `water-shader-chunks.ts`, per-language assembly and injections in `water-shader-source.ts`; per-Scene placeholders, lighting and binding data in `water-scene-state.ts`; GPU wave uniforms and `WaterVertexWaves` in `water-vertex-waves.ts`. `water-material.ts` re-exports their public names.
- To see which water variants a run requests, set `globalThis.__slateWaterCompileLog = []` before the scene loads: every define change appends the look, REFRACTION/SSR/planar/blend/FFT, shadow, depth-pre-pass and prepass defines, the render pass id and the caller (`WaterVariantRequest`). Nothing is recorded without it.
- Refraction/screen-space reflections read a per-view scene copy ([`water-scene-copy.ts`](../../../packages/render/src/water-scene-copy.ts)) registered by render pass id before the first readiness probe; copy-sampling water draws only in `Forward transparent`. Which variant built-in water draws depends on the pass (REFRACTION/SSR compile only into the copy's pass, the depth pre-pass has its own), so the shader warm-up and the pre-graph strict probe skip it (`isBuiltInWaterMesh`) and only the graph's own probe compiles it, under the real pass id: a probe under any other pass compiles a variant nothing draws, and every one is a slow link. Planar mirror ([`water-planar-reflection.ts`](../../../packages/render/src/water-planar-reflection.ts)) is drawn capture-style, entity-free; its mirror camera, oblique projection, target and pass are [`planar-mirror.ts`](../../../packages/render/src/planar-mirror.ts), shared with Mirror components. FFT ([`water-fft.ts`](../../../packages/render/src/water-fft.ts)) is fragment-shader passes on both backends, demand-driven (built-in water, or a Custom Material with a Water Waves node): the whole surface (three cascades, displacement, derivatives with per-layer mipmaps, and a ping-pong turbulence foam target accumulated from the Jacobian, each cascade recovering over its spectrum `foamPeriods` entry). Crest foam is the cascades' turbulence below calm weighted by `WATER_FOAM_WEIGHTS` (long waves first) past `waterFoamThreshold` (core: Crest Foam's share of the sum's Gaussian model, calibrated on GPU readback), bound per asset by `waterFoamThresholdOf` to built-in `slateWaterShape.x` and the Water Waves node's foam uniform `.z`. Devices without float render targets draw water flat (`WaterQualityDeviceClamp.spectrum`). All reserve in the ledger's `water` category.
- [`water-mesh.ts`](../../../packages/render/src/water-mesh.ts) creates water surfaces and runs their per-frame update (placement, culling bounds, CPU waves, copy intent, the Custom Material path, picking). Beside it: the per-surface model in `water-mesh-surface.ts`, the scene water clock in `water-scene-clock.ts`, the rest-grid layout and cell budgets in `water-mesh-grid.ts`, per-vertex rest data and its uploads in `water-mesh-rest-data.ts`, the scene blend registry, blend kernel, Global blend rows and normals' fit in `water-mesh-blend-data.ts`, and the blend index sync and budgeted blend refresh in `water-mesh-blend.ts`. `water-mesh.ts` re-exports their public names, and code outside these modules imports only it.
- `settleSceneWater` ([`water-mesh.ts`](../../../packages/render/src/water-mesh.ts)) runs the water update as an early run (it advances neither the clock nor the drawn flags the frame's own run consumes), so blend, placement (`flat`) and the sky reflection view are final before a surface's variants are first probed. The before-render update fires after the strict probes; left to it, those values change the defines of variants already compiled, and every one compiles again. Copy intent is counted when the surface is created (`createWaterMesh`) and re-synced by the update only when enablement changes through an ancestor or `setEnabled`, and by `updateWaterMeshDefinition` when an asset edit moves Refraction or Object Reflections. Call sites: `prewarmSceneMaterials` (always, before the load's warm-up and graph probes), the render loop on frames that draw the world (only when a surface was created or its enablement changed since the last update: editor edits and drops, Play spawns; load frames leave it to the load's settle), and a published scene stream (its roots are held disabled until then, and the update skips disabled surfaces). The syncs are idempotent with the before-render update, and a Scene without water does nothing. `prepareSceneStream` skips built-in water in its warm-up like the load does.
- Bodies within Water Blend Distance blend via core `water-blend.ts`; only the owning body draws and answers queries. A body takes part out to the full distance (`waterBlendReach`) and fades out of the union shoreline over its outer half, where the union's smooth maximum (radius R) no longer pulls: a fade inside the rounding cuts corners into stepped tabs. A grid's outer vertices past its own reach still evaluate the kernel (`outside`), owning nothing, so shoreline and ownership interpolate toward true values. Colours fade over a wider coverage than shares; each surface keeps up to `WATER_BLEND_COLOR_PARTNERS` differently coloured neighbours (alike-coloured ones share a slot) with per-vertex shares (`slateWaterBlend.w`, `slateWaterBlendColors`), read by built-in water and by the Water Colors node (`WaterNodeSurface.partners`). Custom Material water hides what it does not own through its Water Waves node's fragment (bank and margin in `WATER_NODE_VARYING`'s z and w); without that fragment a blending Custom Material draws its whole mesh over its neighbours.
- Built-in water displaces on the GPU from a static rest grid (`evaluateWaterVertex` in core is the CPU reference); Custom Material water opts in only through a **Water Waves** node. CPU picking hits the rest grid. The other water material nodes ([`water-node-blocks.ts`](../../../packages/render/src/water-node-blocks.ts): Water Colors, Foam, Depth Fade, Scene Color, Reflection) are fragment blocks that read the mesh's `WaterNodeSurface` (asset, and terrain and contact fields the water mesh builds only once a graph reads them) and the pass's scene copy (`SLATE_WATER_NODE_COPY`, same per-pass rule as built-in; an alpha-blended Custom Material whose graph reads the copy counts in the copy intent). Their per-pixel wave inputs come from the graph's Water Waves block. A vertex-and-fragment block gets no automatic varyings for its inputs, so `WaterWavesBlock` passes its rest point and normal itself. Built-in shading has one look; stylized water is a Custom Material. The starter graph `createWaterMaterialDocument` (shader-graph) draws the built-in look from the nodes, which share its formulas with built-in shading (`subsurfaceSource`, `fresnelSource`, `reflectionKeepSource`, `transmittanceSource` with `waterAbsorption`, the body light `sceneWaterBodyLight`, built-in's `slateWaterLight.w`, and the shore and contact foam `edgeFoamHelpers`, which the Water Foam block reads from the Water Waves block's hidden `edgeTurbulence` output, in `water-material.ts`), so keep them in step: a river drawn by the starter that ends inside a built-in lake shows any difference as a seam where ownership hands over. Water meshes never cast shadows (`neverCastsShadows`).
- Grid geometry (except Global Water Volume and a spectrum Ocean) is world-anchored and never depends on the camera. A spectrum Ocean grades its grid around the camera (`oceanBudget`, capped by `WATER_OCEAN_CELL_BUDGET`) and rebuilds it when the camera moves `OCEAN_RECENTRE_SHARE` of the dense region. The worker's `WaterWorld` keeps step and script-query evaluations in separate states.
- Object contacts ([`water-contact-field.ts`](../../../packages/render/src/water-contact-field.ts)): `WaterContactField` is a per-surface, CPU-built, height-aware signed-distance texture (four layers across the wave envelope). Waves never rebake it; objects, the surface and the envelope do. Contact Resolution caps its cells per side (Medium and Low 256, High and Ultra 1024).
- Contact cost cap: `WATER_CONTACT_FRAME_BUDGET_MS` bounds window rebuilds per scene and frame, across surfaces (`WaterContactField.drain`). A moved object queues only the window its movement can change (its slice bounds before and after, grown by the contact range); windows that overlap merge and keep their age, and a cell keeps its last result until its window is built. Order: seen before unseen, nearer before farther, any window waiting past `OVERDUE_MS` first (oldest first), and always at least one window per frame, so none starves. Windows past 64 cells a side are cut into blocks, so a frame overshoots the cap by at most one block. Cadence falls with distance and view: a seen window waits 0 to `FAR_MAX_MS` before it runs (ramping from `FAR_START` to `FAR_END` metres from the nearest camera), an unseen one `OFFSCREEN_MS`, which coalesces bursts of moves; surfaces no camera sees skip their contact update altogether (`updateSceneWater`).
- Full rebuilds (first build, `force`, reshaped body, changed envelope, range or Contact Resolution, a changed cell size) run at once but are counted against the frame. An object that outgrows the allocation carries the kept cells over to the new one (same lattice) and queues only what changed; a moved surface re-cuts every cell at most every `SURFACE_MOVE_MS` as one queued window.
- No duplicate contact work between bodies: a window in which no body draws the surface is not built (`WaterFieldSurface.draws`: a blending neighbour owns the water there, as under an Ocean over Global Water Volume) and stays queued until `drawStamp` (the blend index revision) changes. It samples each window's centre and corners and treats any point the blend cannot place as drawn. Initial and forced builds still cover every cell.
