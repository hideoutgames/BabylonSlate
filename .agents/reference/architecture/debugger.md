# Debugger

Haptic's headless command registry, infinite-loop guard, trace recorder, inspect protocol, Play overlay diagnostics and Simulation Play contracts. Command catalog: [console-commands.md](console-commands.md).

## Core rule

The command system is always present; only the debugger UI and debug-tier commands are optional. A shipped game can still `changescene` or change quality with no console on screen.

## Package boundary

- `@haptic/debugger` imports nothing: no React, Babylon, Capacitor or scripting. New behavior goes through `ConsoleCommandHost` plus bridge commands; rendering, audio and camera stay in render / the Play overlay.
- `@haptic/scripting` may import only `instrumentJsLoops` from it.
- `CommandRegistry.execute` never throws: parse/coercion failures, unknown names and stripped names return `{ success: false, output }`.

## Tiers

- `createCommandRegistry({ includeDebug })`. Core commands always register; debug implementations register only with `includeDebug: true`, but debug names are still recognized so a release build reports "not available in this build" instead of "unknown command".
- Names live in `CORE_COMMAND_NAMES` / `DEBUG_COMMAND_NAMES` ([`commands.ts`](../../../packages/debugger/src/commands.ts)). Editor Play and Preview Build include debug; release exports pass `includeDebugCommands: manifest.bundleDebugger`.
- User `BDebugCommand` classes register as core, so they ship in every export.
- `warnDebugTierConsoleCommands` warns when an `ExecuteConsoleCommand` literal names a debug command; connected pins are not flagged.

## Parser

- Whitespace tokens; quoted tokens are always values (even `"a=b"`). Multi-word names (`stat unit`, `snapshot start`) match longest first.
- Positional or `name=value` / `name:value` arguments; undeclared names fail. A `rest` parameter takes the remaining tokens.
- Coercion to string / float / int / bool / enum; bool accepts true/false/1/0/on/off/yes/no.

## Infinite loop guard

- Editor-only, per-tick iteration cap (Project Settings, default on, `DEFAULT_INFINITE_LOOP_COUNT = 1_000_000`). Play reads live settings; the count is never baked into generated JS.
- `instrumentJsLoops` rewrites `while` / `for` / `do` bodies with a check carrying asset/graph/node identity; it must not rewrite strings, comments, templates, regexes or property names.
- `runtime.infinite_loop` is session-fatal in overlay Play and Preview Build; ordinary `runtime.uncaught` is not. There is no time-based worker watchdog.

## Stats and overlay

- Worker emits `{ type: "stats" }` every `STATS_COMMAND_INTERVAL_MS` (200 ms), not per tick. `isTickOverBudget` sums script + physics against `TICK_BUDGET_MS` (8); `publishMs` is excluded.
- Chrome must not React-update at 60 Hz. Stats HUD starts collapsed; while hidden, the overlay skips HUD-only reads (render diagnostics, memory, draw calls). Test-mode attributes are polled only when `isTestModeEnabled()`.
- Stats rows come from one model, `statsHudModel` in [`stats.ts`](../../../packages/debugger/src/stats.ts): the editor `StatsHud` and the player HUD ([`hud.ts`](../../../apps/player/src/hud.ts)) only render it, so Play, Preview Build and exported games show the same rows. Hosts pass the render package's draw and geometry ceiling warnings in as booleans. `stat threads` is bridge messages per second (`createMessageRateMeter`), live actors against snapshot capacity, and the worker tick index. The player reads memory, object counts and render diagnostics only while its Stats show (`statsVisible`).
- Draw calls come from Babylon `_drawCalls.current` after Play `scene.render()`, not `engine.drawCalls`.
- Every runtime `log` command (Log nodes, failed Assert nodes, driver and captured console logs; never `print` or the `diagnostic` an error log also raises) reaches the editor Output Log once through `onRuntimeLog` / `formatRuntimeLogLine` (`[Category] Warning: message`), in Play and Preview Build, besides the overlay console.
- Output Log and live BT state live in an isolated diagnostics provider; log lines commit once per animation frame (250 ms timer while hidden). The console transcript caps at 500 rows.
- Inspector is read-only (no `setVariable`); Use Camera / Destroy Actor send the debug commands with the selected GUID. Compose it from catalog components only.
- Print HUD and Draw Debug are not debugger chrome: they apply even without `bundleDebugger`. Stats, console and inspect are debugger-bundled.
- Debug Mode (Engine Settings, off) gates copyable diagnostics. Put new copyable diagnostics behind `useDebugMode()`; copy handlers build text synchronously so iPad Safari keeps the clipboard write in the tap. Reports never include project files.

## Inspect protocol

- `{ type: "inspect" }` control → `{ type: "inspectSnapshot" }` command ([bridge.md](bridge.md)). Overlay polls ~5 Hz only while the Inspector or console is open, skips while a request is in flight (abandoned after 3 s), and drops equal snapshots in `inspect-world-store.ts`.
- Snapshot order: Game Instance, subsystems, actors parent-before-child, components. Values are JSON-safe: `BObject` → `{ guid, classId }`, cycles → `formatValue()`; recording a reference never traverses its World.

## Trace recorder

- `snapshot start` / `stop` fill a byte-budgeted `TraceRecorder` (default `DEFAULT_TRACE_BYTE_BUDGET`, 128 MiB; Engine Settings 1–256). The budget counts UTF-8 JSON bytes, not heap; oldest complete frames evict, an oversized frame stops recording. `retention` metadata is required.
- Frames record `timeDilation`, BT, audio voices, sprite clips and anim-graph state. `restoreFromTrace` order is fixed: dilation, BT, Animation Graph, sprite clips, stop missing voices, replay recorded voices with their offsets and rolls.
- Editor Stop waits at most 2 s for the trace reply. Trace opens as a read-only DockView tab; the file format is unchanged by inspection features.

## Simulation Play

- Runs the game runtime in the open Scene viewport on a separate game Scene of the shared Engine. Authoring is locked (read-only editors, central write locks); Save Game writes are dropped on Stop.
- The Scene viewport registers a `SimulationViewport` ([`simulation-viewport.ts`](../../../apps/editor/src/services/simulation-viewport.ts)). Starting a Simulation calls `suspend()`: it abandons a blocking load in flight and closes its Scene Loading dialog (an abandoned load reports nothing more, so the dialog would stay modal over the game and hold background captures), then waits for the viewport's native release. Stop calls `restore()`, which reloads the authoring Scene behind a new Scene Loading dialog; a Simulation started while that load runs suspends it the same way.
- Pause On Errors (Engine Settings, default on) reaches the runtime as the `pauseOnErrors` load option, in Simulation and editor Play. `recordDiagnostic` in the driver pauses (`user` reason, deferred to the end of a running tick) the first time an error source reports, keyed by code, asset and node as the session report groups them (a runaway loop ends the session instead), and emits `sessionPaused` with its `cause`. The overlay takes that pause through the session boundary like Pause, so Resume and Step work, and opens the source through the session report's navigation.
- Keep Simulation Changes (default off) applies one **Apply Simulation Changes** command from a complete capture or fails with Retry / Discard; never partial. Streamed Scenes, SceneLayers and generated resources cannot be kept.
- Trace, performance recording and Frame Capture are refused in Simulation.
- Session controls live in the global toolbar's Play island: Simulate becomes a red **Stop** (accessible name says keep or discard), with **Pause**, **Step** while paused (a `step` session boundary request: one tick from a pause held only by `user`, refused while another hold or a blocking load is active, acknowledged after the tick's commands so the frozen view redraws it), a **Game** / **Edit** input toggle (shows the current input; tooltip names the switch) and, when another document is active, **Return To Scene**. `PlayOverlay` owns pause and input mode and publishes them through `SimulationControlsProvider` (an external store, so a pause re-renders only its readers). Controls marked `data-simulation-control` act without first releasing game input. On a narrow toolbar (390 px phone) Return To Scene, the Debug Instance select and Step collapse into the toolbar's More Actions menu before Pause, Stop or the input toggle, which are pinned ([`toolbar-overflow-priority.ts`](../../../apps/editor/src/lib/toolbar-overflow-priority.ts)). The viewport keeps only Stats / Console and, in Edit, the icon-only Move / Rotate / Scale island; authored documents show a one-line read-only strip.

## Simulation graph debugging

- Simulation and editor Play. Preview Build and exports get no probes, no messages and no editor state; the instrumentation is editor-only and absent wherever `stripDevelopmentOnly` applies. Play compiles with it but observes nothing while it runs behind its view: the chrome bar sets a debug target only while a Simulation runs or Play is stopped (below), so a running Play pays the null checks alone.
- **Play stops** ([`play-overlay.tsx`](../../../apps/editor/src/components/play-overlay.tsx)): a pause cause in Play (a breakpoint or Pause On Errors) becomes `playBreak`. The overlay takes the `user` pause through the session boundary as Simulation does, adds `hidden` to its root (still mounted and paused: its view has no layout box, so it is not admitted and keeps its size; the overlay's resize observer lays it out again on Resume) and publishes `SimulationControls` with `mode: "play"` (Resume, Stop), which the chrome bar shows with Stopped At and Debug Instance (`PlayBreakToolbarControls`). `onPlayBreak` tells the Play session provider, which wakes the editor (`editorQuiet` off), locks authoring (`lockAuthoring("Read-only while Play is stopped")`) and lets the chrome bar set the debug target. Resume clears it and returns focus to the canvas. The overlay forwards the store's requests (`subscribeRequest`) only while it debugs, a Simulation or stopped Play, and tells the runtime to stop watching on Resume, so a running Play watches nothing. There is no Step. Editor viewports stay paused (Play's view still holds the Engine views), so the Scene view does not redraw while Play is stopped.
- **Compiler** ([`compile.ts`](../../../packages/scripting/src/compile.ts)): `CompileOptions.instrumentExecutionTrace` is off by default and ignored with `stripDevelopmentOnly`. Each entry declares `__dbg` from `ctx.debugTrace` (null for every instance but the followed one) and every probe is `if (__dbg !== null) …`: no allocation, no work unobserved. Probes cover exec visits (flow nodes and entry events; gated input events report inside the gate), the exec wire taken (also before a back edge's `continue`) and a node's data outputs. Wired inputs of nodes that run are wrapped in place by `__dv`, never evaluated twice or reordered, so impure inputs sample once. Pure nodes inline into their consumers, so each wired output expression is wrapped in place by `__dw` (`tracedPureOutput`, after the guard and lazy-declaration wrapping so those decisions match an untraced compile): every pure node of a chain records its output each time a consumer evaluates it, adds no evaluation, and a pure node nothing evaluates records nothing. Pure inputs are not recorded; a wired input shows its source's output. Unwired inputs are not recorded: the node shows the literal.
- **Cache**: `GraphScriptCompileCache` keys on the flag, for Class graphs and for Animation Graphs (`animGraphCompileCacheKey`). Only `collectPlayPreviewScripts(…, { traceExecution })` from editor Play or a Simulation sets it. The asset loader's compiled-scripts entry (`play-scripts:` in `play-asset-sources.ts`) outlives a session and keys on `PlayAssetSourceHost.traceExecution` too, so a host compiling without the probes never receives scripts that have them. An Animation Graph's Animation Object graph is probed like a Class graph under `animation-object` (its `assetGuid` is the asset path, as for diagnostics); transition rule graphs (`compileTransitionRuleGraph`) are pure and carry no probes.
- **Runtime** ([`script-debug.ts`](../../../packages/runtime/src/script-debug.ts)): `ScriptDebugObserver` serves `debugObserve`. A class target's roster lists live objects of **exactly** that class (Game Instance, subsystems, then actors each followed by its components), recomputed only when `World.structuralRevision` or the Game Instance / subsystem set changes. A Behaviour Tree or Animation Graph target lists the **components that run the asset** (below) and is rebuilt each tick, because the asset a component runs is a variable a script can set; only actors owning such a component are walked. Rosters are capped at `DEBUG_ROSTER_LIMIT` and sent as `reset` then deltas. Following an instance creates a new `ExecutionTraceSink`; the driver hands it to `ScriptHost.setDebugTrace` (routes `ctx.debugTrace` by identity of the context's variable store, else `self`, so an Animation Graph's component, not its actor, is the instance), `BehaviourTreeRuntime.setDebugTrace` and `AnimGraphRuntime.setDebugTrace`. A late async run of an earlier sink writes into a closed sink. The sink gathers per tick (nodes, wires, last value per pin keyed by node + pin + direction) and `flush` runs at the end of `runTick`: one `executionTrace` per tick with something to report; values are display text (`formatDebugValue`: four decimals, object references, about 100 characters) sent only when changed.
- **Bridge**: `debugObserve` control and `debugRoster` / `executionTrace` / `btState` commands ([`channels.ts`](../../../packages/bridge/src/channels.ts)) never go through the render allowlist and do not advance the command revision a final Simulation capture compares (`DEBUG_VIEW_COMMANDS`). `DebugObserveTarget` is `class` | `behaviourTree` | `animationGraph`; the graph ids a runtime-evaluated graph reports under live in [`debug-target.ts`](../../../packages/bridge/src/debug-target.ts). Worker and in-process runtimes run the same driver code.
- **Editor**: `GraphDebugStore` ([`graph-debug-store.ts`](../../../apps/editor/src/services/graph-debug-store.ts)) lives outside React state. The roster and followed instance reach React through `useSyncExternalStore` (the toolbar's **Debug Instance** select); traces go to `subscribeTrace` listeners and the latest pin values stay readable through `value`. Selection: first listed instance by default, the first remaining on despawn, None when empty, and an explicit None sticks until the target changes. `subscribeRequest` is how `PlayOverlay` sends `debugObserve`. The chrome bar sets the target (`documentGraphDebugTarget`) while a Simulation runs, or Play is stopped, and the focused document is a Class that can have instances, a Behaviour Tree or an Animation Graph. A followed tree's `btState` becomes per-node statuses (`btNodeStatuses`) read through `status` / `subscribeStatus` and the Blackboard through `blackboard` / `subscribeBlackboard`; both are cleared when the followed instance or target changes.
- **Canvas** ([`run-trace.ts`](../../../packages/graph-ui/src/run-trace.ts), [`run-flash.ts`](../../../packages/graph-ui/src/run-flash.ts), [`graph-run-overlay.tsx`](../../../packages/graph-ui/src/graph-run-overlay.tsx)): `GraphEditor.runTrace` is a `GraphRunTrace` (`subscribe`, `value`, optional `status` / `subscribeStatus`). A canvas gets it only while the store's target is its own graph (`useClassGraphRunTrace`, `useBehaviourTreeRunTrace`, `useAnimStateMachineRunTrace`, `useAnimObjectGraphRunTrace`; they follow `useGraphDebugTarget`, which changes only with the target, so instances spawning and despawning re-render no canvas), so plain editing mounts no overlay and shows no tip. Runs coalesce per animation frame and fade through Web Animations on the node shell (`data-node-role`), edge path and pin glyph found by id (never React state); a repeat run cancels and replays the same animation. While the Simulation is paused (`GraphDebugStore.setHeld`, read through `GraphRunTrace.subscribeHold`), the last run's animations are paused at full strength (a run arriving while held, such as a Step's, too); releasing plays them out and lets them go, and following another object releases and retakes the hold so its old path fades. A node that ran also lights the data wires into it, through pure nodes (`__pure`). Reduced motion holds the highlight at full strength for the same time. The tip is one fixed element driven by delegated pointer events: a pin value (`data-pin-side` / `data-pin-id` on each side of a pin row; mouse hover, or a touch tap on `data-pin-label`, the handle staying tap-to-connect) or a node status (`data-run-status-tip`; hover or tap). A pure node's pins show the value of its last evaluation in a Class graph (`resolvePinValue` falls back to what a node that ran read through the pin only where nothing recorded it, as in a graph whose pure nodes do not report). Tree and state wires paint their stroke with `!important`, which outranks an animation, so those canvases mix `--selection` into the stroke through the registered `--run-flash` property and the flash animates that instead.
- **Behaviour Trees**: the instance is the `BehaviourTreeComponent` an actor evaluates (its first live one), matched to the asset by `behaviourTreeGuidOf`. `evaluateBehaviourTree(…, { trace })` reports every node the evaluation worked on (`visit`) and each parent-to-child link it entered or resumed (`link`, named by `btEdgeId`), only for the followed component; a running leaf is visited each tick, its ancestors when they start or advance. The trace is `behaviour-tree` under the tree guid. Node status and the Blackboard come from the same evaluation state `btState` always carried (`publishState`: change-detected, sanitized), now sent only for the followed component, with its `instanceId`, once as the follow starts and then on change. `TreeNode` reads its status through `useRunNodeStatus`, so a status change renders that node alone.
- **Animation Graphs**: the instance is an `AnimationGraphComponent` (an actor can have several, all evaluated), matched by `animGraphGuidOf`. The State Machine trace is `state-machine` under the graph guid: the state the evaluation ends on and every layer's state (the one a blend leaves), each tick the graph runs, and the taken transition as the canvas edge that draws it (`animTransitionEdgeId`: a Both Ways pair and duplicate rows share the first row's edge). A Jump To State replaces the evaluation and so reports no edge. Animation Object scripts report through `ctx.debugTrace` for the followed component (their `self` is the actor).
- **Breakpoints** ([`script-breakpoints.ts`](../../../packages/runtime/src/script-breakpoints.ts)): `CompileOptions.instrumentBreakpoints` (off by default, ignored with `stripDevelopmentOnly`) declares `__bp` per entry from `ctx.breakpoints.graph(assetGuid, graphId)` and adds `if (__bp !== null && __bp.has(id)) __bp.hit(id, entryNodeId, ctx.self)` at every exec visit, next to the trace probe (gated input events check inside the gate). Unlike the trace, the check runs for every instance: `ctx.breakpoints` is a host member that is null while no breakpoint is set, and `graph` is null for a graph without one, so an unset check is one null check and allocates nothing. Breakpoints are `Breakpoint`s (a `BreakpointLocation`: asset, graph, node; plus an optional `condition` and `hitCount`) from the `load` message (`breakpoints`) and `setBreakpoints`, which replaces them all. In a graph with breakpoints the values exec nodes see reach `__bp` for every instance: `__bv(__bp, node, pin, value)` wraps each wired data read (`tracedRead`, so bound subjects too; unwired literals are not wrapped) and the output probe adds `__bp.write` for a node with a breakpoint, both on the raw value. `hit` counts an unconditional run at once and arms a conditional one, which counts the first time its pin's value meets the condition (`meetsBreakpointCondition`: order compares numbers only, text equality matches a number or boolean as its text, `isValid` is `!= null`), so a node reading the pin on each pass (For Loop's Last Index) counts once per run. With a `hitCount` only the run that brings the count to it reports. `set` carries a node's count over when its settings are unchanged (the editor resends every breakpoint on each change) and starts it over otherwise; a new session starts at zero. The first hit in a tick (or in Begin Play, before the first tick) pauses the driver like Pause On Errors (`user` reason, deferred to the end of a running tick) and emits `sessionPaused` with a `cause` of code `BREAKPOINT_PAUSE_CODE`, the node, its event or function entry node (`entryNodeId`) and the object (`instanceId`, `instanceLabel` as the Debug Instance list names it); later hits in that tick are dropped. The object is the run's `self`.
- **Breakpoints (trees and state machines)**: locations keyed like the graph debugger's: a Behaviour Tree's tree guid with `BT_DEBUG_GRAPH_ID` and a tree node id, an Animation Graph's guid with `ANIM_STATE_MACHINE_DEBUG_GRAPH_ID` and a state or transition id. Each runtime looks up `breakpoints().graph(guid, graphId)` once per component and tick; with none it passes nothing to the evaluator. A tree node stops when it starts (`EvaluateBehaviourTreeOptions.breakpoints.hit` where a frame opens past its decorators, so a resumed running node does not) and when it fails: with breakpoints, `evaluateBehaviourTree` writes results through a proxy that reports each change to `failure`, so every failure path (result, decorator, Time Limit, abort) reports once and the returned state keeps the plain object. A state stops when the graph starts in it, a transition (self-transitions included) enters it, or Jump To State sets it; a transition stops when `AnimGraphInputs.transitionTaken` reports it, before the state it enters. The hit's object is the component (it matches the Debug Instance roster), labelled by its actor (`BreakpointHit.owner`), with no `entryNodeId`; `cause.breakpointEvent` says `started`, `failed`, `entered` or `taken`. These are interpreted, so they need no compile flag: any session given `breakpoints` stops on them, and Preview Build and exports are given none. They take a `hitCount` but no `condition` (they have no pins; a condition would arm and never count).
- **Breakpoints (editor)**: [`BreakpointStore`](../../../apps/editor/src/services/breakpoint-store.ts) holds `BreakpointEntry`s: the compiler's location (Class asset **path**, run graph id `event-graph` or `functionGraphExportName`, node id), `enabled`, and the Class, graph and node names for listing closed Classes. It is editor state per project, never in an asset: `BreakpointsProvider` (EditorRoute, above Play) reads and writes `derived/<projectGuid>/breakpoints.json` through `readProjectDerivedText` / `writeProjectDerivedText` (saves debounced, under the guid the project opened with), moves entries with a renamed or moved Class (`subscribeDocumentIdentity`), and the Class graph panel moves them with a renamed function (its run id changes). The panel passes `GraphEditor.breakpoints` (`graphView`) for Class graphs only and offers **Add Breakpoint** / **Remove Breakpoint** / **Disable Breakpoint** in the node menu; the canvas's `toggleBreakpoint` command (F9, `graph.toggleBreakpoint`) and title-bar dot (mouse only; touch uses the menu) also work read-only. Only nodes with an exec pin (`canBreakOnNode`) can have one, since the check runs at exec visits. Play and Simulation compiles set `instrumentBreakpoints` with `instrumentExecutionTrace` (one flag, so the compile caches stay whole), the overlay puts `enabledBreakpoints()` on `load` and sends `setBreakpoints` on each store change. An entry also holds its `condition`, `hitCount` and the condition pin's name (`label.pinName`); the file stays version 1 (the fields are optional, and an entry whose settings do not read is dropped). **Edit Breakpoint…** (`breakpointMenuItems`' `edit` in the Class graph, Behaviour Tree and State Machine node menus; a Details button per transition direction) opens `BreakpointSettingsDialog` through `useBreakpointSettingsEditor`, which stores the result with `setSettings`. Class nodes offer `conditionPins`: data outputs and wired data inputs whose type is Int, Float, Bool, String, Object or Actor; tree and state machine nodes pass `pins: null` (hit count only). A saved condition on a pin no longer offered stays listed until changed. The Breakpoints window shows `describeBreakpointSettings` next to each node. A `BREAKPOINT_PAUSE_CODE` cause opens the node through the same navigation as Pause On Errors (`openSessionSource`, severity `info`, so nothing is marked as an error). The **Breakpoints** window (`openByDefault: false` in the Scene and Class catalogs) lists them all. At a stop the overlay publishes the cause as `SimulationControls.stoppedAt` (cleared when the Simulation resumes or a Step starts); the chrome bar names it through `useBreakpointStop` (the breakpoint's saved names, the open Class's entry node title, the object) and **Stopped At** reopens the node. `GraphDebugStore.follow(instanceId)` selects the object now, or as soon as a roster lists it (the stop's Class comes into focus after the cause arrives); a subclass instance stopping in its parent's graph is not in that roster and is not followed. The runtime follows it from the next tick, so its path and values show after a Step. A Behaviour Tree's breakpoints are keyed by the tree's guid (`BT_DEBUG_GRAPH_ID`, tree node id); the tree editor's view passes `GraphBreakpoints.canBreak` accepting every node, the root included, which the dot and the Toggle Breakpoint command consult instead of the exec-pin rule. Card nodes (`BlueprintNodeShell card`) show the dot on the card's left edge, and `TreeNode` builds its menu when it opens so the breakpoint items are current. For a guid-keyed stop `useBreakpointStop` resolves the asset through the registry, titles a tree node from the open tree and appends `breakpointEvent` (`Patrol › Succeed (Started) on Guard`). A State Machine's are keyed by the graph's guid (`ANIM_STATE_MACHINE_DEBUG_GRAPH_ID`, state or transition row id): states take the dot (top left) and the standard node menu (`useNodeMenu`, breakpoint items as host items); transitions are toggled per row in Details (buttons, so they work under the authoring lock, which makes `PropertyGrid` read-only), and the badge's `data-breakpoint` is the view's state for the edge, which `stateMachineBreakpointView` takes from either row of a Both Ways pair (enabled first). Navigation switches to State Machine mode, and a focused transition id selects that transition and frames its source state. A transition re-drawn on the canvas gets a new id, so its breakpoint stays with the old one, like a deleted node's.
- **Instance rule**: "runs exactly this asset" means the component's effective asset guid (`treeGuid` / `graphGuid` variable, else the asset the component was added from). Neither graph kind nests, so no subtree or nested graph makes the rule ambiguous. A component is named for its actor.

## Performance and Frame Capture

- `SessionDiagnostics` admits one expensive recording or frame capture at a time; viewing results never records. Defaults: 10 s, 16 MiB accounted buffers. GPU timing is an engine-aggregate query, unaligned to frames; unsupported backends report `unavailable`.
- Tick phases: `TickPipeline` times each `TICK_TIMING_PHASES` entry apart (the World's `TICK_PHASES`, then `sceneSystems`, which the driver marks before Delays, Animation Graphs, tile animation, Behaviour Trees and the crowd); `lastScriptMs` is every phase but physics. Profile version 2 added the phases: `PERFORMANCE_TICK_COLUMNS` keeps version 1's six columns first (so `publishMs` stays at its offset) and adds `<phase>Ms` for each phase but physics. `parsePerformanceProfile` also opens version 1 files and keeps their six-column tick rows (`PERFORMANCE_TICK_COLUMNS_V1`) as read, so a reopened version 1 file exports unchanged; consumers find phases by column name and show none for version 1. The `stats` command carries `phaseMs` (the Stats `unit` row, in every host) and trace frames carry `publishMs`.
- Memory and long tasks: recordings write profile version 3, which adds two streams. `memory` (`PERFORMANCE_MEMORY_COLUMNS`) holds the host's accounted texture (`resourceCache.accountedBytes()`) and geometry (`accountedGeometryBytes()`) bytes. `SessionDiagnostics` samples them through its `sampleMemory` port every `STATS_COMMAND_INTERVAL_MS` while recording, whether or not the Stats HUD shows; both are maintained counters, so a sample reads two numbers. `longTasks` (`PERFORMANCE_LONG_TASK_COLUMNS`) holds main-thread long tasks from `observeBrowserLongTasks`, a `PerformanceObserver` on the frames' `performance.now()` clock. Safari reports none, so its observer is null. A task that started before the recording is left out, since the browser reports a task only after it ends. The profile's `identity.enabledDiagnostics` names `memory` and `long-tasks` when the host recorded them. Versions 1 and 2 open with both streams empty, and Preview's transfer (`PREVIEW_PROFILE_STREAMS`) carries every stream.
- The **Profiler** window ([`DiagnosticResultsStore`](../../../apps/editor/src/services/diagnostic-results-store.ts)) floats over the game like the Play Inspector (non-modal, no backdrop, `initialFocus={false}`, only Escape or Close dismisses it) and never takes the game's input: keyboard input needs the game canvas focused, so tapping the game gives it back while the window stays. A recording outlives the window: `ProfilerRecordingChip` shows **Recording** in the Play and Preview Build islands whenever `active === "profile"`, whoever started it, and its Stop opens the Summary. `profile start`, `profile stop` and `capture frame` (`EDITOR_COMMAND_NAMES`, reserved) never reach the game: both overlays' consoles run them against the store first (`runProfilerConsoleCommand`) and append them to the game's `help` (`withProfilerHelp`).
- Preview's diagnostics entry (`player-preview-diagnostics.js`) loads only after an origin-checked handshake and is omitted from ordinary exports. Transfer failures are explicit; never substitute partial or earlier profiles.
- Per-pass GPU timing, WebGPU capture, Spector integration and pixel readbacks are not provided.
